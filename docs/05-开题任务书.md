## 【一】项目概述

本项目将本组已完成并持续维护的 Windows 版《飞机大战》（Java Swing，约 60 个源文件）迁移到 Android 平台，并在移动端新增网络功能。

Windows 版现有能力：三档难度、五种敌机（含 Boss）、五种道具与容量 2 的栈式背包、暂停、七款按本机最高分解锁的皮肤、Supabase 云端排行榜（断网自动回退本地、仅新纪录上传）、60fps 插值渲染与音效。

Android 版目标：保留全部玩法与数值，替换与平台绑定的渲染、主循环、输入、音效、界面与网络传输，并新增实时对战与云端排行榜。

实施意义：

1. 复用判断：迁移前逐文件判定"哪些是平台无关的核心资产"，60 个源文件中约 78% 可迁移、其余集中重写，这本身是一次架构判断训练；
2. 平台迁移：同一份业务逻辑、两套平台 API，接触的是真实工程问题而非玩具 demo；
3. 网络编程：对战涉及长连接、状态同步、延迟处理与断线重连，覆盖完整链路；
4. 分层解耦：为让核心逻辑脱离平台可测，必须把逻辑层与渲染层分开，把课程的分层思想用在有真实复杂度的项目上。

目前进度：核心逻辑层（43 个类、纯 Java、22 项单元测试全绿）与渲染层已在 Android 上跑通；单机玩法、音效、背包点击使用、皮肤系统已完成。

## 【二】原有功能迁移分析

### 1. 选择迁移哪位小组成员的代码，为什么？

迁移本组成员徐晨洛（2024311359）的 Windows 版飞机大战（仓库 aircraftwar，Java Swing，约 60 个源文件）。

理由：该版本功能完整且经两个学期持续维护，三档难度、五种敌机、五种道具、背包、暂停、七款皮肤、云端排行榜均可用，玩法数值已调平衡；迁移时无需重新设计玩法，可把精力集中在 Android 适配与网络功能上。

### 2. 可复用模块及依据

判定方法：逐文件扫描 import，凡依赖 Android 上不存在的 API 即列为"需适配"。60 个源文件中 37 个为纯 Java，可原样复用。

（1）游戏对象模型与规则：bullet（子弹）、strategy（射击策略）、aircraft（5 种敌机 + 5 个敌机工厂）、item（道具与观察者事件）、dao 的接口与模型、三套难度子类。

依据：这些代码只做坐标运算、血量结算、概率判定、对象创建与事件广播，完全不接触 UI。Boss 分数阈值、炸弹伤害、冻结帧数、掉落概率等数值可原样保留。

（2）核心架构决策：逻辑与渲染分离、碰撞判定顺序、失效对象延迟清理，以及观察者 / 策略 / 工厂等设计模式，本身就支持"同逻辑、多平台"。

（3）产品与数值设计：三档难度的递增曲线、皮肤解锁阈值、"仅新纪录上传"的榜单口径，均为长期调校的成果，直接继承。

### 3. 需重新开发的模块及依据

（1）渲染：原用 JPanel / Graphics2D / BufferedImage，Android 无 Swing 与 AWT → 改为 SurfaceView + Canvas + Bitmap；

（2）主循环：原用 javax.swing.Timer（依赖 EDT），Android 无 EDT 且主线程不能跑游戏循环（会 ANR）→ 改为独立渲染线程 + 时间累加器；

（3）输入：原用 MouseListener / KeyListener，触屏无鼠标键盘 → 改为 MotionEvent；

（4）音效：原用 javax.sound.sampled，Android 无 Java Sound → 改为 SoundPool（音效）+ MediaPlayer（背景音乐）；

（5）界面：原用 JFrame / JDialog → 改为 Activity + 布局；

（6）本地存储：原用 Java 对象序列化写 .dat 文件，跨版本脆弱且 Android 不推荐 → 改为 SharedPreferences；

（7）云端网络：原用 java.net.http.HttpClient，Android 不提供该 API → 改为 OkHttp；

（8）配置读取：原用 java.nio.file 读 jar 同级文件，Android 无"jar 同级目录"概念 → 改为 assets / SharedPreferences。

## 【三】新增网络功能设计

### 功能一：实时双人对战（房间制 · 比分竞赛）

**功能内容**：两名玩家凭房间码进入同一对局，各自在本地运行关卡，实时看到对方分数与血量，先达到目标分者获胜，胜负由服务端判定。

**设计原因**：这是实验五的核心要求。采用"比分竞赛"而非"实时互射"——只需同步分数而非游戏状态，延迟容忍度高（200ms 内基本无感），实现复杂度与稳定性明显更好；同时房间、匹配、心跳、断线重连等网络工程问题一个不少，技术含量并未降低。

**技术实现思路**：WebSocket 长连接（OkHttp）承载房间管理与状态广播；客户端每 1 秒上报一次分数与血量；服务端按固定 tick 广播双方状态并判定胜负；断线后服务端保留房间 60 秒，重连补发当前状态；ping/pong 心跳保活，连续超时判定掉线。

### 功能二：云端排行榜与成绩同步

**功能内容**：昵称与本机最高分同步至云端，按三档难度分别展示前 100 名；断网时成绩写入本地待同步队列，联网后自动补传；Android 与 Windows 版共用同一张表，榜单跨端互通。

**设计原因**：Windows 版已有可用的 Supabase + RLS 方案，迁移成本低，同时覆盖实验四"排行榜与存储"；与对战功能形成"实时强交互 + 异步弱一致"两类网络场景的互补。

**技术实现思路**：用 Retrofit / OkHttp 调用 Supabase PostgREST 接口；沿用现有表结构与 RLS 策略（匿名可读、可插入、不可修改删除）；本地用 Room 保存历史与待同步队列，上传失败按指数退避重试；上传口径保持"只有超过本机该难度最高分才上传"。
