## 一、项目概述

### 1.1 项目内容

将已完成并持续维护的 **Windows 版飞机大战（Java Swing）** 迁移到 Android 平台，
并在移动端新增**实时网络对战**与**云端成绩同步**等网络功能，最终交付一个可在 Android
真机/模拟器上运行的完整游戏 APK。

Windows 版现状（迁移的事实基准，非草稿设计）：

| 方面 | 已实现内容 |
|------|-----------|
| 玩法 | 三档难度（简单/普通/困难）、五种敌机（Mob / Elite / ElitePlus / ElitePro / Boss）、Boss 分数阈值与递增血量、困难模式 Elo 射速 |
| 系统 | 五种道具（血包/炸弹/火力/超级火力/冰冻）、容量 2 的背包（栈式，先入后出）、暂停 |
| 表现 | 七款皮肤（按本机最高分解锁）、自绘 HUD、60fps 插值渲染、BGM 与音效 |
| 数据 | 全球排行榜（Supabase + RLS）、断网自动回退本地、仅新纪录上传 |
| 工程 | 观察者/策略/工厂/模板方法/单例/DAO 六种设计模式、EDT 单线程游戏循环、JUnit 测试 |

### 1.2 实施意义

1. **平台迁移能力**：把一个真实的、已投入使用的桌面应用搬到移动端，接触的是
   「同一份业务逻辑、两套平台 API」的真实工程问题，而不是写一个玩具 demo。
2. **网络编程落地**：课程要求的网络对战涉及长连接、状态同步、延迟处理、断线重连，
   这些是后端与客户端都要动手的完整链路，比单纯发一个 HTTP 请求更有技术含量。
3. **架构能力**：为避免「一个类既管规则又管绘制」，必须做逻辑层与渲染层解耦；
   这正好把课上讲的 MVC/MVP/MVVM 分层思想用在一个有真实复杂度的项目上。
4. **复用而非重写**：详见第二节 —— 经逐文件扫描，约 **77%** 的代码可复用，
   这本身就是一次关于「什么是平台无关的核心资产」的判断训练。

## 二、原有功能迁移分析

> 完整版见 [迁移分析](02-迁移分析.md)，本节为摘要。

### 2.1 迁移对象

迁移 **本组成员 Stardropflower 的 Windows 版飞机大战**（Java Swing，
仓库 `Stardropflower/aircraftwar`，约 60 个源文件）。

选择它的原因：功能完整且经过长期维护（排行榜、皮肤、暂停、60fps 插值等均为可用状态），
玩法规则已经调平衡，迁移时不需要再花时间设计玩法，可以把精力集中在 Android 适配上。

### 2.2 判定方法与结论

判定方法：逐文件扫描 `import`，凡依赖 Android 上不存在的 API 即判为需适配（不靠印象）。

| 级别 | 含义 | 文件数 |
|------|------|--------|
| A | 原样复用（纯 Java） | 37 |
| B | 机械替换即可复用 | 9 |
| C | 保留内核逻辑、重写平台外壳 | 1 |
| D | 必须完全重写 | 13 |

### 2.3 可复用的部分及原因

**① 游戏对象模型与规则（A 级，37 个文件）**

- `bullet/`、`strategy/`、`aircraft/`（含 5 种敌机与 5 个工厂）、`item/`（含观察者事件）、
  `dao/` 的接口与模型、三套难度子类。
- **原因**：这些代码只做坐标运算、血量结算、概率判定、对象创建与事件广播，
  完全不碰 UI。例如「炸弹对 Boss 与 ElitePro 各 100 伤害」「一颗子弹命中即消耗」
  「冻结 150 帧」「Boss 阈值 简单无/普通 1000/困难 800」这些规则，换到 Android 一行都不用改。

**② 核心架构决策可整体沿用**

- **逻辑 25Hz + 渲染 60fps 插值**：已验证可显著改善观感，且在 Android 上同样适用
  （逻辑与渲染解耦的做法天然适配 `SurfaceView` 独立渲染线程）。
- **观察者模式**处理炸弹/冰冻广播、**策略模式**切换弹道、**工厂模式**创建敌机 ——
  这些模式本身就是为「同逻辑、多平台」服务的，迁移时零成本。

**③ 数值与产品设计**

难度递增曲线、Boss 血量递增、皮肤解锁阈值、仅新纪录上传的榜单口径、断网回退策略，
都是长时间调出来的，直接继承。

### 2.4 需重新适配的功能模块及原因

| 模块 | 原实现 | 必须改的原因 | Android 方案 |
|------|--------|--------------|--------------|
| **渲染** | `JPanel.paintComponent` + `Graphics2D` + `BufferedImage` | Android 没有 Swing/AWT 绘图体系 | `SurfaceView` + `Canvas.drawBitmap`；HUD 用 `Paint`/`Shader` |
| **主循环** | `javax.swing.Timer`（EDT） | Android 无 EDT，且主线程不能跑游戏循环（会 ANR） | 独立渲染线程 + `Choreographer` 对齐 vsync，沿用时间累加器 |
| **输入** | `MouseListener` / `KeyListener` | 触屏没有鼠标与物理键盘 | `onTouchEvent`；暂停/切弹道改为界面按钮 |
| **音效** | `javax.sound.sampled.Clip` | Android 无 Java Sound | `SoundPool`（音效）+ `MediaPlayer`（BGM） |
| **图片加载** | `ImageIO.read` | Android 无 ImageIO | `BitmapFactory.decodeStream(assets)` |
| **界面** | `JFrame`/`JDialog` + FlatLaf 主题 | Android 无 Swing 组件 | `Activity` + XML 布局 / `RecyclerView` |
| **本地存储** | Java 对象序列化写 `.dat` | 序列化跨版本脆弱，且 Android 推荐结构化存储 | `SharedPreferences` / `Room(SQLite)`，改 JSON |
| **云端网络** | `java.net.http.HttpClient` | **预期 Android 不提供该 API**（Java 11 引入），见风险验证项 | OkHttp / Retrofit |
| **配置读取** | `java.nio.file` 读 jar 同级文件 | Android 无「jar 同级目录」概念 | `assets/` / `SharedPreferences` / `BuildConfig` |

> 补充说明：`application/Game` 是唯一「逻辑与平台强耦合在一个类里」的文件。
> 迁移时会把它拆成 **`GameWorld`（纯逻辑，可单测）+ `GameRenderer`（平台相关）**，
> 拆完后 Windows 版与 Android 版可共用同一个 `GameWorld`。

## 三、新增网络功能设计

按要求规划 **3 项**（第 1、2 项为必修，第 3 项为加分扩展）。

### 3.1 【必修①】实时双人对战

**功能内容**
- 两名玩家通过房间码或房间列表匹配进入同一局
- 双方各操控一架飞机，在同一战场内实时对抗，先击毁对方者胜
- 局内显示对手实时血量/分数，结算页面记录胜负

**设计原因**
- 课程「网络对战」的核心要求；课件第 22 页也明确列出「双人对战得分实时显示」场景
- 它覆盖了网络编程最难的部分：长连接、低延迟通信、状态同步、断线处理，
  比「上传一个分数」更能体现技术含量
- 玩法上，对战比各自跑分更有重复游玩价值

**技术实现思路**
1. **传输层**：WebSocket 长连接（OkHttp WebSocket），服务端用轻量框架（Node.js / Spring Boot）
   维护房间与玩家映射；房间码 6 位，支持房间列表与随机匹配。
2. **同步策略**：采用 **服务器权威 + 客户端预测**：
   - 客户端只上传**输入**（触控目标坐标、是否开火），大幅降低带宽且天然抗作弊
   - 服务器按固定 **20–25Hz tick** 推进权威状态并广播
   - 客户端对**本机**立即响应（预测，保证跟手），对**远端玩家**做**插值 + 平滑**
3. **延迟处理**：直接复用 Windows 版已验证的 60fps 插值机制处理远端实体；
   为每个远端状态打 tick 序号，按序播放；ping/pong 测量 RTT 并在界面显示网络状态。
4. **断线与异常**：心跳保活；短暂断线自动重连并请求最近状态快照；对手掉线判定为胜利并提示。
5. **房间生命周期**：创建 → 等待 → 就绪 → 对局 → 结算 → 销毁；服务端做超时清理。

**风险与对策**：移动网络抖动大 → 采用插值而非严格锁步（lockstep），
牺牲极小的一致性换取不卡顿；必要时对物理判定做服务端兜底。

### 3.2 【必修②】云端成绩同步与排行榜

**功能内容**
- 玩家昵称与个人最佳成绩同步到云端，全球榜/分难度榜可查
- 断网时成绩存入本地待同步队列，联网后自动补传
- Windows 版与 Android 版**同榜互通**（共享同一套 Supabase 表）

**设计原因**
- Windows 版已有可用的 Supabase + RLS 方案，迁移成本低，属于「把已有能力带到新平台」
- 课件第 22 页的「游戏得分云同步」正是此场景；同时覆盖实验四「排行榜与存储」
- 与对战功能形成互补：对战是实时强交互，排行榜是异步弱一致，两类网络场景都练到

**技术实现思路**
1. **接口层**：Retrofit + OkHttp 调 Supabase PostgREST（REST），沿用现有表结构与 RLS 策略
   （匿名可读、可插入、不可改删），客户端 `anon key` 与 Windows 版一致。
2. **本地层**：Room 保存本机历史与**待同步队列**（成绩 + 时间戳 + 重试次数）；
   上传成功置为已同步，失败保留并指数退避重试。
3. **上传口径**：沿用 Windows 版已验证的「**只有超过本机该难度最高分才上传**」，
   避免重复提交与刷榜噪音。
4. **安全**：密钥仍只放 anon/publishable key，权限边界由数据库 RLS 保证；
   绝不把 service_role 打进客户端。

### 3.3 【加分】幽灵竞速回放

**功能内容**
- 记录每局的输入序列与定时状态快照，形成「回放」
- 玩家可与榜单前列玩家（或自己的最佳局）的**幽灵**同屏竞速

**设计原因**
- 复用现有插值渲染即可实现，边际成本低
- 显著提升排行榜的观赏性与可玩性，是结题时的亮点
- 体现「确定性逻辑 + 输入重放」这一经典游戏架构思想

**技术实现思路**：确定性逻辑 + 输入回放（记录 tick 与输入），按 tick 重放即可复现；
用半透明飞机渲染幽灵；只上传精简后的输入序列（远小于逐帧状态），体积可控。
