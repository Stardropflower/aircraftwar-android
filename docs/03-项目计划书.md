## 二、逐项可行性分析与细化设计

### 2.1 每难度云端排行榜（前 100 名）

**现状**：Windows 版已实现 Supabase 云端榜，但每种难度只取前 **15** 名
（`SupabaseRankDAO.TOP_LIMIT = 15`）。

**改造点**

| 项 | 方案 |
|---|---|
| 名次上限 | 15 → **100** |
| 查询性能 | 现有索引 `scores_leaderboard_idx (difficulty, score desc, created_at desc)` 完全覆盖，100 行无压力 |
| 加载策略 | `RecyclerView` 分页加载（每页 20），避免一次渲染 100 行卡顿 |
| 附加能力 | 「我的排名」：额外发一条 `player_name=eq.<昵称>` 的查询取自己的最好成绩与名次 |
| 榜单维度 | 简单 / 普通 / 困难 三个 Tab |
| 缓存 | 本地 Room 缓存最近一次成功结果，断网可看（标注「离线数据」） |

**风险**：低。**工作量：0.5 人日。**

### 2.2 双人合作模式

**需求细化**

- 两台英雄机同场作战，**各自独立血量**，共享敌人与 Boss
- **无友伤**：双方子弹只判定敌机，不判定对方机体
- **不同控制**：一台设备上划分左右两个触控区（见 4.1 的决策）
- **队伍分数** = 两人得分之和，击败 Boss 团队共享奖励
- **独立双人排行榜**：与单人榜分开统计

**技术要点**

| 项 | 方案 |
|---|---|
| 英雄机实例 | 现有 `HeroAircraft` 是**单例**（`getInstance()`），双人必须改成两个实例 → 需重构为可多实例（保留 `HeroAircraft` 单例给单人模式，或整体改为工厂创建） |
| 输入 | 左右触控区各跟一根手指；`MotionEvent` 需按 `pointerId` 分流 |
| 碰撞 | 主循环中遍历两架英雄机，各自与敌机/敌弹判定 |
| 计分 | `GameWorld` 增加 `playerIndex` 概念，分数分别累计再汇总 |
| 排行榜 | 表加 `mode` 字段（`SINGLE`/`COOP`/`VERSUS`），双人榜按 `mode=COOP` 过滤 |

**为什么"英雄机单例"是必须改的**：现在 `HeroAircraft.getInstance()` 全局唯一，
双人模式若复用会变成"两个玩家控制同一架飞机"。这是本次改造中**唯一需要动核心类结构**的地方，
需提前排期。

**风险**：中（同屏 UI 布局、触控冲突、单例重构）。**工作量：3–4 人日。**

### 2.3 双人对战模式（先达到一定分数获胜）

**这一项的设计很关键，值得单独说明**：原计划写的是「可见对方分数，先达到一定分数获胜」，
而不是「互相射击对战」。**这是对本课程项目最合适的取舍**：

- 若做成实时互射，需要同步子弹、碰撞、血量，属于**状态同步**，延迟敏感、实现复杂、易掉线
- 按「比分竞赛」做，**只需要同步一个数字（分数）**，延迟 200ms 都基本无感
- 又有完整的网络链路：房间、匹配、连接、心跳、断线、结算，技术含量一点不少

**协议设计（WebSocket，JSON）**

```jsonc
// 客户端 -> 服务端
{"type":"create",  "name":"玩家A", "difficulty":"NORMAL", "target":5000}
{"type":"join",    "room":"A3F9K2", "name":"玩家B"}
{"type":"score",   "room":"A3F9K2", "score":1200}   // 每 1s 上报一次
{"type":"leave",   "room":"A3F9K2"}

// 服务端 -> 客户端
{"type":"joined",  "room":"A3F9K2", "you":"A", "opponent":"玩家B"}
{"type":"state",   "a":{"name":"玩家A","score":1200,"hp":900},
                   "b":{"name":"玩家B","score":950,"hp":1000}}
{"type":"over",    "winner":"A", "scoreA":5000, "scoreB":4210}
{"type":"opponent_left"}
```

**关键设计**

| 项 | 方案 |
|---|---|
| 房间 | 6 位房间码（大写字母+数字，排除易混淆的 O/0/I/1），支持创建与加入 |
| 同步频率 | 客户端每 1s 上报一次分数与血量（**不是每帧**） |
| 判定 | **服务端权威**：由服务器判断谁先达到目标分，避免客户端作弊 |
| 结算 | 双方分数写入 `scores` 表（`mode=VERSUS`），形成对战榜 |
| 断线 | 服务器保留房间 60s；重连后补发当前 `state` |
| 超时 | 15 分钟未达目标分则判分数高者胜 |

**服务端选型**：Node.js + `ws` 库（轻量，几十行核心逻辑）或 Spring Boot WebSocket。
部署用一台云服务器（学生机即可）。**这是本项目唯一的服务端组件，规模可控。**

**风险**：中（需部署服务端、需处理并发房间）。**工作量：4–5 人日。**

### 2.4 商城 —— 积分可行，RMB 充值不可行

#### ✅ 可做：纯积分商城

| 项 | 方案 |
|---|---|
| 货币 | 虚拟货币「金币」，**只能由游戏内获得**，不可购买 |
| 获取 | 每局按 `得分/100` 结算；双人/对战模式有额外系数 |
| 商品 | 皮肤（7 款）、消耗品（开局携带 1 个炸弹 / 复活 1 次 / 护盾） |
| 存储 | 金币与已购清单存 Room + 云端同步（防卸载丢失） |
| 界面 | 商城页：Tab 分「皮肤 / 道具」，卡片显示价格与所有权 |

#### ❌ 不能做：RMB 充值（建议改为演示占位）

**三个硬约束**（不是技术问题，是合规问题）：

1. **支付渠道门槛**：接入支付宝/微信支付开放平台需要**企业主体**（营业执照、对公账户、
   签约商户号）。个人开发者无法申请。
2. **应用商店分成与审核**：真钱虚拟商品必须通过应用商店内购（Google Play Billing /
   国内各商店），个人开发者账号上架虚拟商品审核严格，且课程项目不上架。
3. **合规风险**：虚拟货币与真实货币挂钩，涉及预付卡/金融监管，个人项目不应涉及。

**替代方案（二选一，建议 A）**

- **A. 完全去 RMB**：金币只能靠玩获得。计划书里删掉「RMB 充值」四个字。
- **B. 演示占位**：保留一个「充值」入口，点击后弹出「演示环境，未接入真实支付」并发放测试金币。
  界面明确标注，仅用于展示交互流程。

> 建议选 **A**。课程评审看的不是有没有支付通道，而是有没有完整的"货币—商品—兑换"闭环，
> 用游戏内金币就能完整演示。

**风险**：低。**工作量：3 人日（积分商城部分）。**

### 2.5 皮肤特效 + 皮肤专属技能

**皮肤特效**

| 皮肤 | 特效 |
|---|---|
| 水蓝 | 基准（无额外特效） |
| 银翼 | 高速移动时白色拖尾 |
| 翡翠 | 机身绿色呼吸光晕 |
| 帝皇 | 金色粒子环绕 |
| 赤霄 | 弹道带火焰尾迹 |
| 曼巴 | 紫色残影 |
| 曜黑 | 半透明消隐 + 青色边光 |

实现：`ParticleSystem`（粒子池）+ `Canvas` 绘制；拖尾用环形缓冲记录最近 N 帧位置。
**注意性能**：粒子数设上限（如 200），避免低端机掉帧。

**皮肤专属技能**

| 皮肤 | 技能 | 平衡定位 |
|---|---|---|
| 水蓝 | 无 | 基准 |
| 银翼 | 道具拾取范围 +30% | 弱 |
| 翡翠 | 回血效果 +50% | 中 |
| 帝皇 | 开局自带 1 层护盾 | 中 |
| 赤霄 | 射速 +10% | 强 |
| 曼巴 | 20% 概率双倍伤害 | 强 |
| 曜黑 | 每局首次致死免疫 | 强 |

实现：`Skin` 枚举增加 `Skill` 字段（枚举 + 参数），`GameWorld` 在对应时机查询
（拾取判定、回血计算、射击间隔、伤害结算、致死判定）。

**⚠️ 必须处理的公平性问题**

技能会破坏**联机对战**的公平性。三种处理方式：

- **A. 对战模式锁定统一皮肤**（推荐）：对战/合作时技能不生效，只保留外观
- B. 对战匹配时按技能分级
- C. 允许技能，接受不平衡

建议 **A** —— 实现简单、逻辑清晰、也便于向老师解释"为什么技能只在单机生效"。

**风险**：中（平衡性、性能）。**工作量：3 人日。**

### 2.7 广告系统 —— 只能做模拟实现

**为什么接不了真实广告**

1. 需要广告平台开发者账号（穿山甲/优量汇/AdMob），需**应用已上架**才能创建正式广告位
2. 课程项目不上架应用商店 → 拿不到广告位 ID → SDK 无法拉取广告
3. 即使拿到测试广告位，也只在测试白名单设备上生效

**可行方案：模拟广告 + 可替换接口**

```
AdService (接口)
├── showRewardedAd(callback)   // 看广告复活
└── isAvailable()

MockAdService   ← 本期实现：播放本地占位视频 30s + 倒计时，结束回调发奖励
RealAdService   ← 预留：接穿山甲/AdMob 时实现同一接口即可
```

界面明确标注「演示：模拟广告」。这样既演示了"看广告复活"的完整交互闭环，
又保留了真实接入的扩展点，也便于向老师说明技术限制。

**风险**：低。**工作量：1 人日。**

## 五、技术方案要点

### 5.1 客户端架构（分层）

```
ui/          Activity / Fragment / RecyclerView Adapter      ← 只做展示与交互
core/        GameWorld（纯逻辑，无 Android 依赖，可单测）      ← 从 Windows 版迁移
             ├── entity/    飞行物、敌机、子弹、道具
             ├── strategy/  射击策略、难度策略
             ├── event/     观察者（炸弹/冰冻）
             └── rule/      碰撞、计分、难度递增
render/      SurfaceView + Canvas + 粒子系统 + 插值          ← 平台相关
input/       触屏分流（单/双人）                              ← 平台相关
audio/       SoundPool / MediaPlayer                        ← 平台相关
data/        Room（本地）+ Retrofit（云端）+ 同步队列          ← 平台相关
net/         WebSocket 对战客户端                            ← 平台相关
```

**核心原则**：`core/` 一行 Android API 都不许有 —— 这样它能在 JVM 上跑单元测试，
也能被 Windows 版复用。这是本项目架构上最重要的一条约束。

### 5.2 数据模型（Supabase 表结构演进）

现有表 `scores`：`id, player_name, score, difficulty, created_at`
RLS：匿名可读、可插入、不可改删

**需要新增/修改**

```sql
-- 1) 增加模式维度（单机 / 合作 / 对战）
alter table public.scores
  add column if not exists mode text not null default 'SINGLE'
  check (mode in ('SINGLE','COOP','VERSUS'));

-- 2) 金币与已购清单（建议独立表）
create table if not exists public.players (
  id          bigint generated always as identity primary key,
  player_name text not null unique,
  coins       integer not null default 0 check (coins >= 0),
  updated_at  timestamptz not null default now()
);

create table if not exists public.purchases (
  id          bigint generated always as identity primary key,
  player_name text not null,
  item_id     text not null,
  created_at  timestamptz not null default now(),
  unique (player_name, item_id)
);

-- 3) 榜单索引按 mode 调整
create index if not exists scores_mode_idx
  on public.scores (mode, difficulty, score desc, created_at desc);
```

> ⚠️ **安全提醒**：`players.coins` 若允许匿名更新，任何人可给自己加金币。
> 课程项目可接受，但**必须在结题报告里写明这是已知限制**（正确处理需引入 Supabase Auth + 服务端校验）。
> 现有 `scores` 表的 RLS 策略**保持不变**（只增不改），这条底线不能破。

### 5.3 网络协议（对战）

见 2.3 的 JSON 协议。补充约定：
- 连接建立后 10s 内需完成 `create`/`join`，否则服务端断开
- 心跳：客户端每 15s 发 `ping`，服务端回 `pong`；连续 2 次无响应判定断线
- 所有消息带 `ts`（客户端时间戳）用于计算 RTT 并显示网络质量

## 六、里程碑排期（对应课程 7 次实验）

## 七、工作量与人员分工建议

### 1 人组（约 6–7 周）
按 MoSCoW 顺序推进：Must 全部完成（约 20 人日）→ Should 择要（约 8 人日）→ Could 视情况。
**建议明确砍掉**：RMB 充值、真实广告、完整剧情。

### 2 人组（约 3–4 周，可并行）

| 角色 | 负责模块 | 依据 |
|------|----------|------|
| 客户端 | `core/` 迁移、渲染、输入、UI、音效、粒子 | 已熟悉 Windows 版代码结构 |
| 服务端 + 数据 | 对战服务端、WebSocket 客户端、Supabase 表演进、Room 同步 | 侧重后端与网络 |

**并行边界**：`core/` 与 `ui/`、`net/` 之间接口先定死（`GameWorld` 的输入输出契约），
两人各自开发不会互相阻塞。

## 八、验收标准

| # | 标准 | 验证方式 |
|---|------|----------|
| 1 | 三档难度均可完整游玩至 Game Over 并正确结算 | 真机手测 |
| 2 | 排行榜正确显示前 100 名，分难度切换正常 | 造 120 条测试数据验证分页 |

| 8 | 主循环在低端机上稳定（逻辑 25Hz、渲染 ≥50fps） | 帧率监控 + 真机对比 |

## 十、与原计划的差异汇总

| 原计划 | 调整后 | 原因 |
|--------|--------|------|
| 皮肤/道具商城（RMB 充值） | 积分商城，**去掉 RMB 充值** | 支付渠道需企业主体，个人项目不可行 |
| 广告系统（看 30s 复活） | **模拟广告** + 可替换接口 | 需应用上架与广告位审核 |
| 剧情模式（待定） | **本期不做 / 折中为关卡模式** | 美术文案成本远超收益 |
| 双人合作（未指明同屏/联机） | **同屏双人** | 与"不同控制"描述一致，且与对战模式互补 |
| 双人对战（可见分数先达标获胜） | **保持原设计** | 只同步分数，延迟容忍度高，是本方案最优取舍 |
