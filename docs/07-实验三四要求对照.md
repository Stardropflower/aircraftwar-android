## 八、关于「排行榜用 Supabase 还是 SQLite」

> 这条是架构决策，需要说清楚，因为两件事被混在一起了。

### 8.1 先纠正一个事实：SQLite 的延迟并不高

| | SQLite | Supabase |
|---|---|---|
| 本质 | 手机**本地**的嵌入式数据库（一个文件） | 云端 PostgreSQL，通过 HTTPS 访问 |
| 一次读写延迟 | **亚毫秒级**（µs～ms 量级，无网络） | **几十到几百毫秒**（取决于网络与区域） |
| 断网 | 完全不受影响 | **不可用** |

SQLite 没有服务端、不走网络，它就是进程内的一个 C 库 + 一个本地文件。
「SQLite 延迟高」这个印象通常来自把它和「远程数据库」搞混了。
真正高延迟的是 Supabase——每次查询都是一次网络往返。

**这直接推翻了「SQLite 延迟高、不适合同屏对战」这个前提**：
- SQLite 延迟远低于 Supabase
- 而且**同屏对战根本不碰数据库**——两个玩家在同一台设备上，状态都在同一个进程的内存里，
  延迟是微秒级的。数据库只在对局结束时存成绩。

### 8.2 它们不是二选一，本来就分工不同

你任务书里其实已经写清楚了（`docs/01-任务书.md` 第 156 行）：

> **本地层**：Room 保存本机历史与**待同步队列**（成绩 + 时间戳 + 重试次数）

**Room 底层就是 SQLite。** 所以任务书原方案是：

| 层 | 用什么 | 职责 |
|---|---|---|
| 本地 | **SQLite**（任务书写的 Room，即 SQLite 的封装） | 本机排行、历史成绩、**断网待同步队列** |
| 云端 | Supabase PostgREST | 跨端榜单前 100 名、Android 与 Windows 互通 |

两者的关系是「本地优先 + 云端同步」，不是「用谁替代谁」。

### 8.3 结论与建议

| 结论 | 说明 |
|---|---|
| **实验四必须用 SQLite** | 课件实验内容第 4 条原文：「改用 SQLite 数据库存储排行榜数据」，验收标准就是它 |
| **Supabase 继续用** | 云端榜（功能二）不动，负责跨端互通 |
| **两者不冲突** | SQLite 是本地权威 + 离线队列，Supabase 是云端汇总 |

所以实验四做完之后的正确形态是：

```
游戏结束
  ├─ 写入 SQLite（本地榜单，立即可见，离线也能看）
  └─ 若刷新本机纪录 → 加入 SQLite 待同步队列
                        └─ 联网时 OkHttp 上传 Supabase → 标记已同步
```

这个结构同时满足：
- 实验四的 SQLite 要求
- 任务书里「断网时成绩写入本地待同步队列，联网后自动补传」
- 云端榜「只上传新纪录」的口径
- 同屏对战（不碰数据库）

> ⚠️ 如果坚持「排行榜只用 Supabase、不引入 SQLite」，实验四的实验内容第 4 条就没法验收。
