## 三条约定

**① 代码摘录是逐字复制的。** 单段不超过 15 行，超了就截断并标 `// ...（省略）`。
行号格式是 `文件名.java:行号`，可以直接跳过去对照。

**② 每一节都按同一个套路写：**

```
#### `方法名()`
（这段真实代码）
- 在干嘛：一句话说清这个方法的职责
- 为什么这么写：为什么不那样写，踩过什么坑
- 老师可能问：（可选）这个地方容易被追问什么
```

**③ 重点是"为什么"，不是"是什么"。** 代码摆在那里谁都能读，
文档要回答的是"为什么不是另一种写法"——那才是验收时真正会被问的。

## 一、启动链路与二级菜单

> 一句话：从你在桌面上戳一下 App 图标，到屏幕中间浮出「单机模式 / 联机对战」那块面板，中间每一行代码在干嘛——以及为什么它长得一点也不像普通安卓界面。

这一章只盯两个文件：`ui/MainActivity.java`（267 行）和 `ui/visual/MenuOverlayView.java`（643 行）。
读完你应该能回答三个问题：**开机那 40 行干了什么、面板上的字和方块是怎么画出来的、手指戳下去怎么知道点中了哪一块。**

### 1.1 先认人：一个是"壳"，一个是"脸"

| 文件 | 身份 | 干的事 | 一句话印象 |
|------|------|--------|------------|
| `MainActivity` | 普通 Activity | 加载 XML 骨架、绑按钮、开面板、跳页面、存昵称 | 前台接待，只负责开关门和引路 |
| `MenuOverlayView` | 自己写的 `View` 子类 | 用 `Canvas` 画面板和卡片，自己收触摸事件 | 一块会画画的玻璃，贴在接待台上 |

关键差别在于：`MainActivity` 里所有界面元素都来自 `res/layout/activity_main.xml`（`findViewById` 拿到的），
而 `MenuOverlayView` 里**一个 `R.layout` 都没有**，连图标都是用 `canvas.drawLine` 画的。
它整个类里跟项目有关的 `import` 只有三行——`R`、`Difficulty`、`LocalStore`（`MenuOverlayView.java:16-18`）。
记一下这个细节，后面讲回调时要用：**它不知道 `GameActivity` 存在**。

### 1.2 onCreate：开机那 40 行其实是四道工序

#### `onCreate()`

```java
    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        store = new LocalStore(this);
        debugGrant = getIntent() != null && getIntent().getBooleanExtra("debug_grant", false);

        // ① 加载 XML 布局（实验三第 8 页：Activity 启动时系统调用 onCreate，
        //    通过 setContentView() 加载布局资源）
        setContentView(R.layout.activity_main);
        UiInsets.applySystemBars(findViewById(R.id.menu_scroll));
        // 底部那行装饰字是首页专属，别的页面开着会和内容打架
        ((StarfieldView) findViewById(R.id.bg_starfield)).setWatermarkEnabled(true);
```

- **在干嘛**：先 `new LocalStore(this)`——整个页面的数据都从这一个对象拿（最高分、皮肤、昵称、静音开关）。`debugGrant` 只在调试时用 `adb ... --ez debug_grant true` 打开，正式包里没人传这个 extra，所以是 `false`。然后 `setContentView` 把 XML 塞进 Activity 的窗口，`UiInsets.applySystemBars(...)` 把状态栏/导航栏的高度换算成 padding 加到菜单滚动区（`menu_scroll`）上，最后单独给星空背景打开底部装饰字。
- **为什么这么写**：`store` 放在最前面，是因为后面每一行几乎都要用它；`UiInsets` 单独抽出来，是因为**每个页面都要处理刘海和手势条**，写在 Activity 里会重复四遍。
- **老师可能问**：`savedInstanceState` 干嘛的？—— 转屏或系统回收后重建时它不为 `null`，本章后面用它决定"要不要重播开场动画"。
- **顺带说一句**：上面注释写着 `debug_grant` "只在 DEBUG 包里生效"，但这一行其实没判断 `BuildConfig.DEBUG`（对比 `startEntrance` 里 `replay_intro` 那个（`164-167`）就判断了）。目前靠"正式包没人传这个 extra"兜住，属于可以顺手加一行判断的小不一致。

#### `onCreate()`（接着：找控件、绑监听）

```java

        bestScoreLabel = findViewById(R.id.tv_best);
        skinLabel = findViewById(R.id.tv_skin);
        titleLabel = findViewById(R.id.tv_title);
        subtitleLabel = findViewById(R.id.tv_subtitle);
        nameInput = findViewById(R.id.et_name);
        nameInput.setText(store.getPlayerName());

        // ③ 基于监听的事件处理（实验三第 11 页）：给控件绑监听器
        findViewById(R.id.btn_start).setOnClickListener(v -> openPanel(MenuOverlayView.Mode.START));
        findViewById(R.id.btn_skin).setOnClickListener(v -> openSkinPage());
        findViewById(R.id.btn_rank).setOnClickListener(v -> openRankPage());
        findViewById(R.id.btn_settings).setOnClickListener(v -> openPanel(MenuOverlayView.Mode.SETTINGS));
```

- **在干嘛**：五个控件存成字段（后面动画和刷新要用），昵称输入框直接填上上次存的名字。四个按钮各绑一个 lambda：两个开面板、两个跳页。
- **为什么这么写**：需要反复访问的控件才存字段（`bestScoreLabel`、`skinLabel`、`titleLabel`、`subtitleLabel`、`nameInput` 五个）；只点一次的按钮就地 `findViewById(...).setOnClickListener(...)`，不占字段。注意 `btn_start` 和 `btn_settings` 都走同一个 `openPanel`，只是传的 `Mode` 不一样——**一个方法顶两个按钮**。
- **老师可能问**：为什么不用 `ButterKnife` / `ViewBinding`？—— 项目刻意走实验三的"手写 findViewById"路线，交作业时能对着 PPT 一页一页讲。

#### `onCreate()`（最后：排队出场、刷新、接管返回键）

```java
        cascadeViews = new View[]{
                bestScoreLabel,
                findViewById(R.id.btn_start),
                findViewById(R.id.btn_skin),
                findViewById(R.id.btn_rank),
                findViewById(R.id.btn_settings),
                skinLabel,
                findViewById(R.id.row_name),
        };

        startEntrance(savedInstanceState == null);
        registerBackHandling();
    }
```

- **在干嘛**：把 7 个控件按"出场顺序"塞进一个数组；`refreshLabels()` 刷最高分和皮肤名；`startEntrance(...)` 决定播不播片头；`registerBackHandling()` 接管返回键。
- **为什么这么写**：`savedInstanceState == null` 这个判断，意思是**只有冷启动才播开场动画**。从游戏页退回来、或者转屏重建时它不为 `null`，就不播——否则每打一局回来都要再等一次片头，很烦人。`cascadeViews` 用数组而不是写死 7 行动画，是因为 `playCascadeIn` 要按下标算延迟（`i * 45L`）。
- **老师可能问**：数组里为什么全是 `findViewById`？—— 因为字段只存了需要读写的控件，按钮用不着留引用，动画时再找一次，代价可以忽略。

### 1.3 布局明明是 XML 的，为什么说"界面靠自绘"

打开 `res/layout/activity_main.xml`，骨架就三层（`activity_main.xml:17-29`）：

```
FrameLayout  root_main        ← 根容器，负责"叠放"
 ├─ StarfieldView bg_starfield  ← 动态星空，铺满
 └─ ScrollView menu_scroll      ← 菜单内容，背景透明，让星空透上来
      └─ LinearLayout（标题、四个按钮、昵称行…）
```

所以准确的说法是：**静态骨架走 XML，动态浮层走自绘**。一级菜单那些按钮、标题、输入框是 XML 声明的；而二级面板是运行时 `new MenuOverlayView(this)` 再 `addView` 上去的，压根不在 XML 里。

为什么不干脆用 `Dialog` 或者 `PopupWindow`？作者在类注释里给了理由（`MenuOverlayView.java:22-25`），翻成大白话是三条：

1. **样式不听你的**。系统对话框的圆角、阴影、弹出曲线是固定的，跟这套深色自绘菜单摆在一起像两个人做的。
2. **要跟星空透叠**。面板背后要能看到压暗的星空在动，对话框会自带一层不透明的窗口背景，叠不出来。
3. **动画要"连续"**。要求面板从 92% 放大到 100%、同时背景从透明压到 62% 黑，这是一条连续曲线；用属性动画拼两个 View 反而更难对齐。

打个比方：XML 是宜家柜子的板材，柜子本身是钉死的；自绘是墙上的投影，想让它从哪儿亮起来、亮多快，都是你说了算。

> 老师可能问：`setContentView` 之后还能加 View 吗？—— 能，往 `root_main` 这个 `FrameLayout` 里 `addView` 就行，后加的在上面（后画的盖住先画的），这正是"叠"的实现方式。

### 1.4 openPanel：面板怎么贴上去，点了又怎么传回来

#### `openPanel()`

```java
    private void openPanel(MenuOverlayView.Mode mode) {
        if (panel != null && panel.isShowing()) {
            return;
        }
        panel = new MenuOverlayView(this);
        panel.bind(store, new MenuOverlayView.Listener() {
            @Override
            public void onStartGame(Difficulty difficulty) {
                panel = null;
                startGame(difficulty);
            }
```

- **在干嘛**：`new` 一个面板 → `bind(store, listener)` 把数据和"回调单"塞进去 → `addView` 铺满全屏 → `panel.open(mode)` 开始播进场动画（后面 142-146 行）。三个回调（`onStartGame` / `onBattle` / `onDismiss`）里**第一句都是 `panel = null`**，然后再做真正的动作。
- **为什么这么写**：`if (panel != null && panel.isShowing()) return;` 是防连点——面板退场动画有 0.16 秒，这期间 `isShowing()` 还是 `true`，所以猛戳"开始游戏"也只会有一个面板。`panel = null` 放在跳转之前，是为了让 Activity 立刻"忘掉"这块面板，避免它已经 `removeView` 了字段还指着旧对象。宽度高度都用 `MATCH_PARENT`，因为面板要盖住整个屏幕才能接收"点空白处关闭"。
- **老师可能问**：为什么回调里不直接 `startActivity`？—— 因为 `MenuOverlayView` 里没有 `GameActivity` 的 import，它只发一个"用户选了难度"的信号，具体去哪由 Activity 决定。这样这块面板以后搬到别的页面也能用。

这就是 `Listener` 接口存在的全部意义：**面板负责"记录用户点了什么"，Activity 负责"点了之后去哪"**。接口只有三个方法（`MenuOverlayView.java:42-49`），比一大坨 `switch` 干净。

### 1.5 Mode：三格状态机，不是三个页面

#### `Mode`

```java
    public enum Mode {
        /** 开始游戏：模式选择 */
        START,
        /** 开始游戏：难度选择 */
        DIFFICULTY,
        /** 设置 */
        SETTINGS
    }
```

- **在干嘛**：整个面板只有**一个** `View` 实例，靠 `mode` 字段决定画什么、点哪儿有效。`START` 和 `DIFFICULTY` 是"开始游戏"这条线的两步，`SETTINGS` 是另一条线。
- **为什么这么写**：如果做成三个类，进场/退场动画、压暗背景、关闭叉、脚注就得复制三份；做成三个 `Mode`，这些公共部分（`onDraw` 里 277-323 行）只写一次，只是中间那段内容按 `mode` 分派。面板高度也是按 `mode` 算的，所以切换状态时面板会"变高变矮"。

状态怎么跳，一张表说清：

| 当前 Mode | 用户动作 | 结果 | 代码 |
|-----------|----------|------|------|
| `START` | 点第 1 张卡片 | `mode = DIFFICULTY`，原地 `invalidate()` | `MenuOverlayView.java:613-616` |
| `START` | 点第 2 张卡片 | 收面板 → 通知宿主开房间页 | `619-620` |
| `DIFFICULTY` | 点某一档难度 | 收面板 → 通知宿主开局 | `622-625` |
| `DIFFICULTY` | 点左上返回箭头 / 系统返回键 | 退回 `START` | `135-138` |
| `SETTINGS` | 点开关 | **状态不变**，只翻转开关 + 重画 | `626-636` |
| 任意 | 点空白 / 点右上叉 | 关闭 | `589-599` |

#### `goBack()`

```java
    /** 返回上一层：难度页退回模式页，模式页/设置页直接关掉 */
    public void goBack() {
        if (mode == Mode.DIFFICULTY) {
            mode = Mode.START;
            invalidate();
        } else {
            dismiss();
        }
    }
```

- **在干嘛**：只有"难度页"有上一层，退回去；其它状态直接关面板。改完 `mode` 只要 `invalidate()`，系统下一帧就会调 `onDraw` 重画——**没有新建任何 View**。
- **为什么这么写**：难度页退模式页是"同一块面板换内容"，用状态切换比"关掉再开一个"平滑得多，也不会闪一下黑。
- **老师可能问**：返回箭头和系统返回键走的是同一段逻辑吗？—— 是。触摸命中 `backRect` 调 `goBack()`（`593-596`），系统返回键经 `registerBackHandling` 也调 `goBack()`（`MainActivity.java:107-108`）。

### 1.6 帧循环：一块静态面板为什么要 Choreographer

#### `MenuOverlayView()`

```java
    public MenuOverlayView(Context context, AttributeSet attrs) {
        super(context, attrs);
        density = context.getResources().getDisplayMetrics().density;
        setClickable(true);
        strokePaint.setStyle(Paint.Style.STROKE);
        loadBitmaps();
    }
```

- **在干嘛**：把屏幕的 `density`（1dp 等于几个像素）存成 `final` 字段，整个类后面算尺寸全靠它；`setClickable(true)` 让这个 View 能收到触摸；给描边画笔设成空心；`loadBitmaps()` 用 `inScaled = false` 把 `hero`、`boss` 两张图按原始像素解码。
- **为什么这么写**：`setClickable(true)` 这行**最容易被漏掉**——`View` 默认不可点击，不设的话 `onTouchEvent` 根本收不到 `ACTION_DOWN`，面板会变成"看得见但点不动"。`inScaled = false` 是为了不让系统按屏幕密度提前把图缩放一遍（那样会糊），缩放留给绘制时的 `RectF` 精确控制。

#### `doFrame()`

```java
        float dt = Math.min((nanos - lastFrameNanos) / 1_000_000_000f, 0.05f);
        lastFrameNanos = nanos;

        float speed = 1f / 0.24f;
        if (dismissing) {
            progress -= dt * speed * 1.5f;
            if (progress <= 0f) {
                progress = 0f;
                finish();
                return;
            }
        } else {
            progress = Math.min(1f, progress + dt * speed);
        }
```

- **在干嘛**：每帧算出"距上一帧过了多少秒"（`dt`），然后拿 `progress`（0→1 的进度条）往前走。进场速度是 `1/0.24`，也就是 **0.24 秒走完**；退场时乘 1.5，**0.16 秒收完**。`progress` 到 1 就停住不再增长，到 0 就调 `finish()`。
- **为什么这么写**：`dt` 那个 `Math.min(..., 0.05f)` 是保险丝。手机切后台再回来，两帧之间可能差 2 秒，不封顶的话面板会"啪"一下瞬间弹满；封到 50 毫秒，最坏情况也就是动画稍慢一点，不会跳帧。用 `dt` 累加而不是用固定步长，是因为这样在 60Hz 和 120Hz 屏幕上**实际耗时都是 0.24 秒**，观感一致。
- **老实说一句**：面板完全展开后（`progress == 1`），`doFrame` 仍然每帧 `invalidate()` 并重新 `postFrameCallback`（`180-181` 行）。效果上没毛病，但严格说是白画——被问到时可以答："这是已知的可优化点，展开完把 `running` 置 `false` 就不再空转，`dismiss()` 那边本来就会在没跑的时候重新 `post`。"

### 1.7 finish：为什么点了难度不立刻跳页

#### `finish()`

```java

        }
```

- **在干嘛**：`finish()` 先把自己从父容器摘掉、停掉帧循环（`188-193` 行），然后才根据"当初点的是什么"发三种回调之一：联机对战、开始游戏、单纯关掉。点难度时**不是马上发信号**，而是先塞进 `pendingStart`，等 `progress` 缩回 0、面板真的收完了，才在 `finish()` 里通知 Activity 跳页。
- **为什么这么写**：如果点下去就 `startActivity`，新页面会立刻盖住旧页面，退场动画根本看不见，感觉像"点一下就闪屏"。打比方：这是电梯门——门关严了才启动，不会门还半开着就往上走。
- **老师可能问**：不 `removeView` 会怎样？—— 面板留在 `root_main` 里，下次 `openPanel` 时旧面板还在上面挡着，而且它的 `Choreographer` 回调会一直持有这个 View，属于泄漏。

`onDetachedFromWindow`（`211-215`）是最后一道保险：万一被别的方式摘掉，也把 `running` 置 `false` 并 `removeFrameCallback`。

### 1.8 computeLayout：先画好格子，再往格子里填东西

#### `computeLayout()`

```java
        float panelH = padV * 2f + headerH + contentH + footnoteH;

        float left = (w - panelW) / 2f;
        float top = (h - panelH) / 2f;
        panelRect.set(left, top, left + panelW, top + panelH);
        headerRect.set(left, top + padV, left + panelW, top + padV + headerH);
        closeRect.set(panelRect.right - 56f * density, top + padV,
                panelRect.right - 12f * density, top + padV + headerH);
```

- **在干嘛**：算出面板和每个热区的矩形，存进字段。宽度 `panelW = Math.min(w * 0.88f, 400f * density)`（`222` 行）——屏宽的 88%，但最多 400dp；高度是 上下留白 22dp×2 + 标题栏 52dp + 内容区 + 脚注 42dp，内容区再按 `mode` 分：`START` 两张 92dp 卡片、`DIFFICULTY` 三张 64dp、`SETTINGS` 两行 68dp（`226-236`）。最后 `top = (h - panelH) / 2f` 让面板垂直居中。
- **为什么这么写**：这是整个类最核心的一条纪律——**命中区域和绘制必须用同一套矩形**。所以布局只算一次，存在 `panelRect` / `itemRects` 这些字段里，`onDraw` 读它画、`onTouchEvent` 读它判。作者在类注释里专门写了这句（`MenuOverlayView.java:27-29`），因为"画在这里、点在那里"是手绘 UI 最常见、最难查的 bug。
- **老师可能问**：`onDraw` 里每次都重算布局，不浪费吗？—— 几个乘法和赋值，跟一帧的画图比可以忽略；换来的是转屏、分屏、折叠屏展开时不用写任何 `onSizeChanged` 逻辑，尺寸自动跟上。

条目格子是从标题栏底下往下"走"出来的（`251-272`）：一个 `cursor` 从 `top + padV + headerH` 开始，每放一张卡片就加"卡片高 + 间距"——`START` 是 `92+12`dp，`DIFFICULTY` 是 `74`dp，`SETTINGS` 是 `78`dp。放一张 `itemCount++` 一次，绘制和触摸循环都用这个数，而不是用数组长度 3——因为 `START` 只有 2 张有效卡片。

### 1.9 onDraw：一帧里到底画了几层

#### `onDraw()`

```java
        if (progress <= 0f) {
            return;
        }
        computeLayout();
        float ease = easeOutCubic(progress);

        // 背景压暗：面板打开时让下面的星空退到后面去
        fillPaint.setColor(0xFF000000);
        fillPaint.setAlpha((int) (255 * DIM_MAX * ease));
        canvas.drawRect(0f, 0f, getWidth(), getHeight(), fillPaint);
```

- **在干嘛**：`progress` 还是 0 就直接返回（面板等于没开，别浪费一帧）。然后重算布局，把线性的 `progress` 过一遍 `easeOutCubic`（`1-(1-p)³`）变成"先快后慢"的曲线，再按 `DIM_MAX = 0.62` 把整屏压暗到 62% 黑。
- **为什么这么写**：所有动画都吃同一个 `ease`：压暗的透明度、面板的缩放、面板的 alpha、文字的 alpha……所以它们**永远同步**，不会出现"背景黑了面板还没出来"。用 `easeOutCubic` 而不是线性，是因为线性运动看着像机器，缓出才像被"推"出来的。

接着是绘制顺序（`290-322`），共 8 层，后面的盖前面的：

1. 全屏压暗矩形；
2. `canvas.scale(0.92 + 0.08 * ease, ...)` 围绕面板中心缩放，画面板圆角矩形（22dp 圆角）；
3. 描一圈 1dp 边框；
4. 面板顶部一道 28dp 内缩、90/255 透明的青色高光——暗示"面板是被推出来的"；
5. `drawHeader`：标题（18dp 粗体）、左侧返回箭头、右上关闭叉；
6. 按 `mode` 分派到 `drawStartContent` / `drawDifficultyContent` / `drawSettingsContent`；
7. `drawFootnote`：底部一句提示；
8. `canvas.restore()` 把缩放了还回去。

值得单独说的是 `drawHeader` 里那两个"图标"：返回箭头是两条 `drawLine`（`356-357`），关闭叉也是两条 `drawLine`（`365-366`）。**整个面板没有一张图片资源是当图标用的**，除了卡片里的机体/敌机贴图。这也是它能随便换分辨率的原因之一。

还有一处细节：标题文字垂直居中不是简单加半个字号，而是 `headerRect.centerY() - (ascent + descent) / 2f`（`345` 行）——`ascent` 是负的、`descent` 是正的，两个一加才是文字真正的视觉中心。同样的算法在 `drawTextCentered`（`567-573`）里又用了一次，并且**画完把 `Paint.Align` 还原**，因为 `Paint` 是全类共用的一支笔，不还原会污染后面所有文字。

### 1.10 图标为什么不会被拉扁

#### `drawModeCard()`（图标部分）

```java
        if (icon != null) {
            float pad = 8f * density;
            RectF dst = new RectF(tile.left + pad, tile.top + pad, tile.right - pad, tile.bottom - pad);
            // 按比例内接，别把敌机拉变形
            float scale = Math.min(dst.width() / icon.getWidth(), dst.height() / icon.getHeight());
            float dw = icon.getWidth() * scale;
            float dh = icon.getHeight() * scale;
            RectF fitted = new RectF(tile.centerX() - dw / 2f, tile.centerY() - dh / 2f,
                    tile.centerX() + dw / 2f, tile.centerY() + dh / 2f);
            iconPaint.setAlpha(contentAlpha);
            canvas.drawBitmap(icon, null, fitted, iconPaint);
        }
```

- **在干嘛**：卡片左边有个 56dp 的圆角小方块，贴图先内缩 8dp，然后取"宽度比"和"高度比"里**小的那个**当作统一缩放比，最后以格子中心对称摆回去。
- **为什么这么写**：`drawBitmap(bitmap, null, dstRect, paint)` 会**无条件把你的图拉伸到 `dstRect`**，长宽比不一样就变形。取 `Math.min` 就是"能完整塞进去的最大等比尺寸"，专业叫法是 contain/内接。同一张 128×128 的图放进 56dp 的方格，出来还是正方形；换成 200×100 的图，就按宽度贴满、上下留白，绝不会压扁。
- **老师可能问**：这不就是 `ImageView` 的 `scaleType="centerInside"` 吗？—— 效果一样，但这里是 `Canvas` 手算的，不依赖布局系统，也不额外造一个 View。

### 1.11 onTouchEvent：点中了哪一块，拖拽怎么不算数

#### `onTouchEvent()`

```java
    public boolean onTouchEvent(MotionEvent event) {
        if (event.getActionMasked() != MotionEvent.ACTION_DOWN) {
            return true;
        }
        // 进场动画没走完先不响应，避免误触
        if (progress < 0.85f || dismissing) {
            return true;
        }
```

- **在干嘛**：**只处理"手指按下"这一瞬间**，其它动作（移动、抬起、取消）全部 `return true` 吃掉。进场动画没走完（`progress < 0.85`，约等于开始后 200 毫秒）或者正在退场时，什么都不做。
- **为什么这么写**：这就是这个面板"区分拖拽和点击"的全部手段——判定只发生在 `ACTION_DOWN`，所以"按住某张卡片 → 手指滑到别处 → 再抬起"不会触发第二次点击，也不会因为抬起位置不在卡片上而漏判。`return true` 表示"这个事件我消费了"，**不能返回 `false`**：返回 `false` 的话，`MOVE` 事件会漏给下面那层星空 View，背景可能会跟着响应，出现"点面板把背景也点了"的怪事。
- **老师可能问**：那用户按下后滑走，算点中了吗？—— 算。这个面板是"按下即选中"的风格，跟系统按钮的"抬起才确认"不同；好处是实现简单、行为确定，代价是没法"按下反悔"。
- **老师可能问**：`progress < 0.85` 为什么是 0.85？—— 进场 0.24 秒，0.85 大约是 0.2 秒；挡掉这一小段是为了防止用户连点两下"开始游戏"，第二下直接穿透到刚出现的卡片上。

命中判定的顺序是有讲究的（`589-609`）：

1. 先看右上角的关闭叉 `closeRect`；
2. 再看返回箭头 `backRect`——**只有 `DIFFICULTY` 状态才判**，因为其它状态压根不画这个箭头；
3. 再判断"是不是点在面板外面"：`!panelRect.contains(x, y)` 就 `dismiss()`，这就是脚注里那句"点空白处关闭"；
4. 最后遍历 `itemRects`，命中就交给 `handleItemTap(i)`。

#### `onTouchEvent()`（遍历条目）

```java
        for (int i = 0; i < itemCount; i++) {
            if (!itemRects[i].contains(x, y)) {
                continue;
            }
            handleItemTap(i);
            return true;
        }
        return true;
```

- **在干嘛**：循环到 `itemCount`（不是 `itemRects.length`，数组固定 3 个但可能只用 2 个），第一个命中的就处理并 `return`。
- **为什么这么写**：`itemRects` 的坐标来自 `computeLayout`，跟 `onDraw` 用的是同一份，所以**看到的位置就是能点的位置**，不存在 1 像素偏移。`return true` 放循环外，保证不论点没点中，事件都被吃掉。

### 1.14 为什么换个分辨率也不变形

把这一章所有跟尺寸有关的代码翻一遍，会发现只有**一处**真正读了屏幕大小：`computeLayout` 里的 `getWidth()` / `getHeight()`（`220-221`）。其它所有数字都是"dp 数值 × density"，而 `density` 在构造时取了一次就再没变过（`99`）。

具体四层保险：

1. **宽度按比例 + 上限**：`min(w * 0.88f, 400f * density)`（`222`）。手机上是屏宽 88%，平板上最多 400dp，不会被拉成一张铺满的大饼。
2. **固定 dp 的部件**：圆角 22dp、卡片 16dp、开关 56×30dp、标题 18dp。dp 和物理毫米挂钩，所以 1080×2400（density 2.75）上 56dp 是 154px，1440×3200（density 3.5）上是 196px——**像素数变了，占屏幕的比例没变**。
3. **图标等比内接**（`402-413`），前面 1.10 讲过。
4. **文字靠测量定位**：`measureText` 量宽度（`433`）、`FontMetrics` 算基线（`345`），不写死像素坐标。

打个比方：做衣服用厘米不用像素，同一个人换台相机拍，衣服还是合身的。

> 老师可能问：那极窄的屏幕（比如 320dp 宽）会不会挤爆？—— 描边和字号都是 dp 的，只会等比缩小；面板宽度是屏宽 88%，最窄也有 280dp，卡片里"图标 + 两行字"按当前字号放得下。真遇到极限尺寸，改动点也只有 `computeLayout` 一个方法。

### 1.15 这一章最容易问倒人的点

1. 如果被问"一会儿说 XML 一会儿说自绘，到底哪个"—— 就答：**静态骨架是 XML**（标题、按钮、昵称框），**动态浮层是自绘**（开场动画、二级面板）；两者在 `root_main` 这个 `FrameLayout` 里叠起来，后加的在上面。
2. 如果被问"面板展开完了为什么还在每帧重画"—— 就答：确实没停，`doFrame` 里到 1 之后还在 `post`；这是已知可优化点——`progress >= 1f && !dismissing` 时把 `running` 置 `false` 再返回即可，`dismiss()` 里本来就写了"没在跑就重新 post"（`149-153`），不会影响退场。
3. 如果被问"你怎么区分点击和拖拽"—— 就答：**只认 `ACTION_DOWN`**，按下瞬间判定，`MOVE`/`UP` 全部 `return true` 吃掉，所以拖走再松手不会触发第二次，也不会漏给背景。
4. 如果被问"开关存哪了、是不是立即生效"—— 就答：`SharedPreferences` 两个 key，`apply()` 异步写；正在进行的对局不会瞬时静音，`GameActivity` 开局时读取并交给 `SoundManager`，因为面板只在对局外出现，体感上就是立即。
5. 如果被问"为什么不用 Dialog 或 Fragment"—— 就答：样式和动画曲线要完全可控、要跟星空透叠、要自己决定"点空白关闭"的行为；代价是返回键和触摸都得自己接管（就是 `registerBackHandling` 和 `onTouchEvent` 那两段）。

## 二、自绘视觉组件：星空背景、渐变文字、皮肤预览

> 一句话：这一章拆三个"从零画出来"的 View——星空背景、渐变标题、皮肤预览，把 `onMeasure` / `onSizeChanged` / `onDraw` 这套自定义 View 的固定套路，讲成"什么时候被叫、被叫到时该干什么"。

三个文件一共 **459 行**（`StarfieldView` 258 行、`GradientTextView` 58 行、`SkinPreviewView` 143 行），是全项目最"图形学"的部分。界面层没有一张背景图、一张标题图：星空、星云、暗角、渐变大字、皮肤光晕全是 `Paint` 一笔一笔刷出来的（游戏页那套滚动背景才用贴图，属于 `render/` 的事）。主菜单的 `activity_main.xml:23` 只给它留了一个 `match_parent` 的坑位，皮肤页更直接——`new StarfieldView(this)` 塞进去（`SkinActivity.java:101`）。下面每节先看代码再看解释，代码逐字抄自源文件，行号真实，可以直接跳过去对照。

### 2.1 三件套：量体、开箱、上色

| 回调 | 谁触发 | 叫几次 | 该干什么 |
|------|--------|--------|----------|
| `onMeasure` | 父容器问"你要多大" | 尺寸可能变时，很多次 | **量体**：报告宽高 |
| `onSizeChanged` | 尺寸**真的**变了 | 至少 1 次，转屏再来 | **开箱**：建和尺寸绑定的对象 |
| `onDraw` | 需要上屏时 | 每帧一次，约 60 次/秒 | **上色**：把状态画出来 |

顺序固定：`onMeasure` → `layout` → `onSizeChanged` → `onDraw`；而 `invalidate()` 只重跑 `onDraw`，**不会**重新测量、重新布局。三个类都没重写 `onMeasure`，因为父容器给的是 `match_parent` 或固定 `190dp`，默认实现够用；默认实现唯一不靠谱的是 `wrap_content`（普通 View 会退化成 0），所以**只有想做 `wrap_content` 的自定义 View 才必须重写**。`GradientTextView` 更不能乱重写：它继承 `TextView`，宽高要按文字排版的真实结果算。

#### `onSizeChanged(int, int, int, int)`
`StarfieldView.java:159` 这里只做一件事——尺寸一变就把依赖像素的东西重新建：
```java
    @Override
    protected void onSizeChanged(int w, int h, int oldw, int oldh) {
        super.onSizeChanged(w, h, oldw, oldh);
        if (w <= 0 || h <= 0) {
            return;
        }
```

### 2.2 星空为什么是"画"出来的，不是贴一张图
作者把理由写在类头上，这段注释本身就是验收答案（`StarfieldView.java:15`）：

```java
/**
 * 主菜单背景：深空渐变 + 两团星云 + 三层视差星点 + 暗角。
 * <p>
 * 为什么不用一张静态背景图（{@code bg.jpg} 那套）：
 * <ul>
 *   <li>静态图只能拉伸，荣耀这类窄长屏上会被压扁；这里全用矢量/程序化绘制，任何比例都自然；</li>
 *   <li>一张 1080x2400 的背景图约 1~2 MB，这里代码不到 10 KB；</li>
 *   <li>游戏页背景要跟着滚动，菜单页则应该静止——分开实现互不干扰。</li>
 * </ul>
 * 帧循环用 {@link Choreographer} 而不是 Timer/Thread：它把回调对齐到屏幕的 VSYNC，
 * 只在真正要刷新时触发，比固定间隔的 Timer 更省电也更不容易掉帧。
 */
```

补一个注释里没写的数字：1080×2400 的图**文件**才 1~2 MB，解码进内存要 `1080 × 2400 × 4 字节 ≈ 10.4 MB`（ARGB_8888，每像素 4 字节）；这段代码编译出来不到 10 KB，还随便什么分辨率。
- **在干嘛**：用数学替代素材——星云位置写成 `w * 0.26f` 这样的百分比，屏幕变宽变长它自己跟着走。
- **为什么这么写**：图只能"拉伸"，代码可以"重新布局"；游戏页背景要滚动、菜单页要静止，代码方案想停就停。

### 2.3 星星存在哪：三层数组，构造时一次分配完
#### 字段与构造函数
先看数量：`StarfieldView.java:29` 定了三层共 `44 + 26 + 12 = 82` 颗，半径 `0.65 / 1.05 / 1.70 dp`、亮度 `0.30 / 0.55 / 0.88`、速度 `4 / 11 / 22 dp/s`——越"近"越大、越亮、越快。三个坐标数组在构造函数里补齐第二维（`StarfieldView.java:72`；字段声明是 `new float[LAYER_COUNT][]`，第一维先建好、第二维留空）：

### 2.4 四个 Shader：一次建好，之后只换不建
#### `onSizeChanged(int, int, int, int)`
全类唯一会创建 `Shader` 的地方（`StarfieldView.java:166`，接在 2.1 那个 `w <= 0` 判断后面）：
```java

                0xFF0C1119, 0xFF05080D, Shader.TileMode.CLAMP);

        // 星云：中心亮、边缘全透明，用 CLAMP 铺满即可
        nebulaShaderA = new RadialGradient(w * 0.26f, h * 0.18f, w * 0.82f,
                new int[]{0x2A3EC8FF, 0x000E1218}, new float[]{0f, 1f}, Shader.TileMode.CLAMP);
        nebulaShaderB = new RadialGradient(w * 0.80f, h * 0.70f, w * 0.92f,
                new int[]{0x1F2E6E9E, 0x000E1218}, new float[]{0f, 1f}, Shader.TileMode.CLAMP);

        // 暗角：中心透明、四周压暗，让视线落在中间内容上
        vignetteShader = new RadialGradient(w * 0.5f, h * 0.44f, Math.max(w, h) * 0.78f,
                new int[]{0x00000000, 0x00000000, 0x59000000},
                new float[]{0f, 0.55f, 1f}, Shader.TileMode.CLAMP);
```
- **`LinearGradient(0, 0, 0, h, ...)`**：起点 `(0,0)`、终点 `(0,h)`，x 相同、y 差一屏高 → 只能"上到下"，颜色从近黑的深蓝灰 `0xFF0C1119` 到 `0xFF05080D`。
- **`RadialGradient`**：一个圆形"灯泡"，中心亮、往外淡。星云 A 在左上 `(0.26w, 0.18h)`，半径 `0.82w` 比屏幕还宽，只看到中间一块；星云 B 在右下，半径 `0.92w`。
- **8 位颜色**：`0x2A3EC8FF` = alpha `0x2A`(42) + RGB `3EC8FF`（青蓝），几乎透明，只加一点冷光。全透明的结束色写 `0x000E1218` 而不是纯黑，是因为 RGB 特意取了底色——渐隐到纯黑时某些设备会透出一圈灰边。
- **`TileMode.CLAMP`**：超出范围沿用端点色，不平铺、不镜像，只是兜底。
- **暗角三个停靠点** `{0f, 0.55f, 1f}`：中心到 55% 半径完全透明（不挡内容），往外才压暗，最边上 alpha `0x59 = 89/255 ≈ 35%`。

- **在干嘛**：把"颜色怎么铺"预先算成 4 个 `Shader`。
- **为什么这么写**：`Shader` 坐标是像素、和 `w/h` 绑死；尺寸不变就永不重建，`onDraw` 里只剩 `setShader()` 这个近乎零成本的动作。
- **老师可能问**：`Shader` 和 `Paint` 什么关系？——`Paint` 是刷子，`Shader` 是刷子上的花纹；一把刷子换 4 次花纹，不用买 4 把刷子。

### 2.5 星星的出生：固定种子，只出生一次
#### `onSizeChanged(int, int, int, int)`
`StarfieldView.java:180`，注意末尾那个 `start()`：

### 2.6 帧循环：每帧只做三件事
#### `doFrame(long)`
`StarfieldView.java:83`，省略的第 96~98 行是下面要讲的三件事：
```java
    @Override
    public void doFrame(long frameTimeNanos) {
        if (!running) {
            return;
        }
        if (lastFrameNanos == 0L) {
            lastFrameNanos = frameTimeNanos;
        }
        // dt 封顶 50ms：从后台切回来时不会因为时间跳跃让星点瞬移一大段
        float dt = Math.min((frameTimeNanos - lastFrameNanos) / 1_000_000_000f, 0.05f);
        lastFrameNanos = frameTimeNanos;
        timeSec += dt;
        // ...（省略）
```
- **`Choreographer`**：屏幕的"发令枪"。屏幕每次刷新（60Hz = 16.6ms）叫一声，回调挂上去就跟着节奏跑；`ValueAnimator` 内部用的也是它。
- **`lastFrameNanos == 0L`**：第一帧没有"上一帧"，先记一笔就返回，避免算出巨大或负的 `dt`。
- **`Math.min(..., 0.05f)`**：`dt` 最多 50ms。切后台几分钟再回来，两次时间差 180 秒，不封顶星星会瞬移、闪烁会跳一大步；50ms 约 3 帧，够平滑。`timeSec` 是给闪烁和浮动用的全局时钟。
- **省略的三行**：`stepStars(dt)` 改数据 → `invalidate()` 说"我脏了，下帧重画" → `postFrameCallback(this)` 把自己排进下一帧。缺一不可：不 `invalidate` 画面不动，不重新 post 只动一帧。

**`invalidate()` 和 `postInvalidateOnAnimation()` 的区别**，本章最容易被追问：

| | `invalidate()` | `postInvalidateOnAnimation()` |
|---|---|---|
| 线程 | **只能 UI 线程** | 任意线程 |
| 何时重画 | 下一个 VSYNC | 下一个 VSYNC |
| 额外开销 | 无 | 一次跨线程投递 |

结论：**两者最终都是"下一帧画"，区别只在能不能跨线程**。`doFrame` 本来就跑在 UI 线程（`Choreographer.getInstance()` 拿的是当前线程实例），所以直接 `invalidate()` 最省；只有从下载线程之类的地方触发重绘，才需要 `postInvalidateOnAnimation()`。
- **在干嘛**：算出"上一帧到现在过了多久"，交给动画逻辑。
- **为什么这么写**：所有运动按时间积分（`速度 × dt`），不是"每帧加固定值"，这样 60Hz 和 120Hz 手机速度一致。
- **老师可能问**：为什么不用 `Timer`？——`Timer` 自己定 16ms 和屏幕不对齐，容易一帧画两次、一帧没画；`Choreographer` 跟着 VSYNC，不掉帧也不空转。

### 2.7 出屏的星星"传送"回顶部，一个都不 new
#### `stepStars(float)`
`StarfieldView.java:101`，省略的是两个循环和方法收尾的 `}`：
```java
    private void stepStars(float dt) {
        int height = getHeight();
        if (height <= 0) {
            return;
        }
        for (int layer = 0; layer < LAYER_COUNT; layer++) {
            float speed = STAR_SPEED_DP[layer] * density * dt;
            for (int i = 0; i < STAR_COUNT[layer]; i++) {
                starY[layer][i] += speed;
                if (starY[layer][i] > height + 8) {
                    starY[layer][i] = -8;
                    starX[layer][i] = random.nextFloat() * getWidth();
                }
                // ...（省略）
```
- 星星永远**向下**走（`starY += speed`），因为镜头在往上飞；走出屏幕（`> height + 8`）后**不删、不新建**：把 `y` 拨回 `-8`（屏幕上方外面一点）、`x` 重新随机，它从底部消失、从顶部出现，像传送带。
- `+8` / `-8` 是防"边缘闪现"：必须等它**完全**离开再回收，否则会在最底下露一半又突然消失。
- `speed = dp × density × dt`：先转像素、再算这一帧走多远。三层 4/11/22 dp/s，以 3 倍密度屏、2400px 高为例：最慢 `4×3 = 12 px/s`，走完一屏 200 秒；最快 `22×3 = 66 px/s`，36 秒。慢的远、快的近，眼睛一看就有纵深——这就是"视差"。

- **在干嘛**：每帧把 82 颗星往下推一点，出界的从顶上重新进场。
- **为什么这么写**：坐标复用，数组长度恒定，永远不触发 GC。
- **老师可能问**：为什么不真的删掉再 add？——每秒 60 帧，每帧删 1~2 颗再加 1~2 颗，一天几百万次对象创建，GC 被打醒画面就卡一下。

### 2.9 82 次 `drawCircle`，还有一个小坑会让人翻车
#### `drawStars(Canvas)`
`StarfieldView.java:235`：
```java

        for (int layer = 0; layer < LAYER_COUNT; layer++) {
            float radius = STAR_RADIUS_DP[layer] * density;
            int baseAlpha = (int) (STAR_ALPHA[layer] * 255);
            for (int i = 0; i < STAR_COUNT[layer]; i++) {
                // 闪烁：每颗星自己的相位，避免整片一起呼吸显得假

```
- **半径、基础透明度提到内层循环外**：44 颗星共用一个 `radius`，不必每颗都乘 `density`。
- **`twinkle = 0.72 + 0.28 * sin(...)`**：`sin` 在 `[-1,1]`，亮度在 `0.44 ~ 1.00` 之间呼吸；乘基础 alpha，最亮是层亮度、最暗是 44%。角速度 1.1 rad/s，一个完整明暗周期约 5.7 秒。
- **`starPhase[layer][i]`**：每颗星相位不同，82 颗各闪各的；相位一样就会整片同时亮暗，像坏掉的灯带。

### 2.10 开关与生命周期：别在后台空转
#### `start()` / `stop()`
`StarfieldView.java:118`：
```java
    private void start() {
        if (running || !starsReady) {
            return;
        }
        running = true;
        lastFrameNanos = 0L;
        Choreographer.getInstance().postFrameCallback(this);
    }

    private void stop() {
        running = false;
        Choreographer.getInstance().removeFrameCallback(this);
    }
```
- **`start()` 两个门槛**：已经在跑就别重复挂；星星还没初始化（`!starsReady`）就等 `onSizeChanged` 里那次调用。`lastFrameNanos = 0L` 是重新计时，下次第一帧不会拿"上次退出时的纳秒"去减。
- **`stop()` 两件事都要做**：`running = false` 只是让下一帧"来了也不干活"，`removeFrameCallback` 才是真正取消排队；只改 `running`，回调会一直挂着空跑。

四个生命周期回调各管一段：`onAttachedToWindow`（`StarfieldView.java:143`）可见就 `start()`；`onWindowVisibilityChanged`（`StarfieldView.java:133`）切后台、被盖住就 `stop()`；`onDetachedFromWindow`（`StarfieldView.java:151`）一定 `stop()`；`onSizeChanged` 初始化完星星后 `start()`（`StarfieldView.java:189`）。

为什么 detach 必须 `stop()`：`Choreographer` 的回调队列**持有这个 View 的引用**，页面都退出了回调还在队列里，View 就回收不掉——最典型的内存泄漏 + 后台耗电。算笔账：60fps 下每秒 `onDraw` 60 次、`drawCircle` `82 × 60 = 4920` 次，后台还跑就是纯烧电。
- **在干嘛**：给帧循环装开关，跟着页面可见性走。
- **为什么这么写**：`Choreographer` 是全局单例，你不主动移除，它就一直叫你。

```java
            shader = new LinearGradient(0f, 0f, 0f, Math.max(1, shaderHeight),
                    topColor, bottomColor, Shader.TileMode.CLAMP);
            getPaint().setShader(shader);
        }
        super.onDraw(canvas);
    }
```
- **为什么继承 `AppCompatTextView` 而不是 `View`**：`TextView` 已经处理了换行、对齐、字距、`ellipsize`、`padding`、深色模式……从 `View` 写起等于重写半个 `TextView`，这里只加一件事：渐变。
- **`getPaint()` 是那支"画字的笔"**：`TextView` 内部就用这支 `TextPaint` 把字画到 `Canvas` 上。挂上 `Shader`，字形的每个像素按渐变取色——**字形不变，只是换了"取色规则"**。
- **坐标 `(0,0)-(0,height)`**：`Shader` 用控件本地坐标，纵向从 0 到控件高，就是"顶部纯白、底部淡蓝"；文字几行、多大、怎么对齐都不用管，渐变永远贴控件高度。
- **`Math.max(1, shaderHeight)`**：防高度为 0 时构造出"零长度渐变"（起点终点重合，退化成一个点）。`CLAMP` 让超出 `[0,h]` 的部分沿用端点色，不镜像重复。
- **懒加载双保险**：`onSizeChanged` 置空、`onDraw` 再查一次 `null` 或高度不一致。真正干活的是"第一次画之前不知道高度，只能等 `onDraw`"；重建只发生在尺寸变化那一两次，之后每帧只做**两次比较**。

颜色写死在构造函数（`GradientTextView.java:35`）：加自定义属性要改 `attrs.xml`、写 `obtainStyledAttributes` + `TypedArray` + `recycle`，"整个项目只有标题用这个效果，为一个控件加一套 declare-styleable 不划算"。上白 `0xFFFFFFFF` 到下淡蓝 `0xFF78C6F0`，就是金属字上亮下暗的感觉。`IntroOverlayView.java:192` 的注释说它照抄了这组"上白下青"，为了让动画交接时看不出接缝——这套渐变已经是项目的视觉规范。
- **在干嘛**：第一次绘制前（或尺寸变化后）建一个纵向渐变，挂到画字的 `Paint` 上，再照常 `super.onDraw`。
- **为什么这么写**：排版交给父类，只劫持"上色"，改动面最小、行为最稳。
- **老师可能问**：为什么不用一张渐变标题图？——换字号、多语言、深色模式都要重做图；代码方案任意尺寸都清晰，放大不发虚。

### 2.14 等比缩放：一个 `min` 解决"不变形"
#### `onDraw(Canvas)`
`SkinPreviewView.java:104` 这几行是全类最该会讲的：
```java
        if (bitmap == null || bitmap.isRecycled()) {
            return;
        }

        float centerX = w / 2f;
        float centerY = h * 0.5f;
        float target = h * 0.62f;
        float scale = Math.min(target / bitmap.getHeight(), (w * 0.55f) / bitmap.getWidth());
```
- **两个限制**：高度最多占控件 `62%`，宽度最多占 `55%`。皮肤页给这个 View 的高度是 `190dp`（`SkinActivity.java:71`），图大概 118dp 高。
- **取 `min`**：谁的放大倍数小听谁的，两边都不越界（叫 `contain`，相当于 `ImageView` 的 `centerInside`）；取 `max` 就是 `cover`：一边撑满、另一边超出被裁。
- **为什么不变形**：后面 `canvas.scale(scale*pop, scale*pop)` 横竖用**同一个** `scale`，只改大小、不改长宽比。

具体例子：贴图 `200×160`、控件 `1080×570`（3 倍密度屏上的 190dp）。高比例 `(570×0.62)/160 = 353/160 ≈ 2.2`，宽比例 `(1080×0.55)/200 = 594/200 ≈ 2.97`，取 2.2 → 画出来约 `441×353`，高度用掉 62%、左右留白，图还是 5:4。

配套细节：`Paint.FILTER_BITMAP_FLAG`（`SkinPreviewView.java:24`）让 GPU 做双线性过滤，缩放不发锯齿，不设就是最近邻、边缘一格一格；`isRecycled()` 检查是因为 `Assets` 的图共享，万一被回收，`drawBitmap` 会抛 "trying to use a recycled bitmap" 崩掉；不用 `createScaledBitmap` 先缩好，是因为每换一次皮肤就多一张约 `441×353×4 ≈ 623 KB` 的位图，换 7 次就是 4 MB 垃圾，而 `canvas.scale` 是纯绘制变换，零分配。
- **在干嘛**：算"这张图在这个控件里最大能放多大"，且不变形。
- **为什么这么写**：7 款皮肤贴图尺寸不完全一样，写死尺寸换一款就歪，公式化才通用。

### 2.15 动效三件套：回弹、浮动、微倾
#### `onDraw(Canvas)`
`SkinPreviewView.java:113`：
```java
        // 换皮肤后的回弹：0.3 秒内从 1.18 收回到 1.0
        float pop = 1f;
        if (popStartNanos > 0L) {
            float t = (System.nanoTime() - popStartNanos) / 1e9f;
            if (t < 0.3f) {
                pop = 1f + 0.18f * (1f - t / 0.3f) * (1f - t / 0.3f);
            } else {
                popStartNanos = 0L;
            }
        }

        float bob = (float) Math.sin(timeSec * 2.0) * 5f * density;
        float tilt = (float) Math.sin(timeSec * 1.4) * 2.5f;
```

**回弹 `pop`**：换皮肤瞬间 `1.18`（大 18%），0.3 秒回到 `1.0`。`(1 - t/0.3)²` 是二次缓出：`t=0.15` 时 `(0.5)² = 0.25`，已经收到 `1.045`——前面掉得快、最后慢慢贴住，像橡皮筋，比线性自然。`t >= 0.3` 后把 `popStartNanos` 归 0，不再计算。

**浮动 `bob`**：`sin(t × 2)`，周期 `2π/2 ≈ 3.14 秒`，幅度 `±5dp`（3 倍屏上 ±15px）。**微倾 `tilt`**：`sin(t × 1.4)`，周期约 `4.49 秒`，幅度 `±2.5°`（`canvas.rotate` 收的就是度）。两个频率不成整数比，所以不会"每 3 秒摆同一个姿势"，看起来更自然。

这三个量都是每帧现算的三角函数，不需要 GIF / Lottie 那种几百 KB 的素材。类注释（`SkinPreviewView.java:15`）说得很直白：静态图也能看，但"活"感就靠这几行三角。
- **在干嘛**：算这一次绘制用多大的缩放、往上浮多少、歪多少度。
- **为什么这么写**：两个永不停息的循环（浮、倾）用 `sin` 自己积分；一次性的回弹用"起点 + 已过时间"现算。

### 2.16 收尾绘制：影子先画，飞机后画；变换必须还回去
#### `onDraw(Canvas)`
`SkinPreviewView.java:127` 先画一个会呼吸的影子：
```java

        float shadowScale = 1f - bob / (60f * density);
        shadowPaint.setColor(0x66000000);
        canvas.drawOval(centerX - bitmap.getWidth() * scale * 0.42f * shadowScale,
                centerY + bitmap.getHeight() * scale * 0.52f - 2f * density,
                centerX + bitmap.getWidth() * scale * 0.42f * shadowScale,
                centerY + bitmap.getHeight() * scale * 0.52f + 8f * density,
                shadowPaint);
```

`SkinPreviewView.java:136` 再变换画布、画飞机、还原：

```java
        canvas.save();
        canvas.translate(centerX, centerY + bob);
        canvas.rotate(tilt);
        canvas.scale(scale * pop, scale * pop);
        canvas.drawBitmap(bitmap, -bitmap.getWidth() / 2f, -bitmap.getHeight() / 2f, bitmapPaint);
        canvas.restore();
```
- **影子先画、飞机后画**：飞机盖住影子，才有"停在影子上"的感觉；反过来影子就糊在飞机脸上。
- **影子不跟着旋转**：影子画在 `save()` **之前**，用控件原始坐标，所以飞机歪多少度影子都水平（地面是平的）。
- **`shadowScale = 1 - bob/(60dp)`**：`bob` 最高 `+5dp`，影子缩到 `1 - 5/60 ≈ 0.917`；最低时放大到 `1.083`。浮得越高影子越小——假装有高度。`drawOval(左, 上, 右, 下)` 上下只差 `10dp`（`-2dp` 到 `+8dp`），是个很扁的椭圆。
- **`save()` / `restore()` 必须配对**：`Canvas` 的变换会一直累积，不 `restore` 后面所有绘制都歪、都被缩放。`save` 是"记住现在的位置"，`restore` 是"退回上一次记住的位置"。
- **顺序 `translate → rotate → scale`**：先挪到中心、再**绕中心**转、最后以中心为原点缩放。先 `scale` 再 `translate` 的话，位移量也会被放大 `scale` 倍，位置跑偏。
- **`-bw/2, -bh/2`**：`drawBitmap` 的坐标是左上角，要居中就得往左上挪半个宽高；这里用 `canvas` 自带的变换栈，依然没有 `new`。

- **在干嘛**：先画一个会呼吸的影子，再在变换后的画布上把皮肤图居中画出来。
- **为什么这么写**：影子负责"落地感"，变换负责"浮动 + 倾斜 + 回弹"，三者在同一个 `onDraw` 里叠加，却只有一次 `drawBitmap`。
- **老师可能问**：忘了 `restore()` 会怎样？——这次它后面没有别的绘制，看起来没事；但 `Canvas` 会反复使用，状态会带到下一帧，早晚出鬼。

### 2.17 这一章最容易问倒人的点
1. 如果被问到"`onDraw` 里为什么不能 `new` 对象"，就答：60fps 下它每秒被调 60 次，一次 `new Paint` 就是每秒 60 个垃圾，GC 一扫画面就顿一下；所以 `Paint`、`Shader`、星星数组全提前建好，`onDraw` 只读不建。
2. 如果被问到"`invalidate()` 和 `postInvalidateOnAnimation()` 有什么不一样"，就答：两者最终都是"下一个 VSYNC 重绘"，区别只在 `invalidate()` 只能 UI 线程调、`postInvalidateOnAnimation()` 任意线程可调但多一次投递；`doFrame` 本就在 UI 线程，所以用更便宜的 `invalidate()`。
3. 如果被问到"星星为什么不会越画越多"，就答：出屏的星不被删也不新建，只是把 `y` 拨回 `-8`、`x` 重新随机（`StarfieldView.java:110`），数组长度永远 82，零分配。
4. 如果被问到"渐变文字为什么不用图片"，就答：`Shader` 坐标是 `(0,0)-(0,height)`，控件多高渐变就多高，换字号、多语言、深色模式都不用重做素材，放大还不发虚（`GradientTextView.java:52`）。
5. 如果被问到"皮肤图怎么保证不变形"，就答：`scale` 取"高度比例"和"宽度比例"里较小的那个（`SkinPreviewView.java:111`），横竖乘同一个 `scale`；用 `canvas.scale` 而不是 `createScaledBitmap`，不产生新位图。

## 三、开场动画 `IntroOverlayView`

> 一句话：这 912 行里**没有一个 `Animation`、也没有一个 `Animator`**，它只干一件事——每帧问一句"离动画开始过了多少毫秒"，再把这个数字代进十几个公式，把整幅画面从头重画一遍。

### 3.1 这 800 行在演什么（先看全景）

先打个底：912 行、42 个方法、10 个 `Paint`、28 个 `T_` 开头的常量。骨架其实土得掉渣，三句话：

1. 用一个 `long` 记下"动画开始的那一纳秒"；
2. 每来一帧，算出"从开始到现在过了多少毫秒"，记作 `t`；
3. `onDraw` 拿到 `t`，把黑场、飞机、英文名、中文标题按 `t` 的位置各画一遍。

**它不是在"播放"动画，是在"按时刻重画"画面**——像老式电影胶片，不是让画面自己动，而是每 16.7 毫秒换一张画好的片子。

这个开场分成**两幕**，而且两幕用的是**两根不同的时间轴**（这是全文最容易看晕的地方，`IntroOverlayView.java:363` 的 `mainMs()` 专干拼接这活）：

```
 0ms                    3020ms                3820ms
 ├────── 第一幕：加载幕 ──────┼── 第二幕：衔接幕 ──┤  结束
   黑屏 + 射线扫出飞机和英文名   起飞 → 翻转 → 交接给真标题
   用 timeMs() 这根轴          用 mainMs() 这根轴 = 1720 + (t - 3020)
```

### 3.2 时间轴怎么算

时间轴就是一根"毫秒进度条"，每个动画节拍都是这根条上的一个区间 `[开始, 结束]`。算某段走到百分之几，永远是同一个模板：**进度 = (现在 − 开始) / (结束 − 开始)，再 `clamp01` 夹到 0~1。**

#### `doFrame(long nanos)`
```java
    public void doFrame(long nanos) {
        if (!running) {
            return;
        }
        frameNanos = nanos;
        if (startNanos == 0L) {
            startNanos = nanos;
        }
        if (freezeMs < 0f && mainMs() >= T_END) {
            finish();
            return;
        }
        invalidate();
        Choreographer.getInstance().postFrameCallback(this);
    }
```

- **在干嘛**：节拍器，每 16.7ms 被系统叫一次。存时间戳，第一次进来时把 `startNanos` 定成零点（所以**动画从第一帧才开始计时**，不是 `new` 出来就计时）；然后请求重绘，再把自己挂到下一帧——`postFrameCallback(this)` 就是"下个 vsync 记得还叫我"，一个自我续期的循环。
- **为什么这么写**：① `nanos` 是 vsync 时间戳，跟刷新同步，60Hz 就是 16.7ms、120Hz 自动变 8.3ms，不用自己 `Thread.sleep(16)`；② 它单调递增，用户改系统时间也不会让动画倒着飞；③ 收尾判断放在这里而不是 `onDraw`——`onDraw` 可能因别的原因被调用，`doFrame` 一定是每帧一次。
- **老师可能问**：`startNanos = 0L` 干嘛的？——哨兵。"还没开始"和"第 0 毫秒"共用 0，所以第一次进来必须用 `nanos` 覆盖掉。

#### `timeMs()`
```java
    private float timeMs() {
        if (freezeMs >= 0f) {
            return freezeMs;
        }
        if (startNanos == 0L || frameNanos == 0L) {
            return 0f;
        }
        return (frameNanos - startNanos) / 1_000_000f;
    }
```

- **在干嘛**：把"两个纳秒相减"换成人话。`/ 1_000_000f` 的 `f` 不能少——整数除法会把 3820.7ms 砍成 3820，几十帧下来就是肉眼可见的抖。
- **为什么这么写**：`freezeMs >= 0` 是调试开关（`setFreezeTimeMs`，`IntroOverlayView.java:297`）。MainActivity 用 `intent` 里的 `intro_at` 传值进来，就能把画面**钉死在 2230ms** 那一帧截图检查排版。这也是自绘的隐藏好处：系统 `Animator` 想冻在某一帧很费劲。
- **老师可能问**：为什么不存"上一帧时间"再累加？——累加会漂，见 3.3 最后一段。

#### `mainMs()`
```java
    private float mainMs() {
        float t = timeMs();
        if (t < T_PRELUDE) {
            return -1f;
        }
        return T_TRAVEL + (t - T_PRELUDE);
    }
```

- **在干嘛**：把第一幕那 3020ms 整段"跳过去"，让第二幕的 0 点落在 `T_TRAVEL`（1720）。`t=3020` 时返回 1720，`t=3820` 时返回 2520（正好 `T_END`）。所以**总时长 = 3020 + (2520 − 1720) = 3820ms**。
- **为什么这么写**：① 第二幕那套常量（1720/2120/2230/2360…）是第一版单时间轴写的，用一个偏移量把旧节拍原封不动搬过来，**常量表不用改、坐标不用重算**；② 返回 `-1` 当"还没轮到我"的信号，`onDraw` 里一句 `if (main >= 0f)` 就把两幕隔开，不用额外状态布尔值。
- **老师可能问**：为什么不做成两个类？——两幕要共用同一张飞机图、同一套落点坐标、同一个收尾动作，拆开反而得互传状态。

### 3.3 为什么不用 `Animation` / `Animator`

这是老师最可能盯住问的一条："Android 明明有动画框架，你为什么自己画？"答这四条，**按重要性排**：

1. **View 动画改不了"真属性"，交接会闪。** `Animation`（补间）只改绘制时的矩阵和透明度，控件自己的 `alpha` 还是 0；动画一结束"啪"地跳到终态，就是常见的"结束闪一下"。本项目最后要跟布局里真实的 `TextView` 无缝换人，必须**每帧自己写** `titleView.setAlpha(...)`（`syncMenuText`，`IntroOverlayView.java:835`），补间做不到。
2. **这里是"十几个参数共用一根时间轴"，不是"一个属性一条动画"。** 同一帧里 `reveal`、`merge`、`bg`、`wordFade`、`travel`、`flip`、`cross` 全要用；写成 `AnimatorSet` 就是二十来个 `ValueAnimator` 互相 `with/before/after`，改一个节拍要动好几处，还没法保证它们在同一帧对齐。现在改节拍只改常量表里一个数。
3. **可控、可冻结、可跳过。** `freezeMs` 钉住任意毫秒截图；`skip()` 点击就 140ms 淡出收工（`IntroOverlayView.java:862`）。系统动画想"停在 2230ms"得自己造 `setCurrentPlayTime`，还不一定准。
4. **不依赖布局层级。** 动画里的标题和布局里的真标题必须**像素级**重合，所以落点是用 `getLocationInWindow` 做差算出来的绝对坐标（`resolveTargets`，`IntroOverlayView.java:389`）；自己 `draw` 就没有"中间夹几层父容器、坐标系被平移过"这笔烂账。

**`Choreographer` 的节奏**：它就是"下一次屏幕刷新"的预约台。`postFrameCallback` 之后，系统在**画这一帧之前**回调 `doFrame`，所以你改的状态这一帧就能画出来，不会晚一帧。**`postInvalidateOnAnimation` 呢？** 它走的是同一个 vsync；本文件在 `doFrame` 里直接 `invalidate()`——人已经站在 UI 线程的帧回调里了，再 `post` 一次是绕远路，`postInvalidateOnAnimation` 是给**非 UI 线程**用的。被追问就这么说："效果一样，`invalidate()` 更直接。"

**掉帧会不会越走越慢？** 不会。每帧画什么都是 `t` 的**解析函数**，没有"在上一帧基础上加 3 像素"这种累加量。掉 3 帧只是少画 3 张，第 4 帧的位置还是按真实时间算——**画面会一顿，但不会越走越慢、也不会整体偏掉**。

### 3.4 每帧怎么把"进度"变成"透明度/位移"

进度 `p` 从 0 走到 1 中间怎么走，全靠文件末尾这四个静态小函数（`IntroOverlayView.java:896-911`）：

#### `clamp01` 与 `easeOutCubic`
```java
    private static float clamp01(float v) {
        return v < 0f ? 0f : (v > 1f ? 1f : v);
    }

    private static float easeOutCubic(float p) {
        float q = 1f - p;
        return 1f - q * q * q;
    }
```

#### `easeInOutCubic` 与 `smoothstep`
```java
    private static float easeInOutCubic(float p) {
        return p < 0.5f ? 4f * p * p * p : 1f - (float) Math.pow(-2f * p + 2f, 3) / 2f;
    }

    private static float smoothstep(float p) {
        return p * p * (3f - 2f * p);
    }
```

- **在干嘛**：`clamp01` 是"别越界"的安全带（时间没到就是 0、过了就是 1，绝不能是 −0.3 或 1.7）。另外三个把匀速的进度条捏出手感：`easeOutCubic` **一开始最快、最后慢慢停**，像被推一把自己滑到位（淡出、光晕、星点）；`easeInOutCubic` **两头慢中间快**，像电梯起步到站（扫描揭示、黑场、高光）；`smoothstep` 也是两头慢，但曲线更"软"，专给 ⑦ 的位移用——位移用 cubic 会"冲一下"，smoothstep 最像被人"端"过去。
- **为什么这么写**：全是不带状态、不查表的纯算式，几十纳秒算完，比查贝塞尔曲线表快，也省得引 `TimeInterpolator` 对象；而且**任何线程、任何帧算出来都一样**，天然可复现，截图对比才有意义。
- **老师可能问**：`smoothstep` 和 `easeInOutCubic` 差在哪？——速度峰值，前者峰值是 1.5 倍匀速、后者是 3 倍；位移用前者不冲。

`drawBurst`（`IntroOverlayView.java:701`）是"一个 `p` 喂三个参数"的最小样板：`p` 喂 `easeOutCubic` 得到飞多远、喂 `(1-p)*(1-p)` 得到还剩多亮、喂 `1 - p*0.55f` 得到缩了多少——**只有一个 `p` 在跑**，其余全是它的函数，所以永远同步、绝不错拍。26 个星点的方向也不随机：`dotAngle[i] = (i * 2.39996) % 6.283`，`2.39996` 就是**黄金角 137.5°**，挨着撒会扎堆、隔 137.5° 撒最匀；再乘 `0.52f` 把纵向压扁成椭圆，比正圆更有速度感。

### 3.5 第一幕：黑屏上被"扫"出来

第一幕的入口是 `drawPrelude`，它开头几行就把整幕剧本一次算完：

```java
    private void drawPrelude(Canvas canvas, float t, float w, float h) {
        float reveal = easeInOutCubic(clamp01((t - T_SCAN_IN) / (T_SCAN_END - T_SCAN_IN)));
        float merge = easeOutCubic(clamp01((t - T_SCAN_END) / (T_HOLD_END - T_SCAN_END)));
        float bg = easeInOutCubic(clamp01((t - T_BG_IN) / (T_BG_END - T_BG_IN)));
        float wordFade = 1f - easeOutCubic(clamp01((t - T_WORD_OUT) / (T_WORD_OUT_END - T_WORD_OUT)));

        if (bg < 1f) {
            coverPaint.setColor(Color.BLACK);
            coverPaint.setAlpha((int) (255 * (1f - bg)));
            canvas.drawRect(0f, 0f, w, h, coverPaint);
        }
```

- **在干嘛**：`reveal`（扫到哪了）、`merge`（合成了多少）、`bg`（黑场褪了多少）、`wordFade`（英文名还剩多少）——四个 0~1 的量就是这一幕的全部剧本，下面 `drawLoadPlane` / `drawLoadWord` / `drawLoadFrame` 只吃这几个数。
- **为什么这么写**：**先算后画**。时间运算集中在顶部，下面几十行纯几何；出问题一眼看出是"时间算错"还是"位置画错"。黑场那三行也典型：`alpha = 255 * (1 - bg)`，`bg` 缓动过，所以黑场不是匀速变淡，是先快后慢地褪。
- **老师可能问**：黑场为什么画在飞机**前面**（先画）？——因为飞机是在黑底上被扫出来的，黑场是背景板不是前景遮罩。整幕顺序是"黑场 → 飞机 → 英文名 → 四角框"。

#### `drawLoadPlane`：扫描的真相只是"一个 `clipRect`"
```java
        float shownTop = ph / 2f - ph * reveal;

        canvas.save();
        canvas.translate(heroX, cy);
        canvas.scale(scale, scale);
        canvas.clipRect(-pw / 2f - 8f, shownTop, pw / 2f + 8f, ph / 2f + 8f);

        if (planeGlow != null && merge > 0.35f) {
            glowPaint.setAlpha((int) (200 * merge));
            canvas.drawBitmap(planeGlow,
                    -planeGlow.getWidth() / 2f, -planeGlow.getHeight() / 2f, glowPaint);
        }

        planePaint.setAlpha(255);
```

- **在干嘛**：没有"逐行绘制"这种高级操作，**就是画整张图，再用 `clipRect` 把没扫到的部分裁掉**。`shownTop` 是裁切区上边界：`reveal=0` 时等于 `ph/2`（机身底部，可见高度 0），`reveal=1` 时回到 `-ph/2`（顶部，全露）——上边界**从下往上移动**，看着就是一道光从机尾扫到机头。
- **为什么这么写**：`save/translate/scale` 之后坐标系已经缩放过，`clipRect` 的数字是**位图坐标**，不用管屏幕密度也不用管倍数；而 `clipRect` 是硬件加速里最便宜的裁剪，比 `Path`+`Region.Op` 快得多。
- **老师可能问**：左右各多留 `8f` 干什么？——给抗锯齿边缘留余量，不然裁切线会有半像素黑缝。

合成那段更好玩，是"画一堆横带"堆出来的：
```java
        } else {
            float gap = 5.5f / Math.max(scale, 0.01f);
            float band = gap * (0.38f + 0.62f * merge);
            float top = -ph / 2f;
            for (float y = top; y < ph / 2f; y += gap) {
                canvas.save();
                canvas.clipRect(-pw, y, pw, y + band);
                canvas.drawBitmap(planeBitmap, -pw / 2f, -ph / 2f, planePaint);
                canvas.restore();
            }
        }
```

- **在干嘛**：每隔 `gap` 开一条高 `band` 的窗口，窗口里把机身画一遍。`merge` 从 0 到 1，`band` 从 0.38 倍 `gap` 涨到 1.0 倍——缝隙被填满，条纹就"长"成实体。
- **为什么这么写**：`gap = 5.5f / scale` 这个除法是关键。此刻画布已被 `scale`（约 3.5 倍）放大，**局部坐标 1 像素 = 屏幕上 3.5 像素**；除以 `scale` 才能让条纹在**屏幕上**恒为 5.5 像素。不这么写，条纹会跟着飞机一起变粗，看着像马赛克不像扫描线。
- **老师可能问**：`merge >= 0.98f` 为什么直接画整张不循环？——省掉上百次 `save/clip/draw/restore`，那时条纹宽已等于间距，视觉没差别，是个小性能开关。

#### `drawLoadWord`：扫描边界 `edge` 从哪来
```java
        float tracking = 4.2f * density;
        float wordW = measureTracked(EN_NAME, tracking, loadTextPaint);
        float maxW = getWidth() * 0.86f;
        if (wordW > maxW && wordW > 0f) {
            tracking *= maxW / wordW;
            wordW = maxW;
        }
```
- **在干嘛**：字距 `tracking` 是 4.2dp，先量总宽；超过屏宽 86% 就按比例把字距缩小，保证窄屏不溢出。真正的扫描边界是方法后面那句 `edge = left + wordW * reveal`——和飞机的 `shownTop` 同一个套路，只是换了方向（从左往右）。
- **为什么这么写**：`baseline` 用"机身底部 + 36dp"推出来，飞机怎么缩放，英文名都贴在机身下方固定距离；`top = baseline + ascent` 里的 `ascent` 是**负数**，所以是"减"，一行就把"基线"翻成"字块顶边"。
- 字是**一个字母一个字母画**的（`drawTracked`，`IntroOverlayView.java:797`）：先加出总宽再逐字右移。不用 `Paint.setLetterSpacing`（软件画布上表现不稳），手算最可控，而且 `tracking` 能直接当动画参数用——就是上面按屏宽缩放的那个数。

#### 小零件们（认识就行）
| 方法 | 干了什么 | 一个细节 |
|------|---------|---------|
| `drawBeam` | 画"光"：5dp 青色模糊线打底，叠 1.3dp 白实线 | 两层叠出"发光芯"，比单层亮线耐看 |

`preludeBob`（`IntroOverlayView.java:455`）值得单独记一笔，4 行代码，却把"跨幕不跳帧"做到了数学上：
`handoff = sin(T_TRAVEL * 0.0032) * 5dp`，而第二幕的浮动是 `sin(main * 0.0032) * 5dp * (1 - travel)`，`main` 在交接那刻正好等于 `T_TRAVEL`——**两幕在交接点的浮动值完全相等**，飞机不会"咯噔"跳一下。最后 280ms 用 `blend` 把 4dp 的 idle 线性混到 `handoff` 上，混得平滑。这种"把边界值代进下一个公式反推出来"的做法，比手动调参靠谱得多。

### 3.6 第二幕：起飞、翻转、交接

#### `drawHeroSequence`：一个 `travel` 管住位置和大小
```java
    private void drawHeroSequence(Canvas canvas, float t) {
        float travel = smoothstep(clamp01((t - T_TRAVEL) / (T_TRAVEL_END - T_TRAVEL)));

        float cx = heroX + (finalCx - heroX) * travel;
        float cy = heroY + (finalCy - heroY) * travel;
```

- **在干嘛**：`travel` 用 400ms 从 0 到 1，然后两行线性插值：`起点 + (终点 − 起点) × 进度`——全项目出现频率最高的公式，任何"从 A 挪到 B"都是它。
- **为什么这么写**：**位置只由 `travel` 决定，不由"上一帧在哪"决定**。所以哪怕掉帧、来电话、切后台，回来还是按真实时间算的位置。
- **老师可能问**：`heroX/heroY` 和 `finalCx/finalCy` 哪来的？——前者是 `onSizeChanged` 算的屏幕中心偏上（`heroY = h*0.47f`）；后者是 `resolveTargets` 用 `getLocationInWindow` 减出来的**真标题控件中心**（`IntroOverlayView.java:397`），拿不到就用 `h*0.19f` 兜底。

翻转那 110ms 是整段动画最巧的地方：
```java
        float scale = (heroPlaneScale * (0.74f + 0.26f * enter)
                + (headerPlaneScale - heroPlaneScale) * travel);

        // 翻转前半程：横向压扁到 0
        float flip = 1f;
        if (t >= T_FLIP_OUT) {
            float q = clamp01((t - T_FLIP_OUT) / (T_FLIP_MID - T_FLIP_OUT));
            flip = Math.max(0f, (float) Math.cos(q * Math.PI / 2f));
        }
```

- **在干嘛**：`flip` 就是横向缩放。`cos(0)=1`、`cos(90°)=0`，110ms 里机身被压成一条竖线；真正生效在 `canvas.scale(scale * flip, scale)`——**只压 X 不压 Y**，"翻面"的全部实现就这样，没有任何 3D 相机。
- **为什么这么写**：① 用 `cos` 不用线性，是因为余弦在终点**速度最大**——压到 0 那一瞬是"闪"过去的；下一段用 `sin` 从 0 展开，起点速度也最大，两边在 0 宽那帧**速度方向一致、宽度都是 0**，所以接缝看不出来。② `Math.max(flip, 0.001f)` 的 `0.001` 不能省：`scale(0, ...)` 会让画布矩阵**不可逆**，后面的 `clipRect`/`drawBitmap` 会退化甚至画不出来；0.001 视觉上就是 0，但矩阵还有救。
- **老师可能问**：为什么不在 0 宽那帧直接 `return`？——那帧正好是"换人"时刻，两段都在画（只是宽度≈0），逻辑上不用特判。

#### `drawPlaneSweep` 与 `drawTitleFlippedIn`：翻转前后的两个细节

`drawPlaneSweep` 是斜带高光：把机身用白色版 `Paint` 再画一遍，只用 `clipRect` 露出斜带里的部分，`x` 从 `-1.1w` 走到 `+1.1w` 扫过机身，亮度用 `sin(π·p)`。诀窍是 `clipRect` 建立后就**固定在画布坐标系里**，`rotate(18f)` 转回来画图裁切区并不会跟着转，所以全程不离开主画布、省掉一次 `saveLayer` 离屏渲染（那要额外分配一张全屏位图）。不过如 3.1 所说，这段现在**已经过点不跑了**。

翻转后半程才是重点：
```java
        float cross = clamp01((t - T_CROSS) / (T_CROSS_END - T_CROSS));
        float blockAlpha = 1f - cross;
        if (blockAlpha <= 0f) {
            return;
        }
        float q = clamp01((t - T_FLIP_IN) / (T_FLIP_IN_END - T_FLIP_IN));
        float open = (float) Math.sin(q * Math.PI / 2f);

        float baseline = -(fontMetrics.ascent + fontMetrics.descent) / 2f;

        canvas.save();
        canvas.translate(finalCx, finalCy);
        canvas.scale(Math.max(open, 0.001f), 1f);
        titlePaint.setAlpha((int) (255 * blockAlpha));
        canvas.drawText(titleText, -textWidth / 2f, baseline, titlePaint);
```

- **在干嘛**：`open` 从 0 涨到 1，`scale(open, 1)` 让中文标题从一条线展开到满宽（130ms）；同时 `blockAlpha = 1 - cross` 让**自己**在最后 140ms 淡出，而 `syncMenuText` 让**真控件**用同一进度淡入——一进一出，就是交叉淡入。
- **为什么这么写**：① 标题的字号、字重、渐变着色器全在 `setTargets` 里**从真控件抄过来**（`setTextSize(title.getTextSize())`、`getTypeface()`、上下白青的 `LinearGradient`），两边看着像同一个东西，交接才无缝。② `baseline` 是"垂直居中"的标准技巧：画布原点已 `translate` 到文字块中心，而 `drawText` 的 y 是**基线**，所以要把基线抬到 `-(ascent + descent)/2`——`ascent + descent` 就是"墨迹高度"，取负一半正好是中心到基线的距离。
- **老师可能问**：`scale` 为什么只压 X？——翻转收尾，Y 方向必须保持原高度，否则字会"长高"，跟前面压扁的机身接不上。

#### `syncMenuText`：把真实控件的透明度跟上节奏

- **在干嘛**：每帧给 `titleView`/`subtitleView` 写 `alpha`。标题**线性**跟 `cross`（和自己的淡出互补，加起来恒等于 1，整体不闪）；副标题用 `easeOutCubic` 单独缓入（`T_SUB` 2160 → `T_SUB_END` 2480）。
- **为什么这么写**：`setAlphaQuietly` 里那个 **2% 阈值**（变化超过 `0.02f` 才真调）是必需的：`setAlpha` 会触发一次 `invalidate`，每帧无脑调两次就是每帧多两次重绘；140ms 淡入里 2% 的台阶肉眼看不出来，省下的重绘是实打实的。
- **老师可能问**：`finish()` 里为什么还要再 `setAlpha(1f)`？——兜底。万一最后一帧停在 `cross = 0.97`，真控件就是 0.97，肉眼能看出"差一点点"，强制拉满最省心。

### 3.7 `onDraw` 里各图层的绘制顺序

```java
    @Override

        float t = timeMs();
        float w = getWidth();
        float h = getHeight();
        if (w <= 0 || h <= 0) {
            return;
        }
        resolveTargets();
        if (!targetsReady) {
            finalCx = w / 2f;
            finalCy = h * 0.19f;

```

```java
        float main = mainMs();
        if (main >= 0f) {
            drawCover(canvas, main, w, h);
            drawScanLine(canvas, main);
            drawBurst(canvas, main);
            drawHeroSequence(canvas, main);
            syncMenuText(main);
        }
        if (t < T_PRELUDE) {
            drawPrelude(canvas, t, w, h);
        }
    }
```

- **在干嘛**：这就是"总导演"。`w/h` 为 0 时直接返回（还没测量完就画会崩）；算落点，拿不到真控件就用 `h*0.19f` 兜底；然后**先画衔接幕、再画加载幕**。
- **为什么这么写**：后面画的盖在前面。加载幕的黑场是**满屏矩形**，必须最后画才能遮住底下一切；衔接幕内部又自成一套"底→面"顺序。两幕时间区间其实互斥（`main >= 0` 等价于 `t >= 3020`，那时 `t < T_PRELUDE` 已不成立），所以这个先后现在严格说"不影响画面"——但按"最后画的最上层"来排，以后加一层过场不会踩坑。
- **老师可能问**：`resolveTargets()` 每帧调不慢吗？——第一句就是 `if (targetsReady || ...) return;`，算过一次就置 `true`，`onSizeChanged` 时再置回 `false` 重算。

六层视觉元素从底到顶：

| 顺序 | 层 | 谁画的 | 备注 |
|------|----|--------|------|
| 1 | 星空背景 | **不是它画的**，是它下面的菜单界面 | 这个 View 是半透明覆盖层，黑场褪去才露得出星空 |
| 2 | 黑遮罩 / 黑场 | `drawCover` / `drawPrelude` 的 `coverPaint` | 唯一的满屏不透明层 |
| 3 | 扫描线、星点 | `drawScanLine` / `drawBurst` | 都在飞机下面 |
| 4 | 机身光晕 | `glowPaint` | 模糊位图，比机身大一圈（四周留 20px） |
| 5 | 机身 / 中文标题 | `drawBitmap` / `drawText` | 白色斜带高光叠在机身上 |
| 6 | 英文名、定位线、射线、取景框 | `drawLoadWord` 系列 | 只在第一幕出现 |

### 3.8 播完之后怎么告诉外面：`skip` 与 `finish`

`onTouchEvent` 里按下就调 `skip()`（`IntroOverlayView.java:862`）：先用 `skipping`/`finished` 两个布尔值防重入，停帧循环、`removeFrameCallback`，然后 `animate().alpha(0f).setDuration(140L).withEndAction(this::finish)`。这里反而用了系统动画——因为这段**不在时间轴上**：它跟 3.82 秒的剧本无关，是"用户随时可能打断"的独立过渡，`withEndAction` 一行就串起收尾，自己再手写一个 140ms 的 `t` 纯属浪费。

```java
        if (titleView != null) {
            titleView.setAlpha(1f);
        }
        if (subtitleView != null) {
            subtitleView.setAlpha(1f);
        }
        if (getParent() instanceof ViewGroup) {
            ((ViewGroup) getParent()).removeView(this);
        }
        if (listener != null) {
            listener.onIntroFinished();
        }
    }
```

- **在干嘛**：`finish` 是全剧终。① 兜底把真控件透明度拉满；② **把自己从父容器摘掉**——它已经没用了，留着就是一层白占全屏、每次重绘都要跑 `onDraw` 的空壳；③ 回调 `listener.onIntroFinished()`，外面（`MainActivity`）接着播菜单项依次淡入。
- **为什么这么写**：注意顺序——**先 `removeView` 再回调**。这样外部收到回调时，"覆盖层已经不存在"这个前提一定成立，可以放心操作下面的控件；`Listener` 接口注释也是这么承诺的（`IntroOverlayView.java:53`）。`getParent() instanceof ViewGroup` 的判空也必要：万一已被别处移除，直接强转会 NPE。
- **老师可能问**：位图什么时候回收？——`onDetachedFromWindow` 里 `removeFrameCallback` + `releaseBitmaps()`。`removeView` 会触发 detach，所以摘掉自己那一刻两张位图（机身 + 光晕）也就 `recycle()` 了，不留内存。

另外两个"准备工作"顺口提一句：

- **`setTargets` 必须在 `addView` 之前调**：它从真标题抄字号/字重/渐变，并触发 `buildPlane()`。`buildPlane` 干三件不显眼但必要的事：`(pixels[i] >>> 24) < 150` 把半透明尾焰**清零**（否则放大 3.5 倍后机头多一根毛刺）；扫非透明像素求包围盒**裁掉四周空白**（否则光晕和机身圆心对不上、光会偏）；用 `PorterDuff.Mode.DST_IN` 把白→青渐变"喷"进剪影里，得到同色填充的蓝色飞机。
- **`onSizeChanged` 里全是比例没有绝对值**：`heroX = w/2`、`heroY = h*0.47f`、主角态宽 `0.30f * w`、页头态高 `textHeight * 1.25f`——5 寸小屏到平板构图比例不变。注释那句"原图只有 100px，再放就要糊边"是实话，30% 屏宽已是这张图的清晰度上限。

### 3.9 这一章最容易问倒人的点

1. 如果被问到 **"为什么不用 `Animator`/`Animation`"**，就答：这里是"一个时间数字同时驱动十几个参数"，而且最后要把透明度写回**布局里真实的 `TextView`**——补间动画改不了真属性，交接必然闪；`AnimatorSet` 会把一条时间轴拆成二十条，改节拍要动好几处。
2. 如果被问到 **"结束为什么不会闪一下"**，就答：落点用 `getLocationInWindow` 相减算出**真控件中心**，字号/字重/渐变从真控件抄来，最后 140ms 交叉淡入（`T_CROSS` 2360 → `T_CROSS_END` 2500），`finish` 再兜底 `setAlpha(1f)`，并**先 `removeView` 再回调**。
3. 如果被问到 **"掉帧会不会越走越慢/错位"**，就答：不会。所有位移和透明度都是 `t` 的**解析函数**，没有累加量，掉帧只少画几张，时间照样往前走。
4. 如果被问到 **"`scale` 为什么写 `0.001` 不写 0"**，就答：`scale(0, ...)` 让画布矩阵不可逆，后面的 `clipRect`/`drawBitmap` 会退化；0.001 在屏幕上就是 0 宽，但矩阵还合法。
5. 如果被问到 **"`drawCover`/`drawBurst` 是不是根本没执行"**，就答：按现在的双时间轴确实过点了（`mainMs()` 一进场就是 1720，它们窗口在 0–900），是第一版单时间轴留下的段落，功能已被加载幕接管——如实说"保留常量、不影响运行"，别硬说它们在跑。

## 四、游戏页 `GameActivity` 与系统栏适配

> 一句话：`GameActivity` 是个“包工头”——它自己不打飞机、不算碰撞，只负责把素材、战场、世界、屏幕、存档按顺序装好，再在合适的时候按下暂停键和结算键。

### 4.1 先认识这个“包工头”

`GameActivity.java` 五百多行，看着吓人，其实可以按“手里攥着的东西”分成三堆：

| 攥着什么 | 字段 | 用处 |
|---|---|---|
| 游戏对象 | `gameView`、`world`、`difficulty`（`GameActivity.java:74`–`78`） | 一个负责画，一个负责算，一个记住这局难度 |
| 存档与声音 | `sound`、`store`、`scoreDao`（`GameActivity.java:76`、`77`、`80`） | SharedPreferences、SQLite、SoundPool/MediaPlayer |
| 一次性状态 | `scoreSaved`、`newRecord`（`GameActivity.java:83`、`85`） | 防止重复结算、记住是否破纪录 |

它只做五件事：建世界、把 `GameSurfaceView` 放进来、把核心层事件翻译成声音、结算成绩、管生命周期。**没有一行“敌机怎么飞、子弹怎么撞”**——那些全在 `core/GameWorld` 里。所以读这个类，重点看“顺序”和“时机”，不要找游戏规则。

### 4.2 `onCreate`：一条装配线，顺序不能乱

#### `onCreate(Bundle)`

```java
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        enterFullscreen();

        difficulty = readDifficulty();

        battleMode = getIntent() != null && getIntent().getBooleanExtra(EXTRA_BATTLE, false);
        if (battleMode) {
            // 对战局的难度由房间决定（进房方从服务端的 joined 消息里拿到），
            // 这里用会话里已同步好的难度覆盖本地传入值，保证两人玩同一难度。
            session = BattleSession.getInstance();
            if (session.getDifficulty() != null) {
                difficulty = session.getDifficulty();
            }
        }
```

- **在干嘛**：先全屏，再读难度；如果是对战局，用房间里的难度覆盖掉 Intent 带来的难度。
- **为什么这么写**：全屏要放在 `setContentView` 之前，先把窗口的避让规则定下来再放内容；反过来的话，内容会先按默认规则量一遍，可能出现一次尺寸跳变。
- **老师可能问**：对战为什么不用传进来的难度？——两个人必须玩同一难度，以服务端房间为准，本地参数只当默认值。

后面是一条 8 步的装配线，按执行顺序列出来：

| 步 | 位置 | 干什么 | 漏了会怎样 |
|---|---|---|---|
| 1 | `GameActivity.java:111` | `Assets.load(this)` 解码 22 张图 | 画面全空 |
| 2 | `GameActivity.java:112` | `SpriteMetricsHolder.install(assets)` 把宽高告诉核心层 | 所有实体按默认 32×32 算碰撞，手感全错 |
| 3 | `GameActivity.java:115` | `configurePlayField()` 算逻辑战场尺寸 | 敌机从屏幕外生成或提前消失 |
| 4 | `GameActivity.java:116` | `PlayField.setTopInset(135)` 划出顶部安全带 | 英雄机飘进 UI 区，手指和背包格打架 |
| 5 | `GameActivity.java:119`–`124` | 建 `LocalStore`、`ScoreDao`、`SoundManager`，套用静音开关 | 没声音、成绩存不下 |
| 6 | `GameActivity.java:127`–`132` | `createWorld(difficulty)` + 套皮肤 + 挂监听器 | 没世界可画 |
| 7 | `GameActivity.java:142`–`143` | `world.start()` 注册观察者，播普通 BGM | 炸弹/冰冻的观察者没注册，效果不触发 |
| 8 | `GameActivity.java:146`–`159` | `new GameSurfaceView(...)` + `setContentView` | 黑屏 |

**为什么顺序不能换**：`Assets` 必须在 `createWorld` 前面，因为核心层造实体时就要问“这类东西多宽多高”（`SpriteMetricsHolder` 默认返回 32）；`PlayField` 也必须先配好，因为英雄机初始位置要按战场宽高算。这就像开饭：先买菜、再量桌子、最后才请厨师，顺序反了只能干瞪眼。

### 4.3 先备菜，再量桌子：素材与战场尺寸

#### `configurePlayField()`

```java
    private void configurePlayField() {
        DisplayMetrics dm = getResources().getDisplayMetrics();
        int logicalWidth = 512;
        int logicalHeight = Math.round(logicalWidth * (dm.heightPixels / (float) dm.widthPixels));
        // 兜底：极端比例下也不能算出离谱的高度
        logicalHeight = Math.max(768, Math.min(logicalHeight, 1600));
        PlayField.configure(logicalWidth, logicalHeight);
    }
```

- **在干嘛**：逻辑宽度永远 512，高度按屏幕长宽比换算，再夹在 768～1600 之间。
- **为什么这么写**：Windows 版窗口固定 512×768，直接搬到 20:9 手机上会上下留黑边；按比例拉伸能铺满，代价是纵向更“深”、难度略降。
- **具体数字**：1080×2400 的手机算出 `512 × 2.222 ≈ 1138`；1080×1920 算出 910；再长的屏最多 1600，防止战场长得离谱。
- **老师可能问**：为什么不用 dp？——`core` 里所有速度、半径都是“逻辑单位”，渲染层统一乘缩放系数；换单位等于把整套数值重调一遍。

`Assets.load(this)` 每次进游戏都会重新解码 22 张图（19 张精灵 + 3 张难度背景），没有做缓存。换来的是“进游戏前素材一定齐”，不会玩到一半才发现某张图没加载。

`PLAY_TOP_INSET = 135` 是个很实在的数：顶部得分卡占 12～88、难度胶囊 14～38、背包格 12～78，135 刚好把这些都让开——在 1138 高的战场上约占 12%。它在核心层的 `AbstractFlyingObject.moveTo()` 里生效，`y` 会被钳在 `topInset` 以下（`AbstractFlyingObject.java:111`），所以英雄机永远进不了那一条带。

### 4.4 存档、声音、世界、皮肤

#### 存档、声音、世界与皮肤

```java

        scoreDao = new ScoreDao(this);
        sound = new SoundManager(this);
        // 音乐与音效是两个独立开关，分别套用
        sound.setMusicMuted(store.isMusicMuted());
        sound.setSoundMuted(store.isSoundMuted());

        // 4) 创建游戏世界，套上玩家选中的皮肤

        HeroAircraft.Skin skin = store.getSelectedSkin();
        for (HeroAircraft hero : world.getHeroes()) {
            hero.setSkin(skin);
        }
```

- **在干嘛**：三个“外设”各建一个：`LocalStore` 管 SharedPreferences，`ScoreDao` 管 SQLite，`SoundManager` 管 BGM 和音效；然后按难度造世界，把玩家选的皮肤套到每一架英雄机上。注意皮肤**不是**从 `Intent` 传的，是 `LocalStore.getSelectedSkin()` 从 SharedPreferences 里读的，`MainActivity` 只传了难度。
- **为什么这么写**：世界是“一局一个”的，必须在 `onCreate` 里新建；存档和声音是“跟着页面走”的，页面销毁时要关掉/释放，所以也在这里建。
- **老师可能问**：皮肤为什么要循环 `getHeroes()`？——底层支持双人同屏，可能有两架英雄机，循环写以后加第二个人不用改。

`createWorld()`（`GameActivity.java:241`）就是一个 `switch`：`HARD` 给 `HardGameWorld`，`NORMAL` 给 `NormalGameWorld`，其余给 `EasyGameWorld`。三个子类的差别只在刷怪节奏、同屏敌机数量、英雄射速、Boss 阈值和各类敌机的出现概率，公共流程全在父类 `GameWorld` 里。说“工厂”可以，但它没有工厂类，就是一个返回父类引用的方法。

`world.start()`（`GameActivity.java:142`）看着像“启动线程”，其实不是——渲染线程是 `GameSurfaceView` 自己起的，`GameWorld.start()` 只做一件事：把世界注册到 `BombSubject`、`FreezeSubject` 两个观察者单例上，这样炸弹/冰冻事件才能通知到它。

调试注入那段（`GameActivity.java:135`–`140`）只有 DEBUG 包生效：在渲染线程启动前，往英雄机坐标塞一个血包和一个火力包，第一帧就被捡走，用来验证背包。**两个道具正好塞满容量 2 的背包**，多一个都放不下。

### 4.5 把 `GameSurfaceView` 塞进 Activity

#### 挂载视图与回调

```java
        // 5) 挂载渲染视图
        gameView = new GameSurfaceView(this, world, assets);
        gameView.setCallback(new GameSurfaceView.Callback() {
            @Override
            public void onGameOver(int score) {
                GameActivity.this.onGameOver(score);
            }

            @Override
            public void onExitRequested() {
                // 点返回键 / 暂停菜单里选返回：立刻结算本局再回主菜单
                GameActivity.this.settleAndFinish();
            }
        });
        setContentView(gameView);
```

- **在干嘛**：把世界和素材交给 `GameSurfaceView`，再注册两个回调；最后 `setContentView`，整页就这一个 View，没有 XML 布局。
- **为什么这么写**：`SurfaceView` 自己开渲染线程，Activity 不需要 `findViewById` 任何东西，也不需要 `setContentView(R.layout...)`。
- **注意线程**：`onGameOver` 是渲染线程调过来的（`GameSurfaceView.java:165`–`168`），`onExitRequested` 是主线程触摸事件里调的（`GameSurfaceView.java:240`–`242`）。同一个匿名类，两个方法跑在两个线程上，这是后面必须用 Handler 的原因。

`getWindow().addFlags(...FLAG_KEEP_SCREEN_ON)`（`GameActivity.java:160`）和 `GameSurfaceView` 构造里的 `setKeepScreenOn(true)`（`GameSurfaceView.java:81`）是双保险，防止玩家盯着看的时候屏幕自己灭。

返回键不是默认的 `finish()`，而是被接管了：

```java
        // 系统返回键也走「结算后返回」，避免直接把一局成绩丢掉
        getOnBackPressedDispatcher().addCallback(this, new OnBackPressedCallback(true) {
            @Override
            public void handleOnBackPressed() {
                settleAndFinish();
            }
        });
```

- **在干嘛**：按返回键时先结算，再关页面。
- **为什么这么写**：默认返回是直接 `finish()`，这一局的分数就白打了；`OnBackPressedCallback(true)` 里的 `true` 表示“启用”，抢下返回键。
- **老师可能问**：这个回调会不会泄漏？——`addCallback(this, ...)` 传了 LifecycleOwner，页面销毁时自动移除。

### 4.6 事件监听器：逻辑层“咳嗽”，这一层“配音”

#### `createListener()`


### 4.7 难度参数怎么从 `Intent` 进来

#### `readDifficulty()` + 发送端

```java
    private Difficulty readDifficulty() {
        String extra = getIntent() == null ? null : getIntent().getStringExtra(EXTRA_DIFFICULTY);
        if (extra == null) {
            return Difficulty.EASY;
        }
        try {
            return Difficulty.valueOf(extra);
        } catch (IllegalArgumentException e) {
            return Difficulty.EASY;
        }
    }
```

- **在干嘛**：从 Intent 里取字符串，转成 `Difficulty` 枚举；取不到、传错都退回 `EASY`。
- **为什么这么写**：发送端是 `MainActivity.java:219`–`220`，存的是 `difficulty.name()`，也就是 `"EASY"`、`"NORMAL"`、`"HARD"`；接收端用 `valueOf` 反解，不玩“0/1/2”这种魔法数字。
- **老师可能问**：万一别人传个 `"easy"` 小写呢？——`valueOf` 抛 `IllegalArgumentException`，被 catch 住退回 `EASY`，页面不会崩。

### 4.8 游戏结束：从渲染线程“跳”回主线程

#### `onGameOver(int)` 与 `GameHandler`

```java
    private void onGameOver(int score) {
        if (battleMode) {
            // 对战局：本机阵亡，上报 hp=0 等对手结束，不写排行榜
            handler.post(() -> onBattleLocalGameOver(score));
            return;
        }
        Message message = Message.obtain();
        message.what = MSG_GAME_OVER;
        message.arg1 = score;          // 用 arg1 携带分数，省去额外对象
        handler.sendMessage(message);
    }
```

- **在干嘛**：单机局把分数塞进 `Message.arg1`，`what = MSG_GAME_OVER`，发给主线程 Handler；对战局换个分支，只上报“我死了”。
- **为什么这么写**：这个回调来自渲染线程（`GameSurfaceView.run()`），在子线程弹 `AlertDialog` 会直接抛 `CalledFromWrongThreadException`。`Message` 比 `Bundle` 轻，分数是 `int`，`arg1` 刚好装得下。
- **老师可能问**：`Message.obtain()` 和 `new Message()` 有区别吗？——前者从池子里复用，少一次对象分配；一局只发一条，差别不大，但习惯是好的。

真正的界面操作在静态内部类里：

```java
    private static class GameHandler extends Handler {
        private final WeakReference<GameActivity> activityRef;

        GameHandler(GameActivity activity) {
            super(Looper.getMainLooper());
            this.activityRef = new WeakReference<>(activity);
        }

        @Override
        public void handleMessage(@NonNull Message msg) {
            GameActivity activity = activityRef.get();
            if (activity == null || activity.isFinishing()) {
                return;
            }
```

- **在干嘛**：`super(Looper.getMainLooper())` 把 Handler 绑到主线程队列；`handleMessage` 里先看 Activity 还在不在，再按 `msg.what` 调 `showGameOverDialog(msg.arg1)`。
- **为什么这么写**：非静态内部类会隐式持有外部 `GameActivity`，消息队列里只要还有一条没处理的消息，Activity 就回收不了；写成 `static` + `WeakReference` 才是标准解法。
- **老师可能问**：那为什么不用 `runOnUiThread`？——也行，它内部也是往主线程 post；用 Handler 是为了顺便练 `what`/`arg1` 这套消息机制，而且 `onDestroy` 里能一次性 `removeCallbacksAndMessages(null)`。

### 4.9 结算、弹框、跳排行榜

#### `showGameOverDialog(int)` 与 `saveScore(int)`

```java
    private void showGameOverDialog(int score) {
        saveScore(score);
        String message = "本局得分：" + score
                + (newRecord ? "\n\n刷新了本机最高分！" : "");
        new AlertDialog.Builder(this)
                .setTitle("游戏结束")
                .setMessage(message)
                .setCancelable(false)
                .setNegativeButton("返回主菜单", (dialog, which) -> finish())
                .setPositiveButton("查看排行榜", (dialog, which) -> openRankAndFinish())
                .show();
    }
```

- **在干嘛**：先存成绩，再拼提示语，最后弹一个不能点外面关掉的对话框；左边回主菜单，右边去排行榜。
- **为什么这么写**：`saveScore()` 要在拼字符串之前调用，因为 `newRecord` 是它顺手改的；顺序反了，破纪录提示就永远不出现。`setCancelable(false)` 防止玩家点空白处把对话框关掉、成绩却没结算。
- **老师可能问**：对话框按钮为什么用 `setNegativeButton` 放“返回主菜单”？——`negative` 在左、`positive` 在右，和系统习惯一致；这里“去排行榜”更像主操作。

```java
    private void saveScore(int score) {
        if (scoreSaved) {
            return;
        }
        scoreSaved = true;
        newRecord = store.submitScore(difficulty, score);

        ScoreRecord record = new ScoreRecord(
                store.getPlayerName(), score, difficulty.name(), System.currentTimeMillis());
        long id = scoreDao.insert(record);
        if (id == -1) {
            Log.e("GameActivity", "排行榜写入失败: " + score);
        }
    }
```

- **在干嘛**：同一份成绩写两个地方——`LocalStore` 存“本机该难度最高分”，SQLite 存“这一局的完整记录”。
- **为什么写两份**：最高分用来解锁皮肤、判断有没有破纪录，只需要一个数；排行榜要按难度列前 100 条，得留完整记录（名字、分数、难度、时间）。
- **老师可能问**：`scoreSaved` 为什么在写之前就置 `true`？——防重入：写库失败也不重试，总比弹两次结算、写两条记录强。

主动退出走另一条路：

```java
    private void settleAndFinish() {
        if (!isFinishing()) {
            if (!battleMode) {
                saveScore(world == null ? 0 : world.totalScore());
            }
        }
        finish();
    }
```

`isFinishing()` 防止页面已经在关闭时又结算一次；对战局不写排行榜，因为那局的输赢由服务端判。点“查看排行榜”则是 `openRankAndFinish()`（`GameActivity.java:347`）：`startActivity` 打开 `RankActivity`，紧接着 `finish()` 自己。这样从排行榜返回时回到主菜单，而不是又弹回结算框。

### 4.10 生命周期四兄弟：谁负责什么

一张表先记住：

| 回调 | 什么时候来 | 这一页干什么 |
|---|---|---|
| `onCreate` | 页面第一次创建 | 装配整个世界（只做一次） |
| `onResume` | 回到前台、能交互 | 解除暂停、恢复 BGM |
| `onPause` | 失去前台（Home、锁屏、切应用） | 暂停渲染循环、暂停 BGM |
| `onDestroy` | 页面真正销毁 | 停线程、注销观察者、释放音频/数据库 |

#### `onPause()` / `onResume()`

```java
    @Override
    protected void onPause() {
        super.onPause();
        if (gameView != null) {
            gameView.setPaused(true);
        }
        if (sound != null) {
            sound.pauseBgm();
        }
    }
```

```java
    @Override
    protected void onResume() {
        super.onResume();
        if (gameView != null) {
            gameView.setPaused(false);
        }
        if (sound != null && !world.isGameOver()) {
            sound.resumeBgm();
        }
    }
```

- **在干嘛**：`onPause` 把 `GameSurfaceView` 的 `paused` 置真、暂停 BGM；`onResume` 反过来。`paused` 是 `volatile` 字段，渲染线程每圈都会看它，置真后只是空转画最后一帧，不再 `world.update()`。
- **为什么切后台必须暂停**：渲染线程不知道你有没有在前台，不暂停就继续 25Hz 跑逻辑、继续耗电；更坑的是回来时 `System.nanoTime()` 已经跳了一大截，如果不做处理会“追帧”连跳，飞机瞬间被撞。`GameSurfaceView` 里虽然也做了“落后超过 5 步就丢弃欠账”（`GameSurfaceView.java:160`–`162`），但暂停才是从源头解决。
- **为什么 `onResume` 要判断 `!world.isGameOver()`**：游戏结束已经把 BGM 停了，如果这时从后台回来还恢复 BGM，就会在结算框后面又响起战斗音乐。
- **老师可能问**：切后台为什么不直接结算？——玩家可能只是回个微信，切回来还要接着玩；结算只发生在“死亡”或“主动退出”。

#### `onDestroy()`

```java
    protected void onDestroy() {
        // 清掉还没处理的消息，避免 Handler 继续持有已销毁的 Activity
        handler.removeCallbacksAndMessages(null);
        if (gameView != null) {
            gameView.shutdown();
        }
        if (world != null) {
            world.stop();
        }
        if (sound != null) {
            sound.release();
        }
        if (scoreDao != null) {
            scoreDao.close();
        }
```

- **在干嘛**：按“消息 → 渲染线程 → 世界 → 音频 → 数据库”的顺序拆。
- **为什么是这个顺序**：先清 Handler，防止刚销毁又弹出一个结算框；再 `shutdown()`（内部 `join(1000)` 等渲染线程退出，`GameSurfaceView.java:113`–`124`），然后才 `world.stop()`，避免线程还在 `update()` 时把世界拆了。`world.stop()` 会把世界从 `BombSubject`/`FreezeSubject` 这两个**静态单例**里注销——不注销的话，静态集合会一直攥着旧 `world`，下一局的炸弹/冰冻会同时通知到它，内存也回收不掉。
- **老师可能问**：`onDestroy` 一定会执行吗？——正常返回、`finish()` 会；进程被系统直接杀掉时不会。成绩在死亡或主动退出时就写好了，不靠 `onDestroy` 兜底。
- **补充**：旋转屏幕默认会销毁重建 Activity，这一页在 `AndroidManifest.xml:29`–`30` 锁了竖屏并声明了 `configChanges="orientation|screenSize|keyboardHidden"`，所以转屏不会重建，一局不会丢。

### 4.11 全屏：三行代码 + 一个主题

#### `enterFullscreen()`

```java
    private void enterFullscreen() {
        WindowCompat.setDecorFitsSystemWindows(getWindow(), false);
        WindowInsetsControllerCompat controller =
                WindowCompat.getInsetsController(getWindow(), getWindow().getDecorView());
        controller.hide(WindowInsetsCompat.Type.systemBars());
        controller.setSystemBarsBehavior(
                WindowInsetsControllerCompat.BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE);
    }
```

- **在干嘛**：三件事——① 让内容铺到系统栏底下（edge-to-edge）；② 把状态栏和导航栏都藏起来；③ 设置“从边缘上划可以临时叫出系统栏，过几秒自动隐藏”。
- **为什么这么写**：`setDecorFitsSystemWindows(false)` 管“布局避不避让”，`hide()` 管“栏可不可见”，两件事，不能互相替代。`BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE` 是沉浸式游戏的标准行为，否则玩家想调音量/回桌面都找不到手势条。
- **主题里还有一道保险**：`themes.xml:19`–`22` 的 `Theme.AircraftWar.Fullscreen` 声明了 `windowFullscreen=true`、无 ActionBar、无标题栏。主题在窗口创建时就生效，代码在 `onCreate` 里再补一刀，避免启动瞬间闪出状态栏。
- **老师可能问**：全屏了，状态栏盖住内容怎么办？——游戏页故意让它盖：画面本来就该铺满，顶部 HUD 由渲染器自己在安全位置画；普通页面则用下一节的 `UiInsets` 补回来。

### 4.12 `UiInsets`：为什么别的页面都调，游戏页不调

先看它自己的注释，已经把原因说透了：

```java
/**
 * 系统栏内边距处理。
 * <p>
 * 从 Android 15（targetSdk 35）开始，系统对非全屏页面也会强制 edge-to-edge：
 * 内容会绘制到状态栏和导航栏底下。普通页面必须自己把系统栏高度补成内边距，
 * 否则顶部的返回按钮会被状态栏压住、底部内容会被手势条盖住。
 * <p>
 * 游戏页是全屏沉浸式，自己隐藏了系统栏，不需要这个处理。
 */
```

#### `applySystemBars(View)`

```java
    /** 把根布局的内边距设为系统栏高度 */
    public static void applySystemBars(View root) {
        ViewCompat.setOnApplyWindowInsetsListener(root, (view, windowInsets) -> {
            Insets bars = windowInsets.getInsets(WindowInsetsCompat.Type.systemBars());
            view.setPadding(bars.left, bars.top, bars.right, bars.bottom);
            return WindowInsetsCompat.CONSUMED;
        });
    }
```

- **在干嘛**：给根 View 挂一个监听器，每次系统栏尺寸变化（进入页面、旋转、键盘弹出、手势条显隐），就把根 View 的 padding 设成四条边的系统栏高度。
- **为什么需要**：`targetSdk` 是 35（`app/build.gradle:19`），Android 15 强制 edge-to-edge。状态栏一般有二十多到四十多 dp，底部手势条大约 24dp；不补 padding，顶部的“返回”按钮会被时间和电量压住，排行榜最后一行会被手势条盖住。
- **为什么返回 `CONSUMED`**：表示“这层已经把 insets 用掉了”，不再往子 View 传，避免 ScrollView 里的内容又被加一次 padding、出现双倍空白。
- **谁在调**：`MainActivity.java:69`（`menu_scroll`）、`SkinActivity.java:107`（`scroll`）、`RankActivity.java:59`（`root_rank`）、`BattleRoomActivity.java:143`（`scroll`）。四个普通页面，一个不落。
- **为什么 `GameActivity` 不调**：它把系统栏藏了，insets 基本是 0；它用另一套办法解决顶部遮挡——`PlayField.setTopInset(135)`，把“UI 安全带”交给核心层，英雄机自己就进不去。系统栏都藏了还补 padding 没有意义，游戏要的是从 (0,0) 铺满，HUD 位置由 512 逻辑坐标自己算。
- **老师可能问**：为什么不直接在 XML 里写 `fitsSystemWindows="true"`？——那是“整体缩进去”，背景也会跟着缩，还会和 ScrollView 的裁剪打架；手动监听只补 padding、不动背景，控制权在自己手里。

> 注意一个小坑：`setPadding` 是**覆盖**，不是累加。这些页面的根布局本身没设 padding（`activity_main.xml` 的 `menu_scroll`、`activity_rank.xml` 的 `root_rank` 都没有），所以直接覆盖没问题；如果根布局原本有 padding，得先记住原值再相加。

### 4.13 网络对战那一段（可以先跳过）

`EXTRA_BATTLE=true` 时走另一套逻辑，和单机最大的区别是：**不算排行榜，等服务器判胜负**。

- `setupBattle()`（`GameActivity.java:357`）：挂会话监听、刷新对手信息、启动每秒上报。它放在 `setContentView` 之后，因为要往 `gameView` 上写“等待对手加入…”。
- `createBattleListener()`（`GameActivity.java:363`）把 `onState`/`onOver`/`onOpponentLeft`/`onError`/`onDisconnected` 翻译成刷新信息、弹框或 Toast；`refreshOpponentInfo()`（`GameActivity.java:419`）负责拼“对手 xx 得分 xx 生命 xx/1000”的文案。
- `startBattleReporting()`（`GameActivity.java:396`）：主线程 Handler 每秒跑一次，把 `world.totalScore()` 和血量报给服务器；网络 IO 绝不能放渲染线程。
- `onBattleLocalGameOver()`（`GameActivity.java:437`）：本机死了就停上报、报一次 `hp=0`，然后等对手。
- `onBattleOver()`（`GameActivity.java:448`）：按自己是 A 还是 B 取出双方分数，同分判平局，弹框后 `finish()`。
- `onBattleOpponentLeft()`（`GameActivity.java:468`）：对手掉线，直接判赢。
- `stopBattleReporting()`（`GameActivity.java:413`）：结算、对手离开、页面销毁时都会调用，把每秒上报的 `Runnable` 从主线程队列里撤掉；`onDestroy()` 里再 `session.leave()`（`GameActivity.java:555`）通知服务端退出并关连接。

核心就一句：**对战局不写本地排行榜，胜负以服务端消息为准**；单机那套 `saveScore` 在这里被 `battleMode` 判断绕开了。

### 4.14 这一章最容易问倒人的点

1. 如果被问到“游戏结束为什么不能直接弹对话框”，就答：这个回调来自 `GameSurfaceView` 的渲染线程，子线程碰 UI 会抛 `CalledFromWrongThreadException`，所以用 `Handler` 把分数 `post` 回主线程再弹。
2. 如果被问到“Handler 为什么要写成静态内部类 + WeakReference”，就答：非静态内部类隐式持有 Activity，消息没处理完 Activity 就回收不了；静态类 + 弱引用切断这条链，`onDestroy` 里再 `removeCallbacksAndMessages(null)` 清队列。
3. 如果被问到“为什么别的页面都要调 `UiInsets`，游戏页不调”，就答：Android 15（targetSdk 35）强制 edge-to-edge，普通页面不补 padding 会被状态栏/手势条盖住；游戏页主动隐藏系统栏、全屏自绘，顶部遮挡用 `PlayField.setTopInset(135)` 在核心层解决。
4. 如果被问到“切后台为什么只暂停不结算”，就答：玩家可能马上切回来，成绩只在死亡或主动退出时结算；`scoreSaved` 保证这两条路径不会重复写。
5. 如果被问到“`onDestroy` 里为什么先 `shutdown()` 再 `world.stop()`”，就答：先让渲染线程停下并 `join`，再拆世界和注销 `BombSubject`/`FreezeSubject` 里的观察者，避免线程还在跑的时候世界被拆、也避免静态单例一直攥着旧世界。

## 五、渲染层：主循环、绘制与贴图

> 一句话：这一章讲一个线程怎么把 25Hz 的逻辑"抻"成 60fps 的画面、`GameRenderer` 怎么一层层往上盖、`Assets` 怎么在开局前把二十来张贴图塞进内存——顺带讲清"贴图放大了 3 倍，为什么碰撞框一步都不能动"。

### 5.1 三个人各管一摊

渲染层就三个文件，378 + 410 + 289 行，加起来一千行出头，分工却特别干净：

| 文件 | 打个比方 | 管什么 |
|---|---|---|
| `GameSurfaceView.java` | 发动机 + 方向盘 | 起线程、跑循环、算时间、收触摸 |
| `GameRenderer.java` | 画笔 | 把 `GameWorld` 里的数字画到 `Canvas` 上 |
| `Assets.java` | 贴纸盒 | 开局把图片解码成 `Bitmap`，并决定"谁贴哪张、贴多大" |

装配顺序在 `GameActivity.java:110-116`：先 `Assets.load()`，再 `SpriteMetricsHolder.install(assets)`，然后 `configurePlayField()`。**资源必须在建世界之前装好**，因为核心层创建实体时就要问宽高（5.14 会细说）。

### 5.2 骨架：线程在 `surfaceCreated` 出生，在 `surfaceDestroyed` 收尸

`GameSurfaceView` 的签名是 `extends SurfaceView implements SurfaceHolder.Callback, Runnable`。一句话理解：**它是块画布（View），也是那个画画的工人（Runnable）**，`Callback` 的三个回调就是画布的"出生 / 变形 / 死亡通知"。

#### `surfaceCreated()`

```java
    @Override
    public void surfaceCreated(SurfaceHolder holder) {
        running = true;
        loopThread = new Thread(this, "aircraftwar-loop");
        loopThread.setPriority(Thread.NORM_PRIORITY + 1);
        loopThread.start();
    }
```

- **在干嘛**：Surface 一准备好，就开一条叫 `aircraftwar-loop` 的线程，把 `this`（自己，因为实现了 `Runnable`）丢进去跑。`running` 是 `volatile` 的，线程能立刻看见这个 `true`。
- **为什么这么写**：游戏循环绝不能跑在主线程——主线程一卡 5 秒系统就弹 ANR 对话框，而 `world.update()` + 画上百个对象正好要占住 CPU 好几毫秒。优先级 `+1` 是让渲染线程比普通后台线程稍微优先一点，别被日志、网络线程抢走时间片。`setKeepScreenOn(true)` 在构造函数里（`GameSurfaceView.java:81`），挂机时屏幕不会自己黑。
- **老师可能问**：为什么不用 `View.invalidate()` 定时重画？——那是把节奏交给 UI 线程，触摸、布局、对话框都能挤掉你的帧；游戏要自己控节奏，所以用 SurfaceView + 独立线程（`GameSurfaceView.java:16-22` 的类注释就是这么写的）。

#### `stopLoop()`

```java
    private void stopLoop() {
        running = false;
        Thread t = loopThread;
        loopThread = null;
        if (t != null) {
            try {
                t.join(1000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
    }
```

- **在干嘛**：举旗（`running = false`）→ 把线程引用先挪到局部变量、字段清空 → `join(1000)` 等它最多 1 秒。`surfaceDestroyed()` 里只调了这一个方法（`GameSurfaceView.java:109-111`），`shutdown()` 也是调它。
- **为什么这么写**：`join` 是在**等**，不是在**杀**。`surfaceDestroyed` 返回之后，系统才敢真正销毁 Surface 的缓冲区；如果渲染线程还活着、还在 `lockCanvas`，它拿到的就是一块已经死掉的 surface——轻则抛 `IllegalArgumentException("Surface has been released")`，重则 native 层直接崩，而且 Activity 都关了线程还在跑就是泄漏。`join` 保证"这一句返回时，工人已经收工出门"。
- **为什么不写 `join()`**：`surfaceDestroyed` 跑在主线程，无限等万一线程卡在 `lockCanvas` 里就轮到主线程 ANR 了。`join(1000)` 是"最多等你 1 秒，等不到我也要走"。
- **老师可能问**：为什么先把 `loopThread` 置 null 再 join？——切后台再回来会再走一次 `surfaceCreated` 新开线程，字段先清空，新旧线程的引用不会打架。

### 5.3 `lockCanvas` / `unlockCanvasAndPost`：两张草稿纸轮着用

#### `run()`（画布部分）

```java
            Canvas canvas = null;
            try {
                canvas = getHolder().lockCanvas();
                if (canvas != null) {
                    renderer.draw(canvas, world, alpha, paused);
                }
```

- **在干嘛**：问 Surface 借一张"后台草稿纸"（`lockCanvas`），画完在 `finally` 里 `unlockCanvasAndPost(canvas)` 交卷（`GameSurfaceView.java:186-193`）。
- **为什么这么写**：这就是**双缓冲**。Surface 背后有一个缓冲区队列，通常两块：一块正被屏幕显示（前台），一块给你画（后台）。你画的时候，屏幕上放的还是上一帧完整的画面；`unlockCanvasAndPost` 一交卷，两块互换。所以**屏幕永远不会看到画到一半的帧**——不然每一帧都能看见"背景画了、飞机还没画"的撕裂。
- **为什么每帧第一句是 `canvas.drawColor`**：后台那块纸上还留着**两帧前**的旧画（不是空白），不刷底色就会拖影。`GameRenderer.java:93` 那句 `canvas.drawColor(0xFF0E1218)` 就是擦黑板。
- **为什么 `canvas` 可能为 null**：Surface 还没准备好或尺寸为 0 时 `lockCanvas` 返回 null，所以要判空。另外 `catch (Throwable)` 把异常吞了（`GameSurfaceView.java:184-185`），因为切后台时 `lockCanvas` 抛异常属于正常流程，打日志会刷屏——代价是真正的 bug 也看不见了，这是有意的取舍。

### 5.4 心跳：40ms 一步，凭什么用 `nanoTime`

> 这一节讲"怎么写"。想把"**为什么**逻辑 25Hz、渲染 60fps，以及如果统一成 60 帧要改多少东西"
> 彻底想通，看**第八章**——那里把代价一条条算过。

#### `run()`（逻辑步部分）

```java
        long lastLogic = System.nanoTime();

        while (running) {
            long now = System.nanoTime();

            if (!paused) {
                if (now - lastLogic >= LOGIC_INTERVAL_NS) {
                    // 按固定步长累加，而不是对齐到当前帧；否则实际步长会被渲染节拍撑长
                    lastLogic += LOGIC_INTERVAL_NS;
                    if (now - lastLogic > 5 * LOGIC_INTERVAL_NS) {
                        lastLogic = now;   // 落后太多（切后台/卡顿）就丢弃欠账
                    }
                    applyInput();
                    world.update();
```

- **在干嘛**：`LOGIC_INTERVAL_NS = 40_000_000L`，即 40ms 一步（25Hz，`GameSurfaceView.java:30`）。每转一圈看表：够 40ms 就走一步逻辑，不够就先不推进，直接去渲染。
- **为什么用 `System.nanoTime()` 而不是 `currentTimeMillis()`**：`currentTimeMillis` 是墙上的挂钟，NTP 对时、用户改时间都能把它往前拨或往后拨。它一倒退，`now - lastLogic` 变成负数，逻辑就卡住不走了；它一跳 10 秒，逻辑就突然补一堆步。`nanoTime` 是**单调**的，只保证"一直往前走"，天生就是拿来量间隔的（代价是它的绝对值没有日期含义，不能拿去显示时间）。
- **为什么是 `lastLogic += 40ms` 而不是 `lastLogic = now`**：后者会把"这一圈多花的时间"算进步长里——比如每次调度多 3ms，实际步长就变成 43ms，25Hz 悄悄掉成 23Hz，而且误差**越积越多**。`+=` 相当于地铁按时刻表发车：这一班晚了，下一班还是原定时刻，平均频率严格 25Hz。
- **为什么落后太多要丢欠账**：`5 * 40ms = 200ms`。切后台一秒回来，如果老老实实补 25 步，一帧之内敌人瞬移、子弹穿人、Boss 血条乱跳。所以"睡过头了就重新排班，不补发"。注意逻辑步用的是 `if` 不是 `while`：一圈最多补一步，配合丢欠账，永远不会出现一帧跑 N 步。
- **为什么 `applyInput()` 在这儿**：触摸事件在 UI 线程产生，这里只把目标坐标写进 `volatile`/数组字段，由渲染线程在每个逻辑步开头统一应用。跨线程直接改游戏状态会一边遍历一边改，`ConcurrentModificationException` 立刻教你做人（`GameSurfaceView.java:207-208` 的注释写得很直白）。
- **`Thread.sleep` 在这儿怎么用**：循环末尾 `Thread.sleep(IDLE_SLEEP_MS)`，`IDLE_SLEEP_MS = 4`（`GameSurfaceView.java:32`）。注意它**不是"睡到下一个 40ms"**，而是每圈只睡 4ms 就回来看一眼——因为这一圈剩下的时间要拿去渲染（下面 5.5 的插值），一帧 16.7ms，40ms 里能发 2~3 帧。真正限制帧率的是 `lockCanvas` 等 vsync 的阻塞，这 4ms 只是"别空转把 CPU 吃满"的兜底。`InterruptedException` 时 `break` 出循环，线程干净退出。

### 5.5 插值：把 25 格/秒的连环画补成 60 帧

先看问题：逻辑 25Hz，位置只有每秒 25 个"台阶"；屏幕 60Hz，每秒要 60 张图。直接照着画，飞机就是一格一格"跳"的。插值就是**在两格之间凭空画出中间那张**。

#### `alpha` 的计算（`run()` 内）

```java
            double alpha = paused ? 1.0
                    : Math.min(1.0, (System.nanoTime() - lastLogic) / (double) LOGIC_INTERVAL_NS);
```

- **在干嘛**：算"离上一次逻辑推进过去了百分之几"。刚推完 ≈0，快到下一次 ≈1。`paused` 时硬给 `1.0`。
- **为什么暂停要给 1.0**：暂停时逻辑不动，就该画在"当前位置"。给 0 的话画面会**倒回上一格**，一暂停飞机往回缩一下，很怪。
- **为什么 `Math.min(1.0, ...)`**：万一这一圈拖久了，算出来 1.7，不钳住就会画到"未来"的位置，下一帧再跳回来。钳到 1 最多是多停留一帧。
- **为什么又调了一次 `nanoTime()`**：上面 `now` 是这一圈刚开始取的，中间可能已经跑完 `world.update()` 花了几毫秒。用旧值算 alpha 会偏小，画面比实际稍微滞后。这是一个很小但很典型的细节。

时间轴长这样（逻辑每 40ms 一步，屏幕每 16.7ms 一帧）：

```
逻辑步 n                     逻辑步 n+1
  |------------------------------|
 t=0ms                         t=40ms
 alpha=0                       alpha→1

屏幕帧：  t=0      t=16.7    t=33.4        t=40
          alpha≈0  alpha≈0.42 alpha≈0.83   alpha=0（新一步，prev/cur 整体前移）
          画在prev 画在42%处  画在83%处      重新从 prev 开始
```

注意一个诚实的代价：**画面永远比逻辑晚最多 40ms**（alpha≈0 时画的是这一步之前的位置）。用 40ms 的延迟换 60fps 的顺滑，值。

#### `snapshotPosition()` 与 `renderX()`

```java
    /** 在每个逻辑步开始前记下当前位置，作为这一帧插值的起点 */
    public void snapshotPosition() {
        prevLocationX = locationX;
        prevLocationY = locationY;
    }

    /** 插值后的绘制坐标，alpha 为「距上一次逻辑推进过去了多少比例」 */
    public int renderX(double alpha) {
        return (int) Math.round(prevLocationX + (locationX - prevLocationX) * alpha);
    }

    public int renderY(double alpha) {
        return (int) Math.round(prevLocationY + (locationY - prevLocationY) * alpha);
    }
```

- **在干嘛**：这几个方法其实在**核心层**（`AbstractFlyingObject.java:51-64`），不在渲染层。`snapshotPosition()` 在每步开头把当前位置存进 `prevLocationX/Y`；`renderX(alpha)` 在 `prev` 和 `location` 之间做线性插值：`prev + (cur - prev) × alpha`。alpha=0 得 prev，alpha=1 得 cur，alpha=0.42 得四成二的位置。
- **为什么实体要存两个位置**：只存一个"当前位置"的话，渲染层只知道 25 个台阶，没法造中间帧。存两个，就等于给每段路记了起点和终点，alpha 是"走了百分之几"。`GameWorld.update()` 第一句就是 `snapshotPositions()`（`GameWorld.java:194`），**先快照再移动**，顺序不能反。
- **为什么 `Math.round` 而不是直接强转**：`(int)` 是向零截断，正数范围内等于向下取整，插值点会系统性地偏小，视觉上整架飞机一直往左上"蹭"半像素，抖。四舍五入让插值点均匀落在两侧。
- **为什么碰撞不用 `renderX`**：`crash()` 读的是 `locationX/Y`（`AbstractFlyingObject.java:84-91`）。拿插值坐标去判定，会出现"看着擦过去了却中弹"或"看着撞上了却没扣血"，而且判定会比画面早半帧——手感立刻变飘。**画面可以骗人，判定不能。**

### 5.6 `draw()`：先把自己缩小到 512 宽的假想画布

#### `draw()`

```java

        canvas.drawColor(0xFF0E1218);

        float scale = canvas.getWidth() / (float) PlayField.width();
        int save = canvas.save();
        canvas.scale(scale, scale);

        drawEntities(canvas, world.getEnemyBullets(), alpha);
        drawEntities(canvas, world.getHeroBullets(), alpha);
        drawEntities(canvas, world.getEnemies(), alpha);
        drawEntities(canvas, world.getHeroes(), alpha);
```

- **在干嘛**：擦底色 → 算缩放比 → `save` 存档 → `scale` 放大整块画布 → 之后所有坐标都按 512 宽的逻辑系写，不用管手机是 1080 还是 1440。收尾 `canvas.restoreToCount(save)` 把坐标系还回去（`GameRenderer.java:115`）。
- **具体数字**：逻辑宽固定 512（`GameActivity.java:258`），1080 宽的手机 `scale ≈ 2.11`。一个 40px 的按钮画出来 84 个真实像素，52px 的背包格是 110 个真实像素，12 号字变 25px——手指点得着。战场高度按屏幕比例算：1080×2400 的手机就是 `512 × 2400 / 1080 ≈ 1138`。
- **为什么用 `save` / `restoreToCount`**：`save()` 返回的是当前"存档层数"，`restoreToCount` 一次回到那一层，比配对 `restore()` 更难写错。
- **为什么图层要分五次 `drawEntities`**：这就是画家算法——**后画的盖住先画的**。顺序定死成 道具 → 敌弹 → 我弹 → 敌机 → 英雄：道具永远在最底下（不挡子弹），英雄永远在最上面（自己不能丢）。如果全塞一个列表按添加顺序画，就会出现"英雄被道具盖住半张脸"。
- **这一版没有粒子层**：代码里没有任何 particle/爆炸特效类，"爆炸"就是贴图消失 + 音效。老师问"分层绘制"照实说这个顺序就行，别硬编一个不存在的粒子系统。
- **为什么 HUD 在实体之后、弹窗在 HUD 之后**：UI 不能被飞机盖住，弹窗要连 HUD 一起压暗。`GameRenderer.java:109-113` 用 `if / else if`，结束优先于暂停，两个遮罩不会叠在一起。

### 5.7 背景：一张 512×768 的图循环铺

#### `drawBackground()`

```java
        float scale = fieldW / bg.getWidth();
        float tileH = bg.getHeight() * scale;

        // 滚动量按插值回退一格，避免跨回绕点时背景倒跳
        double scroll = world.getBackgroundScroll() - (1.0 - alpha);
        float offset = (float) (scroll % tileH);
        if (offset < 0) {
            offset += tileH;
        }

        src.set(0, 0, bg.getWidth(), bg.getHeight());
        for (float y = offset - tileH; y < fieldH; y += tileH) {
            dst.set(0, y, fieldW, y + tileH);
            canvas.drawBitmap(bg, src, dst, bitmapPaint);
        }
```

- **在干嘛**：三张背景（`bg3` / `bg` / `bg4`，对应简单/普通/困难）都是 **512×768**，和逻辑画布同宽，所以 `scale = 1`、`tileH = 768`。战场一般 1138 高，一张不够铺满，于是从 `offset - 768` 开始，每 768 一张往下铺，一共画 2~3 张。
- **为什么从 `offset - tileH` 开始**：最上面要留一张"尾巴"，否则滚动时顶边会露出黑缝。
- **滚动有多快**：`GameWorld.java:388` 每逻辑步 `backgroundScroll += 1`，40ms 加 1 → **25 逻辑像素/秒**，在 1080 屏上约 53 真实像素/秒。慢悠悠的云层，不是"嗖嗖飞"。
- **`% tileH` 干嘛**：取模实现无缝回绕——滚到 768 就归零，因为图首尾是接得上的。Java 的 `%` 遇负数给负值，所以补了 `if (offset < 0) offset += tileH`，否则第一帧背景会跑到屏幕上方去。
- **`- (1.0 - alpha)` 是这一段的精髓**：`backgroundScroll` 没有 `prev` 字段，可它在 `update()` 末尾就 `+1` 了。alpha=0（刚推完）时应该还显示"上一格"，alpha→1 才用"这一格"，所以用"减掉还没走完的那部分"把值倒推回上一格。这样背景和实体是同步平滑的，跨回绕点也不会"倒跳一格"。
- **老师可能问**：为什么背景不用两张图交替画？——一张图循环铺更省内存，`drawBitmap` 同一个 `Bitmap` 画 3 次几乎没有额外开销。

### 5.8 实体：一个方法画完所有东西

#### `drawEntities()`

```java
    private void drawEntities(Canvas canvas, List<? extends AbstractFlyingObject> objects, double alpha) {
        for (AbstractFlyingObject object : objects) {
            if (object.notValid()) {
                continue;
            }
            Bitmap bmp = assets.bitmapFor(object);
            if (bmp == null) {
                continue;
            }
            // 绘制尺寸用逻辑碰撞框，不用贴图像素。高清图更大，缩回原尺寸后边缘才顺。
            int drawW = object.getWidth();
            int drawH = object.getHeight();
            float x = object.renderX(alpha) - drawW / 2f;
            float y = object.renderY(alpha) - drawH / 2f;
```

- **在干嘛**：遍历一类对象 → 跳过已销毁的（`vanish()` 后还在列表里等着被 `remove`）→ 问 `Assets` 要贴图 → 用 `renderX/renderY(alpha)` 拿插值位置 → 以中心点对齐算出左上角 → `drawBitmap` 把整张贴图缩放到 `drawW × drawH`（`GameRenderer.java:160-162`）。
- **为什么宽高用 `object.getWidth()` 而不是 `bmp.getWidth()`**：英雄机贴图是 **300×249**，逻辑框是 **100×83**，正好 3 倍。按贴图尺寸画，飞机立刻变成屏幕上的巨无霸，碰撞框却没变——"看着撞上了却没死"。按逻辑框画，等于把 3 倍图降采样回去，边缘反而更细腻（`bitmapPaint` 开了 `FILTER_BITMAP_FLAG`，双线性过滤，`GameRenderer.java:60`）。
- **为什么是"中心点对齐"**：全项目约定 `locationX/Y` 是实体中心，所以画的时候要往回退半个宽高。敌机、子弹、道具全靠这一条，写错了所有东西都会偏半个身位。
- **为什么不每帧 `new Rect()`**：`src` / `dst` 两个 `Rect` 是字段（`GameRenderer.java:66-67`），`Paint` 也是构造时建好 5 个复用。一帧要画上百个对象，每个都 `new` 两个 `Rect` 就是每秒上万次分配，GC 一抖画面就卡。这是"别在 draw 里分配对象"的标准做法。

### 5.13 为什么图片必须放 `drawable-nodpi`

#### `Assets` 构造函数

```java
    /** 关闭按屏幕密度缩放，保证拿到的是图片原始像素尺寸 */
    private final BitmapFactory.Options options = new BitmapFactory.Options();

    private final Map<String, Bitmap> images = new HashMap<>();
    private final Map<HeroAircraft.Skin, Bitmap> heroSkins = new EnumMap<>(HeroAircraft.Skin.class);
    private final Map<Difficulty, Bitmap> backgrounds = new EnumMap<>(Difficulty.class);

    private Assets(Context context) {
        this.resources = context.getApplicationContext().getResources();
        this.options.inScaled = false;
    }
```

- **在干嘛**：`options.inScaled = false` 关掉"按屏幕密度缩放"；图片文件全部放在 `app/src/main/res/drawable-nodpi/`（`bg.jpg`、`hero.png`、`boss.png`……）。
- **不放 `nodpi` 会怎样**：Android 会按 `drawable-*` 目录的密度限定符自动缩放。同一张 300px 宽的图，放在 `drawable-mdpi` 里，到 480dpi 的手机上会被乘 3 变成 900px——**内存直接 9 倍**，而且 `getWidth()` 拿到的数字全变，逻辑尺寸彻底失真。
- **`nodpi` 是什么意思**：告诉系统"这张图没有密度概念，别动它"。`inScaled = false` 是第二道保险，有些代码路径仍会尝试缩放。
- **代价算给你听**：一局全部贴图解码后在内存里约 **9.5MB**——Boss `900×600×4B ≈ 2.1MB`，7 张英雄机 `300×249×4B × 7 ≈ 2.0MB`，3 张背景 `512×768×4B × 3 ≈ 4.5MB`，剩下的是敌机和道具。3 倍图 = 9 倍像素面积，这 9.5MB 是拿内存换清晰度，现代手机扛得住。

- **为什么不干脆把图片缩回 100×83 存**：那样在高分屏上就是拿小图放大，糊。现在的做法是"**存 3 倍图保清晰度，画的时候缩回逻辑尺寸**"，两头都要。

### 5.15 这一章最容易问倒人的点

1. 如果问"**`surfaceDestroyed` 为什么要 `join`**"，就答：Surface 马上要被销毁，渲染线程还在 `lockCanvas` 会拿到一块死缓冲区，抛异常甚至 native 崩；`join` 是等它彻底退出，`join(1000)` 是防止主线程被卡超过 1 秒。
2. 如果问"**为什么不用 `invalidate()` 定时重画**"，就答：那是把节奏交给 UI 线程，触摸、布局、弹窗都能挤掉帧；游戏要自己控节奏，所以 `SurfaceView` + 独立线程。
3. 如果问"**插值会不会影响碰撞判定**"，就答：不会。碰撞读 `locationX/Y`，插值只作用在绘制用的 `renderX/renderY`；画面可以平滑，判定必须是真坐标。
4. 如果问"**贴图 3 倍清晰度，碰撞框为什么不变**"，就答：这组数字同时是绘制尺寸和判定尺寸，跟着变大等于重做平衡（Boss 判定会堵死半个屏幕），所以钉死在换贴图之前的老尺寸上。
5. 如果问"**为什么暂停时 `alpha` 是 1.0**"，就答：暂停时逻辑不推进，应该画在当前位置；给 0 会让画面倒回上一格，一暂停飞机往回缩一下。

## 六、皮肤页、排行榜与本地数据

> 一句话：这一章讲七款皮肤怎么解锁和切换、100 条成绩怎么塞进 SQLite 又怎么列出来，以及"昵称、开关"这种小东西为什么不住数据库。

代码分两摊：一摊是**存**（`db/` 三个文件 + `data/LocalStore.java`），一摊是**摆出来**（`ui/` 下三个界面文件）。先看存的那摊，界面只是把存好的东西念出来。

### 6.1 先认人：七个文件各管一件事

| 文件 | 身份 | 一句话职责 |
| --- | --- | --- |
| `ScoreDbHelper.java` | 建库的包工头 | 第一次打开库时建表，改结构时重建 |
| `ScoreDao.java` | 仓库管理员 | 增、删、查，SQL 都写在这 |
| `ScoreRecord.java` | 一张快递单 | 纯数据，六个字段，零逻辑 |
| `LocalStore.java` | 门后的便利贴 | 最高分、皮肤、昵称、静音开关 |
| `RankActivity.java` | 排行榜总控 | 难度标签、空状态、删除确认 |
| `RankAdapter.java` | 传送带上的托盘工 | 把一条 `ScoreRecord` 变成一行 View |
| `SkinActivity.java` | 皮肤货架 | 2 列网格、解锁判定、点一下换装 |

分工的界线很好记：**"会越积越多、要排序、要一条条删"的进 SQLite（成绩）；"就一个值、读得比写得勤"的进 SharedPreferences（设置）**。前者像档案柜，后者像冰箱门上的便利贴。

### 6.2 SQLite 三件套：建库的、管增删改查的、装一行的

`ScoreDbHelper` 的构造是私有的，只能通过 `getInstance` 拿单例（双重检查 + `volatile`），而且传进去的是 `getApplicationContext()`：Helper 内部缓存着数据库连接，活得和进程一样久，多建一个就多一条连接抢同一把文件锁；传 Activity 进来则等于把已经关掉的页面钉在内存里。`ScoreDao` 的 `writable()`/`readable()`（第 39–51 行）也做了防御——`db` 为空或 `!db.isOpen()` 时才向 Helper 要连接，所以 `close()` 之后再查会自动重开，这正是后面 `onDestroy` 里敢直接关的底气。

#### `onCreate(SQLiteDatabase)`：一辈子只跑一次的建表

```java
        String sql = "CREATE TABLE IF NOT EXISTS " + TABLE_SCORE + " ("
                + COL_ID + " INTEGER PRIMARY KEY AUTOINCREMENT, "
                + COL_NAME + " TEXT NOT NULL, "
                + COL_SCORE + " INTEGER NOT NULL, "
                + COL_DIFFICULTY + " TEXT NOT NULL, "
                + COL_CREATED_AT + " INTEGER NOT NULL, "
                + COL_SYNCED + " INTEGER NOT NULL DEFAULT 0"
                + ");";
        Log.d(TAG, "onCreate: " + sql);
        db.execSQL(sql);

        // 排行榜要按「难度 + 分数倒序」查，建个索引让排序走索引而不是全表扫描
        db.execSQL("CREATE INDEX IF NOT EXISTS idx_score_difficulty ON "
                + TABLE_SCORE + " (" + COL_DIFFICULTY + ", " + COL_SCORE + " DESC);");
    }
```

- **在干嘛**：拼一条 `CREATE TABLE` 建出 `score_list` 表，六列：`_id` 自增主键、`name` 昵称、`score` 分数、`difficulty` 难度（存 `EASY/NORMAL/HARD` 字符串）、`created_at` 毫秒时间戳、`synced` 是否已同步（0/1）。最后建一个复合索引。
- **为什么这么写**：六列是照"排行榜要显示什么"倒推的——排名不用存（查出来自己数），分数和名字必须有，难度分 tab，时间给同分排先后，`synced` 是给云端同步预留的坑位（现在只写不读，但结构先占好，以后不用改表）。`_id` 下划线开头不是随便起的，是 Android 约定；难度**存字符串**是为了 `sqlite3` 里一眼看懂，代价只有几十字节；时间存 `long` 而不是文本日期，比较快且没有时区歧义。索引顺序 `(difficulty, score DESC)` 正好对上排行榜那句 `WHERE difficulty=? ORDER BY score DESC LIMIT 100`：先按难度筛，再按分数倒序取，B-tree 里是连着的一段，不用全表扫描再临时排序。
- **老师可能问**：`onCreate` 只在装完 App 第一次跑时执行，升级 App 不会重跑；只改这里的 SQL 对已装用户完全无效。

#### `onUpgrade(SQLiteDatabase, int, int)`：改表结构的唯一入口

```java
    @Override
    public void onUpgrade(SQLiteDatabase db, int oldVersion, int newVersion) {
        Log.d(TAG, "onUpgrade: " + oldVersion + " -> " + newVersion);
        // 课程项目的数据不重要，简单起见直接重建表。
        // 真实项目应写 ALTER TABLE 做无损迁移。
        db.execSQL("DROP TABLE IF EXISTS " + TABLE_SCORE);
        onCreate(db);
    }
```

- **在干嘛**：先删表再重建。触发条件是 `DB_VERSION` 从 1 改成 2（或更大），用户下次打开 App 时系统比对版本号，自动调这里。
- **为什么这么写**：本地就几十条自己打出来的成绩，删了不心疼。真实项目得写 `ALTER TABLE ... ADD COLUMN`，或"建新表 → `INSERT INTO new SELECT ...` → 删旧表 → 改名"把老数据搬过去，否则用户升级即清档。

#### `insert(ScoreRecord)`


- **在干嘛**：把对象拆成"列名 → 值"的键值对（`ContentValues` 就是个 Map），写一行，返回新行 id，失败返回 `-1`。
- **为什么这么写**：不自己拼 `"INSERT ... VALUES ('" + name + "')"`。`ContentValues` 先把值按列类型装好，名字里带单引号（`O'Brien`）也不会把 SQL 拼断；拼字符串等于邀请用户往你的 SQL 里插话。`record.name == null ? "" : ...` 是防表上的 `NOT NULL`：昵称没设过时给空串，别让 `insert` 抛异常。`insert` 第二个参数传 `null` 是"values 为空时用哪列插 NULL 行"，这里永远不空，用不上。
- **老师可能问**：`-1` 什么时候出现？主键冲突、磁盘满、库被关都可能；调用方 `GameActivity` 拿到就 `Log.e`，不会崩。

#### `queryByDifficulty(...)`：排序交给数据库

```java
        // orderBy 直接写 "score DESC" 就是排行榜顺序（课件第 16 页原话）
        Cursor cursor = readable().query(
                ScoreDbHelper.TABLE_SCORE,
                null,
                selection,
                args,
                null,
                null,
                ScoreDbHelper.COL_SCORE + " DESC, " + ScoreDbHelper.COL_CREATED_AT + " ASC",
                String.valueOf(TOP_LIMIT));
```

- **在干嘛**：`query` 一共八个参数：表名、columns（传 `null` = 全查）、WHERE、WHERE 的实参、groupBy、having、orderBy、limit。其中三个 `null` 分别是 columns、groupBy、having；排序是 `score DESC, created_at ASC`，最后 `LIMIT 100`。前面的 `selection` 是 `COL_DIFFICULTY + " = ?"`，实参放 `args` 数组（第 87–90 行）。
- **为什么这么写**：顺序不在 Java 里 `Collections.sort`，而是交给数据库——`ORDER BY score DESC` 能吃到索引，100 条是索引里顺序扫一遍；在 Java 里排等于把几千行全读进内存再排，白费索引。同分用 `created_at ASC` 兜底，让顺序稳定，不然刷新两次同分两条会换位置，看着像 bug。`?` 是预编译占位符：数据库先把模板编译好，再把 `args` 当**纯数据**填进去，谁把昵称写成 `EASY' OR '1'='1` 都只是普通字符串，变不成 `OR` 条件，这就是防注入。
- **老师可能问**：`TOP_LIMIT` 为什么是 100？对齐任务书"云端按难度分别展示前 100 名"的口径。

#### 取数据：`Cursor` 为什么必须在 `finally` 里 close

```java
        List<ScoreRecord> result = new ArrayList<>();
        try {
            while (cursor.moveToNext()) {
                result.add(readRow(cursor));
            }
        } finally {
            // 课件明确要求：遍历取值后必须 close()
            cursor.close();
        }
        return result;
    }
```

- **在干嘛**：`moveToNext()` 把游标往下挪一行，有数据返回 `true`、到底返回 `false`；每挪一行就 `readRow` 拆出一个对象。不管中间抛不抛异常，`finally` 里都关游标。
- **为什么这么写**：`Cursor` 不是"一个 List"，它是结果集上的一个窗口（`CursorWindow`，约 2MB 共享内存）：查询并不把所有行拷给你，而是先装一窗，滑到哪儿再补。窗口用完不还，攒几十个就 `CursorWindow: Window is full` 或直接泄漏。放 `finally` 是因为 `readRow` 里的 `getColumnIndexOrThrow` 可能在列名写错时抛异常，真抛了游标照样得还。

#### `readRow(...)` 与 `ScoreRecord`：一行怎么变成对象

`readRow` 拿游标按列名找列号再取值，逐个塞进 `ScoreRecord` 的公开字段（第 115–126 行），被排行榜查询和待同步查询共用。这里的关键是 `getColumnIndexOrThrow` 的 "OrThrow"：列名打错立刻抛异常；换成 `getColumnIndex` 会默默返回 `-1`，然后 `getString(-1)` 抛一个看不出原因的错，或更糟——取到隔壁列的值。

```java
public class ScoreRecord {

    /** 主键，插入前为 0，插入后由数据库分配 */
    public long id;
    /** 玩家昵称 */
    public String name;
    /** 本局得分 */
    public int score;
    /** 难度：EASY / NORMAL / HARD */
    public String difficulty;
    /** 创建时间（毫秒时间戳） */
    public long createdAt;
```

- **在干嘛**：六个公开字段（含第 28 行的 `synced`）+ 无参构造 + 带参构造，一个方法都没有。
- **为什么这么写**：它只是三层之间的搬运箱，DAO 从 `Cursor` 填进去，Adapter 和 Activity 直接 `record.name` 读出来。公开字段省掉一堆 getter/setter，是 Android 里 bean 的常见写法。两个构造器各有用途：无参的给 `readRow`（先 `new` 再逐字段赋值），带参的给 `GameActivity`（一行就齐活）。规则判断（比如最高分）不放在这，它只装数据。

#### `deleteById(...)`，以及三个同类小方法


### 6.3 排行榜界面：ListView 的三个角色

`ListView` 只认三样：数据从哪来（Adapter）、一行长什么样（item 布局）、点了干啥（监听器）。先交代一个例外：这一页是全项目**唯一**用 XML 布局的地方（`activity_rank.xml`、`item_rank.xml`），因为课件要求演示"ListView + 单行布局"的标准流程；其他页面才是纯代码 `new View`。

`onCreate` 里先搭一个 `FrameLayout`：底层 `StarfieldView` 星空，上层 `inflate` 出来的 XML 且背景设成透明（`0x00000000`），于是星空透上来。主菜单、皮肤页、排行榜用同一套星空，切页时背景连续，不会有"点进来突然换纯色底"的割裂感。`inflate` 第三参传 `container` 且 `attachToRoot = false`，是为了让 XML 根节点的 `layout_*` 按父容器类型解析，解析完再手动 `addView`。

初始难度用 `readDifficulty()`（第 82–92 行）从 `Intent` 的 `EXTRA_DIFFICULTY` 读：`Difficulty.valueOf(extra).name()` 先校验再转回字符串（顺便挡掉 `"easy"` 这种大小写不对的值），不合法或没传就退回 `EASY`。跨页面传的是字符串，不能信；真让它抛异常，整个页面就在 `onCreate` 里崩了。

#### `getView(...)` 与 ViewHolder：全章最该看懂的一段

```java
    public View getView(int position, View convertView, ViewGroup parent) {
        ViewHolder holder;
        if (convertView == null) {
            // ① 首次：把 XML 单行布局解析成一个 View，并缓存里面的控件
            convertView = inflater.inflate(R.layout.item_rank, parent, false);
            holder = new ViewHolder();
            holder.tvRank = convertView.findViewById(R.id.tv_rank);
            holder.tvName = convertView.findViewById(R.id.tv_name);
            holder.tvScore = convertView.findViewById(R.id.tv_score);
            holder.btnDelete = convertView.findViewById(R.id.btn_delete);
            convertView.setTag(holder);
        } else {
            // ② 复用：直接取出缓存的控件，不再 findViewById
            holder = (ViewHolder) convertView.getTag();
        }
```

- **在干嘛**：`convertView` 是系统递来的"旧托盘"。为 `null` 就 `inflate` 一个，把四个控件引用装进 `ViewHolder`、挂到 `setTag(...)` 上；不为 `null` 就直接从 tag 里掏出来用。
- **为什么这么写**：`inflate` 要解析 XML、反射建控件，是这行里最贵的操作；`findViewById` 要遍历整棵子树，也不便宜。屏幕一次只显示 8~9 行，滑到第 100 条时系统不会造 100 个 View，而是把滑出去的洗干净再用——所以 `inflate` 一辈子只发生八九次，`findViewById` 也被 `ViewHolder` 压到同样次数。如果把 `findViewById` 挪到 `if` 外面，每次滑动都要找 4 遍控件，快速滑动就掉帧。
- **老师可能问**：`ViewHolder` 为什么 `static`？它不持有 Adapter/Activity 引用，`static` 才没隐式外部引用，也免得每个 holder 都拖着一个 Adapter 指针。

后面三步：**绑定数据**——排名取 `position + 1`（查询已排好序），填姓名分数；**第一名高亮**——`position == 0` 时换金色背景、排名数字换强调色（第 92–97 行）；**绑删除事件**——把当前 `record` 交给 `deleteListener`（第 99–104 行）。这里有两个必须"每次重设"的地方，都是复用的坑：

- 第一名的高亮：金色背景是设在 `View` 上的，复用后会跟着托盘跑到第 20 行，所以代码里 `setBackgroundResource` 和 `setTextColor` 每次都无条件执行，哪怕不是第一名。凡是"随位置变的外观"，一次都不能省。
- 删除按钮的监听：lambda 捕获的是**当前这一行**的 `record`，不重绑的话点第 20 行的 × 会删掉第 1 名，数据错得毫无规律、最难查。

#### `submit(...)` 与 `loadScores()`：空数据怎么显示"暂无记录"

`submit` 三句：`data.clear()`、`data.addAll(records)`、`notifyDataSetChanged()`（第 46–51 行）。保持"同一个集合、换内容"而不是 `this.data = records`，并靠 `notifyDataSetChanged` 通知 `ListView` 重绘——忘了它就会出现"库里删了、界面还在"。另外三个必答方法：`getCount` 返回 `data.size()`，`getItem`/`getItemId` 按 position 取；`getItemId` 返回的是数据库 id，但 `BaseAdapter.hasStableIds()` 默认 `false`，`ListView` 并不拿它做复用优化，写它主要是把接口补完整。

```java
    private void loadScores() {
        List<ScoreRecord> records = dao.queryByDifficulty(currentDifficulty);
        adapter.submit(records);

        boolean empty = records.isEmpty();
        emptyView.setVisibility(empty ? View.VISIBLE : View.GONE);
        listView.setVisibility(empty ? View.GONE : View.VISIBLE);

        int best = empty ? 0 : records.get(0).score;
        summaryView.setText(empty
                ? "该难度还没有记录"
                : "共 " + records.size() + " 条 · 最高 " + best + " 分（最多显示 " + ScoreDao.TOP_LIMIT + " 条）");
    }
```

- **在干嘛**：查库 → 交给 Adapter → 按有没有数据切换"列表 / 空提示"可见性 → 底部小字写条数和最高分。空提示"还没有记录\n去玩一局吧"写在 XML 里（默认 `gone`），这里只管显示隐藏。
- **为什么这么写**：`ListView` 自己不会显示空状态，塞个 `TextView` 叠在同一个 `FrameLayout` 里、二选一，是最省事的做法。`records.get(0).score` 敢直接取第一个，是因为 `orderBy` 保证了第一条就是最高分——这是隐含约定，改排序时得记得这儿。
- **删数据**：`confirmDelete` 先弹 `AlertDialog`（取消按钮传 `null`），确认后 `dao.deleteById`，`rows > 0` 才 Toast，然后重跑 `loadScores()`。不自己 `data.remove(position)`，是因为删掉第一名后所有人的名次和"最高分"那行小字都得变——重新查库全部自动正确，还只有一个数据源。`onDestroy` 里 `dao.close()` 关的是连接对象不是库文件，Helper 单例还在，下次 `writable()` 发现 `isOpen()` 为 `false` 会重新打开。

### 6.5 `LocalStore`：设置项为什么不住进数据库

`LocalStore` 管七个键名常量（`best_` 前缀 + `selected_skin`、`muted`、`music_muted`、`sound_muted`、`player_name`、`battle_server`），实际落盘 9 个键（最高分三个难度各一个），文件是 `/data/data/edu.hitsz.aircraftwar/shared_prefs/aircraftwar.xml`，只有几百字节；SQLite 库在隔壁 `databases/aircraftwar.db`。构造时 `getApplicationContext().getSharedPreferences(..., MODE_PRIVATE)`：用 ApplicationContext 是不让 `LocalStore` 攥着 Activity（它会在菜单、皮肤页、游戏页、对战页各 `new` 一次）；`MODE_PRIVATE` 表示只有本应用能读。四个页面各 `new` 一个，拿到的是**同一个**实例（系统按文件名缓存），所以不会"这边存了那边读不到"。

- **为什么不用 SQLite**：`SharedPreferences` 首次读就把整个 XML 读进内存 Map，之后 `getInt` 是内存读（微秒级）；SQLite 每次要过 JNI、解析 SQL、定位数据页（几十微秒到毫秒）。更关键的是这些设置**没有"多条"的概念**——皮肤一个、昵称一个，为它建表、写 `Cursor`、关游标纯属找活干。反过来，成绩会越打越多、要排序、要删单条，那才是 SQLite 的主场。

#### `submitScore(...)`：一个 `<=` 的细节

```java
    public boolean submitScore(Difficulty difficulty, int score) {
        if (score <= getBestScore(difficulty)) {
            return false;
        }
        prefs.edit().putInt(KEY_BEST_PREFIX + difficulty.name(), score).apply();
        return true;
    }
```

- **在干嘛**：只有**严格大于**本机该难度最高分才写入，返回"是否破纪录"。
- **为什么这么写**：用 `<=` 而不是 `<`，是让"平了最高分"不算新纪录，否则结算页每次打平都弹"新纪录！"，很吵。写盘用 `apply()` 不用 `commit()`：立刻改内存、异步刷盘，不卡 UI 线程；就一个 int，进程马上被杀也只丢这一次最高分。键名用 `best_` 前缀拼 `difficulty.name()`，加难度不用加键。
- **老师可能问**：它和 `ScoreDao.insert` 重复吗？不重复——前者只维护"本机最高分"这一个数（皮肤解锁、新纪录提示用），后者往榜单追加**每一条**成绩，哪怕比最高分低。

#### `getSelectedSkin()`：读字符串、转枚举、兜底

```java
    public HeroAircraft.Skin getSelectedSkin() {
        String name = prefs.getString(KEY_SKIN, HeroAircraft.Skin.HERO.name());
        try {
            return HeroAircraft.Skin.valueOf(name);
        } catch (IllegalArgumentException e) {
            return HeroAircraft.Skin.HERO;
        }
    }
```

- **在干嘛**：读字符串转枚举；没存过用默认"水蓝"；存了个不认识的字符串就兜底回"水蓝"。
- **为什么这么写**：`getString/putString` 这层包装的意义就是外部只看见枚举、看不见字符串，没人拿 `"HERO"` 这种魔法值到处传。`valueOf` 遇到未知名字抛异常必须接住：这方法会在 `onCreate` 路径上被调，真抛了就是启动闪退。写的那半反过来很简单，`setSelectedSkin` 一句 `putString(KEY_SKIN, skin.name()).apply()`，参数是枚举，天然写不错。
- **顺带几个**：`setPlayerName` 去空格、超 8 个字砍尾（排行榜一行姓名是"占满剩余宽度"那列，太长屏幕上全是省略号，而且这名字还要发云端/对战对手，在数据层卡死最省事）；`getPlayerName` 遇到 null 或空白返回默认"玩家"；`getTotalBest` 把三个难度的最高分加起来给菜单显示总战绩。

#### `migrateLegacyMute()`：老用户升级不能突然有声音

```java
    private void migrateLegacyMute() {
        if (prefs.contains(KEY_MUSIC_MUTED) || prefs.contains(KEY_SOUND_MUTED)) {
            return;
        }
        if (!prefs.contains(KEY_MUTED)) {
            return;
        }
        boolean legacy = prefs.getBoolean(KEY_MUTED, false);
        prefs.edit()
                .putBoolean(KEY_MUSIC_MUTED, legacy)
                .putBoolean(KEY_SOUND_MUTED, legacy)
                .remove(KEY_MUTED)
                .apply();
    }
```

- **在干嘛**：两个新键都不存在、但旧总开关 `muted` 存在时，把旧值抄给"音乐静音""音效静音"，再删旧键（删掉等于"迁移已做"的标记）。
- **为什么这么写**：最早只有一个"静音"总开关，后来拆成音乐、音效两个独立开关（BGM 是一整首循环、音效是几百次短促触发，确实有人只想关 BGM）。不管旧数据的话，老用户升级后两个新键都读不到，`getBoolean(..., false)` 返回 `false`，于是**原本静音的人一进游戏满屋音乐**——这种"升级后行为突变"是最典型的迁移 bug。两个提前 `return` 让它幂等：新键只要有一个存在，就说明迁过或用户手动设过，绝不覆盖。
- **老师可能问**：为什么在 getter 里调，不放在构造器？`LocalStore` 没有生命周期，四个页面各 `new` 一次，放在读取处是唯一能保证"读之前一定迁过"的位置；几次 `contains` 检查，开销可忽略。

### 6.6 一局结束，数据写到了两个地方

```java
    private void saveScore(int score) {
        if (scoreSaved) {
            return;
        }
        scoreSaved = true;
        newRecord = store.submitScore(difficulty, score);

        ScoreRecord record = new ScoreRecord(
                store.getPlayerName(), score, difficulty.name(), System.currentTimeMillis());
        long id = scoreDao.insert(record);
        if (id == -1) {
            Log.e("GameActivity", "排行榜写入失败: " + score);
        }
    }
```

- **在干嘛**：结算时做两件事——先 `submitScore` 更新本机最高分（返回是否破纪录，存进 `newRecord` 给结算页显示"新纪录"），再 `new` 一个 `ScoreRecord` 插进 SQLite 排行榜。`scoreSaved` 是防重入开关。
- **为什么这么写**：这份数据天然有两个用途，就得写两处：最高分是**一个数**（要快、要判"破没破纪录"、给皮肤解锁用），成绩列表是**很多行**（要排序、分难度、能删）。`scoreSaved` 防的是结算被触发两次（页面重建、按钮连点），没有它榜单里会出现两条一模一样的成绩。没让 DAO 顺手 `SELECT MAX(score)` 算最高分，是因为菜单显示最高分、皮肤解锁这些地方不该为了读一个数去开数据库。

### 6.7 这一章最容易问倒人的点

1. **如果被问"皮肤解锁为什么不用排行榜数据"**，就答：榜是所有人共享的，出现一个高手会让所有人瞬间解锁，成长曲线就没了；断网时还读不到榜，皮肤页会全灰。所以用 `LocalStore` 里**本机**该难度的历史最高分，口径和 Windows 版一致。
2. **如果被问"皮肤选完怎么把结果传回上一个页面"**，就答：没有 `setResult`，选择写进 `SharedPreferences` 这份全局存档，主菜单和游戏页各自 `new LocalStore(this)` 去读，读到的是同一份数据；Intent 回传只适合一次性的结果。
3. **如果被问"`Cursor` 忘了 `close()` 会怎样"**，就答：它占着约 2MB 的 `CursorWindow` 共享内存，攒多了会报 `Window is full` 并泄漏，所以一律 `try { 遍历 } finally { cursor.close(); }`，连 `readRow` 抛异常时也能还回去。
4. **如果被问"为什么删一条要重新查库，不直接从 List 里 remove"**，就答：删掉第一名后所有人的名次和"最高分"那行小字都要变，重新 `queryByDifficulty` 一次全部重算，只有一个数据源，也不会出现"界面删了库里还在"。
5. **如果被问"`onDestroy` 里 `dao.close()` 会不会影响别的页面"**，就答：关的是连接对象不是库文件，`ScoreDbHelper` 单例还在，下次 `writable()` 看到 `isOpen()` 为 `false` 会重新打开；真删数据得 `DROP TABLE` 或卸载 App。

## 七、联机对战：房间页、协议与对局状态机

> 一句话：这一章把“点一下创建房间”到“服务器判你赢”拆成四段——房间页收信息，`BattleClient` 通电话，`BattleProtocol` 对暗号，`BattleSession` 管流程。

先把四个角色对上号：

| 文件 | 像什么 | 管什么 | 不管什么 |
|---|---|---|---|
| `BattleRoomActivity` | 餐厅前台 | 填昵称/地址/难度/目标分，显示房间码，跳游戏页 | 不碰 WebSocket，不解析 JSON |
| `BattleClient` | 电话线 | 连、发文本、收文本、断 | 不知道 `create`/`score` 是什么意思 |
| `BattleProtocol` | 暗号本 | 消息类型、字段名、JSON 编解码 | 不保存连接状态 |
| `BattleSession` | 领班 | 建房/进房、心跳、重连、把消息翻译成回调 | 不画界面 |

一条消息的路线是：房间页 → `BattleSession` → `BattleClient` → `BattleProtocol` → 服务端；回来的消息反向走一遍，最后变成 `BattleSession.Listener` 的回调。下面的代码摘录都逐字来自源码；长方法只摘核心段，省略处在正文说明。

### 7.1 房间页：一张用代码“摆”出来的表单

`BattleRoomActivity` 一共 468 行，没有一行 XML 布局。整页就是一个纵向 `LinearLayout`，外面套 `ScrollView`，所有输入框、按钮都是 `new` 出来的。根容器在 `onCreate` 里设成深色，左右各留 24dp、顶部 40dp，右上角先塞教程按钮，最后 `setContentView(scroll)` 显示。

- **在干嘛**：搭一个深色纵向容器，再把教程按钮和各输入框按顺序 `addView` 进去。
- **为什么这么写**：项目约定界面全用代码搭，不写 XML；`ScrollView` 是给小屏和弹出键盘兜底的，内容比屏幕高时还能滑，不会把“加入房间”按钮挤没。`dp()` 把设计尺寸乘屏幕密度，保证不同手机看起来差不多大。
- **一个细节**：Android 15 起普通页面也强制 edge-to-edge，所以 `onCreate` 最后调了 `UiInsets.applySystemBars(scroll)`（`BattleRoomActivity.java:143`），给系统栏补内边距，不然右上角教程按钮会被状态栏挡住。

#### 服务器地址、状态提示和 SharedPreferences

这一段是整页最值得看的，服务器地址和状态提示上下挨着：

```java
        root.addView(label("服务器地址"));
        serverField = field(BattleProtocol.DEFAULT_SERVER_URL);
        // 记住上次填的地址：真机联机时电脑 IP 是固定的，每次重敲太烦
        String savedServer = store.getBattleServer();
        serverField.setText(savedServer != null ? savedServer : BattleProtocol.DEFAULT_SERVER_URL);
        root.addView(serverField);

        // 状态提示放在这里而不是页面底部：房间码、连接错误都从这行出，
        // 放最底下时用户在屏幕上看不到「等待对手加入…」和房间码
        statusText = new TextView(this);
        statusText.setTextSize(13);
        statusText.setTextColor(TEXT_MUTED);
        statusText.setGravity(Gravity.CENTER);
        statusText.setPadding(0, dp(12), 0, dp(4));
        root.addView(statusText);
```

- **在干嘛**：建服务器地址输入框，默认 `ws://10.0.2.2:8765`；从 `LocalStore` 读上次的地址，有就用上次的。紧接着建一行灰色状态文字，房间码、连接错误、重连提示都写它。
- **为什么状态放这里**：它不是“创建房间”专属，也不只属于“加入房间”，而是两块共用的状态条。放在服务器地址下面、两个大区块**上面**，用户不用滑到页面最底部找房间码；而且它紧挨着服务器地址，连不上时“出错了”和“你刚填的地址”在同一屏，改起来顺手。
- **具体数字**：`10.0.2.2` 是 Android 模拟器访问宿主机的固定别名；真机要改成电脑的局域网 IP，例如 `ws://192.168.1.5:8765`，端口默认 `8765`。
- **地址怎么记住**：`validServer()` 去掉首尾空格，空的话退回默认地址，非空就 `store.setBattleServer(server)`。`LocalStore` 底层是 `SharedPreferences`：`getBattleServer()` 用 `prefs.getString(KEY_BATTLE_SERVER, null)` 读，`setBattleServer()` 用 `prefs.edit().putString(...).apply()` 写，key 是 `"battle_server"`，`apply()` 异步落盘、不卡界面。下次进房间页，`onCreate` 里的 `savedServer != null ? savedServer : DEFAULT` 就把它自动带出来了。

#### 创建房间与加入房间

创建房间的核心就这几行（`BattleRoomActivity.java:156` 起）：

```java
        String server = validServer();
        int target = validTarget();
        store.setPlayerName(nickname);

        BattleSession session = BattleSession.getInstance();
        session.configure(server, nickname, BattleSession.Mode.CREATE, null, difficulty, target);
        session.setListener(sessionListener());
        statusText.setText("正在创建房间…");
        session.connect();
```

- **在干嘛**：把昵称、服务器、难度、目标分打包交给单例 `BattleSession`；`Mode.CREATE` 表示建房，房间码传 `null`（还没生成），然后挂监听、改状态文字、发起连接。
- **为什么这么写**：房间页只负责“收集参数”，连接和协议全部甩给 `BattleSession`。加入房间时只是把 `Mode.CREATE` 换成 `Mode.JOIN`、把 `null` 换成房间码，其他流程完全一样。
- **目标分怎么校验**：`validTarget()`（`BattleRoomActivity.java:282`）里 `Integer.parseInt` 失败就回退默认 5000；成功则夹在 `100` 到 `1_000_000` 之间。客户端夹一次，服务端还会再夹一次，防止有人改包传负数或十亿分。
- **难度怎么选**：三个按钮“简单/普通/困难”，用 `LinearLayout.LayoutParams(0, dp(46), 1f)` 做等宽权重，每个按钮 `setTag(d)` 存自己的 `Difficulty`；点谁就换 `difficulty`，选中的涂青色、其余恢复深色。默认是 `Difficulty.NORMAL`。

加入房间时，房间码只做“去空格 + 转大写”：

```java
        String room = roomField.getText().toString().trim().toUpperCase();
        if (room.isEmpty()) {
            Toast.makeText(this, "请输入房间码", Toast.LENGTH_SHORT).show();
            return;
        }
```

- **在干嘛**：去掉首尾空格、统一转大写；空的就弹 Toast 并中止。输入框还设了 `TYPE_TEXT_FLAG_CAP_CHARACTERS`，键盘默认大写。
- **一个容易被抓的点**：界面写着“6 位”，但客户端只校验了“非空”，没校验长度。真正的合法性是服务端拿这个码去 `rooms` 表里查，查不到就回 `{"type":"error","message":"房间不存在"}`。所以“6 位”是协议约定，不是客户端强校验。
- **加入时传什么**：`configure(server, nickname, Mode.JOIN, room, difficulty, 0)`。难度和目标分只是占位，进房后服务端在 `joined` 里把房主选的难度、目标发回来，客户端以服务端为准。

#### `sessionListener()`：房主和加入者为什么不是同一个时机开局

先看 `onJoined`：

```java
            public void onJoined(String room, String you, String opponent,
                                 Difficulty difficulty, int target) {
                if (you == null) {
                    return;
                }
                if ("A".equals(you) && (opponent == null || opponent.isEmpty())) {
                    // 房主：还没有对手，显示房间码等队友
                    statusText.setText("房间码： " + room + "\n\n等待对手加入…");
                    statusText.setTextColor(SUCCESS);
                } else {
                    // 加入者：已和对手碰头，直接开局
                    launchGame();
                }
            }
```

- **在干嘛**：服务端告诉你“你是 A 还是 B、对手叫什么”。如果你是 A 且对手为空，说明房间刚建好，显示房间码等人；否则（你是 B，或者你是 A 但对手已经来了）直接进游戏。
- **为什么这么写**：房主建完房必须停下来等，不能自己先开一局；加入者一进来双方就齐了，可以立刻开。用 `you` 槽位判断比用“我是不是房主”这种本地布尔可靠，因为断线重连后槽位还是服务端说了算。

房主什么时候开局？靠下一条 `state`（`BattleRoomActivity.java:216`）：`onState` 里只要 `oppName` 非空就 `launchGame()`。房主第一次收到 `joined` 时对手还是空的，开了就是单人局；加入者进来后服务端广播一条 `state`，这条才是“人齐了”的信号。加入者不会重复开，因为 `launchGame()` 里有 `launched` 布尔挡着。另外 `onConnected` 只把状态条改成“已连接，等待服务端应答…”，`onError` 把它标红并弹 Toast，`onDisconnected` 写“连接断开，正在重连…”——状态条上的字全部来自这几个回调。

#### `launchGame()` 和 `onDestroy()`：连接怎么从房间页带到游戏页

```java
    private void launchGame() {
        if (launched || isFinishing()) {
            return;
        }
        launched = true;
        Intent intent = new Intent(this, GameActivity.class);
        intent.putExtra(GameActivity.EXTRA_BATTLE, true);
        startActivity(intent);
        finish();
    }
```

- **在干嘛**：防重复、打上“对战局”标记、启动 `GameActivity`、结束房间页。
- **为什么这么写**：`launched` 是“已经跳过了”的闸门，防止 `onJoined` 和 `onState` 前后脚各触发一次，开出两个游戏页。`finish()` 之后房间页会走 `onDestroy`，但那里有个判断：`if (!launched) BattleSession.getInstance().close();`（`BattleRoomActivity.java:256`）——正常跳游戏时**不关连接**，把同一条 WebSocket 留给游戏页用；用户直接按返回没进游戏时，才把连接关掉，别让心跳一直挂着。
- **老师可能问**：为什么要用单例？答：房间页和游戏页是两个 Activity，连接是在房间页建的；如果游戏页再建一条，房间可能已经没了，所以用同一个 `BattleSession` 把连接带过去。

#### 右上角“使用教程”：把最容易卡住的步骤贴在出问题的地方

按钮在 `buildTutorialBar()` 里：右对齐的 `Button`，高 36dp，半透明青色描边，点了调 `showTutorial()`。弹窗用 `AlertDialog` 套一个 `ScrollView`（`BattleRoomActivity.java:361` 起），把一大段教程文字塞进 `TextView`；文字设了 `setTextIsSelectable(true)`，用户可以长按复制里面的 IP 或 `adb` 命令。

- **教程内容的顺序**：① 两台设备连同一个 WiFi；② 电脑启动服务端（双击 `start-server.bat`，或 `npm install` + `npm start`）；③ `ipconfig` 查局域网 IPv4；④ 地址改成 `ws://电脑IP:8765`（模拟器用 `10.0.2.2`）；⑤ 一人创建、一人输 6 位码加入；⑥ 各自打同一关，每秒同步分数血量。最后附了排查清单：防火墙放行 8765、服务端没起、端口写错、校园网终端隔离时用 `adb reverse tcp:8765 tcp:8765` 再填 `ws://127.0.0.1:8765`。
- **为什么这么写**：真机联机失败，绝大多数不是代码错，而是 IP 填错、防火墙没放行、两台设备不在一个网段。教程放在房间页，用户卡住的那一刻就能看，不用再翻另一份文档。

### 7.2 `BattleClient`：只负责“把话传到”的水管

`BattleClient` 只有 95 行，职责特别窄：建立 WebSocket、发文本、收文本、断开。它不知道 `create` 是什么，也不知道分数怎么算。你可以把它当成一根电话线：线通了就喊一声，线断了就通知，电话里聊什么不归它管。

#### 两个超时：5 秒连接、0 读超时

`BattleClient` 的构造函数（`BattleClient.java:40`）建了一个 OkHttp 客户端：`connectTimeout(5, TimeUnit.SECONDS)`、`readTimeout(0, TimeUnit.MILLISECONDS)`。

- **为什么连接超时是 5 秒**：`connectTimeout` 是“TCP/握手阶段最多等多久”。服务端没开、IP 写错时，5 秒就失败，用户不用干等；失败后 `BattleSession` 会走重连。
- **为什么读超时是 0**：`readTimeout(0)` 表示“连接建立后多久没数据算超时”，0 就是永不超时——WebSocket 是长连接，平时可能十几秒没有业务消息，如果设成 5 秒，正常局也会被误杀。真正判断“对面还活着”靠应用层心跳，不靠读超时。

#### `connect(String url, Listener listener)`：四个回调

```java
    public void connect(String url, Listener listener) {
        Request request = new Request.Builder().url(url).build();
        socket = client.newWebSocket(request, new WebSocketListener() {
            @Override
            public void onOpen(WebSocket webSocket, Response response) {
                listener.onOpen();
            }
```

- **在干嘛**：把 `ws://...` 包成 OkHttp 的 `Request`，调用 `newWebSocket` 异步建连；真正的回调转发给自己定义的 `Listener`。
- **为什么这么写**：OkHttp 的 `WebSocketListener` 回调不止四个，`BattleClient` 只挑 `onOpen`/`onMessage`/`onClosed`/`onFailure` 这四个转出去，自己不处理业务。这样换网络库时只改这一个文件，`BattleSession` 不用动。

四个回调各自该干什么：

| 回调 | 什么时候来 | 业务层应该做什么 |
|---|---|---|
| `onOpen` | HTTP 101 握手成功，线通了 | 发 `create`/`join`，启动心跳，更新“已连接” |
| `onMessage` | 收到一条文本帧 | 解析 JSON，按 `type` 分发 |
| `onFailure` | 连不上、握手中断、连接异常断开 | 当作掉线，走重连 |
| `onClosed` | 对方或本机正常关闭（有 close code） | 也当作掉线，但本机主动关时不要重连 |

- **为什么要区分 `onFailure` 和 `onClosed`**：`onClosed` 是“双方好好说再见”，`onFailure` 是“线突然断了”。但对 `BattleSession` 来说，两者都意味着“当前这条连接不能用了”，所以最后都汇到 `onSocketDown()`；区别只在 `closedByUser` 这个标志——本机主动 `close()` 时不许重连。
- **`send()` 的小坑**：`socket.send(text)` 的布尔返回值被忽略了。OkHttp 在发送队列满或连接已关闭时会返回 `false`，这里不会重试、不会报错，消息就悄悄丢了。对“每秒上报一次”的比分来说可以忍，下一拍会补上；但如果做实时射击，这就得处理。
- **`close()` 的写法**：先把 `socket` 存到局部变量、把字段置 `null`，再调 `s.close(1000, "client close")`，外面包 `try/catch`。先置空是防止关闭过程中又有人调 `send()`；`1000` 是 WebSocket 的正常关闭码。

#### 为什么回调不能碰 UI

这四个回调跑在 OkHttp 的**后台线程**，不是 Android 主线程。在后台线程里 `TextView.setText()` 轻则日志报警，重则直接抛 `CalledFromWrongThreadException`。`BattleSession` 的做法是统一 `handler.post(...)` 回主线程（`BattleSession.java:160` 起）：

```java
            @Override
            public void onOpen() {
                handler.post(BattleSession.this::onOpenOnMain);
            }

            @Override
            public void onMessage(String text) {
                handler.post(() -> dispatch(text));
            }
```

- **为什么用 `Handler` 而不是 `runOnUiThread`**：`BattleSession` 是个普通 Java 对象，不是 Activity，也不是 View，拿不到 `runOnUiThread`；`new Handler(Looper.getMainLooper())` 只依赖 Android 主线程 Looper，跟界面解耦。所有会话状态（`joined`、`over`、分数）都在主线程改，就不会出现“后台线程改一半、主线程读一半”的脏数据。
- **`isOpen()` 也有个小坑**：它只返回 `socket != null`（`BattleClient.java:74`），不代表 TCP 还活着。连接失败后、`onSocketDown` 把 `client` 置空之前，`socket` 仍然非空，`isOpen()` 会返回 `true`。所以真正判断掉线不能只靠它，要靠 `onFailure`/`onClosed` 和心跳超时。

### 7.3 `BattleProtocol`：两个人共同的暗号本

这个类只有 123 行，但它是客户端和服务端“能聊起来”的基础。所有消息都是 **JSON over WebSocket**。类里定义了 11 个 `TYPE_*` 常量（`BattleProtocol.java:39` 起），客户端和服务端都只认这些字符串。为什么单独抽一个类？因为消息类型有 11 种，如果到处写 `"joined"`、`"state"`，哪天打错一个字母，编译器不会管，运行时才莫名其妙不响应。

- **为什么用常量**：`switch (type)` 里用常量，拼错会在编译期报错；服务端 `server.js` 的 `case 'create'` 也照着这套名字写，两边对得上。另一个好处是改协议只改一处，不用全局搜索字符串。
- **一个取舍**：字段名（`"room"`、`"score"`）并没有全部抽成常量，`str(msg, "room")` 里还是裸字符串；`room` 在 `join`/`score`/`leave` 里都出现，也没为它单独建常量。类型值是分支入口、重复得多，所以收口；字段名再包一层常量收益不大。这是取舍，不是完美。

每种消息长什么样（字段名和源码一致，实际发送时由 Gson 序列化）：

| 消息 | 方向 | 关键字段 | 大概长这样 |
|---|---|---|---|
| `create` | 客户端 → 服务端 | `name`、`difficulty`、`target` | `{"type":"create","name":"玩家A","difficulty":"NORMAL","target":5000}` |
| `join` | 客户端 → 服务端 | `room`、`name` | `{"type":"join","room":"A3F9K2","name":"玩家B"}` |
| `score` | 客户端 → 服务端 | `room`、`score`、`hp` | `{"type":"score","room":"A3F9K2","score":1200,"hp":900}` |
| `leave` | 客户端 → 服务端 | `room` | `{"type":"leave","room":"A3F9K2"}` |
| `ping` | 客户端 → 服务端 | 无 | `{"type":"ping"}` |
| `joined` | 服务端 → 客户端 | `room`、`you`、`opponent`、`difficulty`、`target` | `{"type":"joined","room":"A3F9K2","you":"A","opponent":"玩家B","difficulty":"NORMAL","target":5000}` |
| `state` | 服务端 → 客户端 | `a`、`b`，各含 `name`/`score`/`hp` | `{"type":"state","a":{"name":"玩家A","score":1200,"hp":900},"b":{"name":"玩家B","score":950,"hp":1000}}` |
| `over` | 服务端 → 客户端 | `winner`、`scoreA`、`scoreB`、`reason` | `{"type":"over","winner":"A","scoreA":5000,"scoreB":4210,"reason":"达到目标分"}` |
| `opponent_left` | 服务端 → 客户端 | 无 | `{"type":"opponent_left"}` |
| `pong` | 服务端 → 客户端 | 无 | `{"type":"pong"}` |
| `error` | 服务端 → 客户端 | `message` | `{"type":"error","message":"房间不存在"}` |

- **`you` 是什么**：不是玩家名字，是槽位 `"A"` 或 `"B"`。房主固定 A，加入者固定 B；断线重连也靠“同一个名字 + 这个槽位还空着”认人。
- **`winner` 可能是 `null`**：双方同分时服务端发 `winner:null`，客户端不能拿它直接 `equals` 出胜负，后面会讲怎么处理平局。
- **为什么不用 11 个 DTO 类**：消息形状不固定，`joined` 有 5 个字段、`ping` 一个字段都没有；用 `JsonObject` 加几个取值辅助方法，代码量小、加字段不用改类。代价是编译期不知道字段对不对，只能靠协议表和测试兜底。

#### 房间码和容错解析

`generateRoomCode()` 从 32 个字符里随机抽 6 个，字符集是 `"ABCDEFGHJKLMNPQRSTUVWXYZ23456789"`，去掉了容易看混的 `O/0/I/1`；`32^6 ≈ 10.7 亿` 种组合。不过客户端这个方法目前**没有调用点**，真正发码的是服务端 `server.js` 的 `generateCode()`（带查重）；老师问起就照实说“发码权在服务端，客户端这个是备用/冗余方法”。

解析则走“宁可跳过，不许崩”的路线（`BattleProtocol.java:92`）：

```java
    public static JsonObject parse(String json) {
        try {
            return JsonParser.parseString(json).getAsJsonObject();
        } catch (Exception e) {
            return new JsonObject();
        }
    }
```

- **在干嘛**：把文本解析成 `JsonObject`；解析失败（不是 JSON、不是对象、空串）就返回空对象，不抛异常。
- **为什么这么写**：网络消息可能因为版本不一致、服务端 bug、代理插了一行字而变成坏数据。如果这里直接抛，`onMessage` 回调会炸，整条会话可能挂掉；返回空对象后，`typeOf()` 取不到 `type`，`dispatch()` 里 `type.isEmpty()` 直接 return，相当于“这条不认识，跳过”。
- **代价**：错误被吞了，排查时看不到“哪条消息坏了”；更稳的做法是 `Log.w` 打一条日志。
- **配套方法**：`typeOf()` 取 `type`（没有返回空串），`str()` 取字符串（缺失/`null` 返回 `null`），`integer()` 取整数（缺失/非法返回默认值）。上层不用到处写 `has()`/`isJsonNull()`，也不怕服务端少发字段。

### 7.4 `BattleSession`：一条连接的五个阶段

`BattleSession` 是这四个文件里最复杂的，491 行。它把“连接、建房/进房、心跳、重连、收消息、判胜负”全管了。先记住一句话：**它是单例，房间页建好的连接要原封不动交给游戏页**。如果每个页面各建一条，进游戏的一瞬间就会断线重连，房间可能直接没了。

它没有用 `enum`，而是用几个布尔量组合：

```text
configure() ──→ [未连接] joined=false, over=false
connect()/open() ──→ [连接中] 等 onOpen / joined
handleJoined() ──→ [已进房] joined=true, mySlot=A/B
GameActivity 开局 + 每秒 reportScore() ──→ [对局中] joined && !over
handleOver()/handleOpponentLeft()/leave()/close() ──→ [结束] over=true

旁支：onSocketDown() ──→ [掉线] down=true ──3 秒后──→ [连接中]
```

- **未连接**：`configure()` 刚调完，参数填好了，但还没连。
- **连接中**：`connect()` 调了 `open()`，WebSocket 正在握手；此时 `joined` 还是 `false`。
- **已进房**：收到 `joined`，`joined=true`，知道自己 A/B、对手是谁；房主停在这里显示房间码。
- **对局中**：游戏页已启动，每秒上报；代码里没有单独的 `playing` 标志，靠 `joined && !over` 推断。
- **结束**：收到 `over` 或 `opponent_left`，或者本机 `leave()`/`close()`，`over=true`。
- **掉线**：不算独立阶段，是旁支；`down=true` 时禁止重复处理，重连成功后回到“连接中/已进房”。

关键标志在 `BattleSession.java:99` 起：

```java
    private boolean joined = false;
    private boolean over = false;
    private boolean closedByUser = false;
    private boolean down = false;             // 是否已进入「掉线」状态（去重 onClosed/onFailure）
    private boolean reconnectScheduled = false;
    private int missedPongs = 0;
    private int reconnectCount = 0;
```

- **`joined`**：进过房没有。没进房时 `reportScore()` 直接丢掉。
- **`over`**：这一局结束了没有。结束、主动退出、`close()` 都会置 `true`，用来停心跳、停重连、停上报。
- **`closedByUser`**：是不是本机主动关的；主动关不许自动重连。
- **`down`**：是不是已经处理过“掉线”了。`onFailure`、`onClosed`、心跳超时可能同时/先后到达，没有这个闸门会安排三次重连。
- **`reconnectScheduled`**：预留给“是否已安排重连”，但目前只被赋值、没有被读取，真正防重入的是 `down`。
- **`missedPongs` / `reconnectCount`**：前者数“发了几次 ping 还没等到 pong”，后者数“连续失败了几次”。

#### 开局的清理：`configure()` / `connect()` / `onOpenOnMain()`

`configure()`（`BattleSession.java:122`）做两件事：先 `reset()`，再保存服务器地址、昵称、模式、房间码、难度、目标分。`reset()` 会关旧 socket、`handler.removeCallbacksAndMessages(null)` 撤掉心跳和重连任务、把所有布尔量清零。上一局可能还留着 `joined=true`、`over=true`、一个 3 秒后要执行的重连任务；不擦干净就开新局，旧任务会在新局里“诈尸”。

`connect()`（`BattleSession.java:139`）先检查地址，再把 `closedByUser`、`over`、`down`、`reconnectCount`、`missedPongs` 全部复位，然后调 `open()`。注意它没有把 `joined` 置 `false`——`joined` 是给断线重连用的，重连时还要带着原房间码回去，不能清。`open()` 里如果旧 `client` 还在就先 `close()`，再 `new BattleClient()` 连新线。

`onOpenOnMain()`（`BattleSession.java:184`）在连接成功后做三件事：

```java
    private void onOpenOnMain() {
        down = false;
        reconnectCount = 0;
        resendCurrentRequest();
        listener.onConnected();
        startHeartbeat();
    }
```

- **在干嘛**：清掉“掉线”标记和连续失败计数；补发建房/进房请求；通知界面“已连接”；启动心跳。
- **为什么在这里把 `reconnectCount` 清零**：`MAX_RECONNECT` 限制的是“连续失败次数”，不是“一辈子只能重连五次”。只要成功打开过一次，计数就归零；下次再掉线，又给你五次机会。反过来说，如果网络一直“连上就断”，它会一直循环，不会触发上限。
- **`resendCurrentRequest()` 的分支**：如果 `joined && room != null`，发 `join`（重连回原房间）；否则按 `mode` 发 `create` 或 `join`。重连不能发 `create`，否则会新建一个房间。边界情况：如果 `create` 已到服务端、但 `joined` 还没回来就断了，重连会再发一次 `create`，理论上可能多出一个房间（旧房间靠 TTL 清理）。`sendCreate()`/`sendJoin()` 本身只是 `new JsonObject()` + `addProperty`，最后都走 `send()`：先检查 `isOpen()`，再把 `BattleProtocol.encode()` 的结果交给 `client.send()`。

#### `reportScore(int score, int hp)`：每秒一次的上报

```java
    public void reportScore(int score, int hp) {
        if (!joined || over || client == null || !client.isOpen()) {
            return;
        }
        JsonObject o = new JsonObject();
        o.addProperty("type", BattleProtocol.TYPE_SCORE);
        o.addProperty("room", room);
        o.addProperty("score", score);
        o.addProperty("hp", hp);
        send(o);
    }
```

- **在干嘛**：四个条件全满足才发：进过房、没结束、有客户端、连接还开着。然后拼一条 `score` 消息，带上房间码、分数、血量。
- **为什么先判断再拼 JSON**：没进房时房间码可能还是 `null`，发出去服务端也不认；结束后再发，服务端已经 `room.ended`，纯属浪费。断线重连期间 `client` 为空或 `isOpen()` 不可靠，也直接丢，等连上后的下一拍再补。

谁在每秒调它？不是 `BattleSession` 自己定时，而是游戏页的 `GameActivity.startBattleReporting()`。方法体从 `GameActivity.java:397` 开始：

```java
        reporterHandler = new Handler(Looper.getMainLooper());
        reporter = new Runnable() {
            @Override
            public void run() {
                if (session != null && world != null) {
                    int hp = world.isGameOver() ? 0 : world.getHero(0).getHp();
                    session.reportScore(world.totalScore(), hp);
                }
                if (reporterHandler != null && reporter != null) {
                    reporterHandler.postDelayed(this, 1000);
                }
            }
        };
        reporterHandler.post(reporter);
    }
```

- **在干嘛**：在主线程建一个 `Handler`，用一个 `Runnable` 上报；`run()` 最后又 `postDelayed(this, 1000)`，把自己一秒后再次排进队列，形成循环。第一次是 `post`，所以进游戏立刻报一次，之后大约每 1000ms 一次。
- **为什么用主线程 `Handler`**：`world` 的分数和血量是游戏状态，主线程读最安全；`reportScore()` 只是拼 JSON 并调 `send()`，`send()` 内部是 OkHttp 的异步队列，不会阻塞主线程。用 `Handler` 还能在 `onDestroy` 里 `removeCallbacks` 一把停掉。
- **具体数字**：1 秒 1 次，两个人就是 2 条/秒；按 60fps 上报就是 120 条/秒，完全没必要。
- **什么时候停**：`onBattleOver()`、本机阵亡 `onBattleLocalGameOver()`、`onDestroy()` 都会调 `stopBattleReporting()`。本机阵亡时还会手动补一条 `reportScore(score, 0)`，把“我已经死了”告诉服务端，然后等对手打完；不是自己死了就立刻判输。

#### `dispatch()`：消息分诊

`dispatch()`（`BattleSession.java:260`）先 `parse()`，再取 `type`；取不到就丢弃。后面是一个 `switch`：

| `type` | 交给谁 | 干什么 |
|---|---|---|
| `joined` | `handleJoined()` | 记录房间、槽位、对手、难度、目标分 |
| `state` | `handleState()` | 更新双方分数/血量，回调界面 |
| `over` | `handleOver()` | 记录胜负，停心跳，弹结算 |
| `opponent_left` | `handleOpponentLeft()` | 对手离开，判本机赢 |
| `pong` | 直接处理 | `missedPongs = 0` |
| `error` | `listener.onError()` | 把服务端的错误文案交给界面 |
| 其他 | `default` | 忽略，保证向后兼容 |

所有网络消息都从这一个口进来，新增消息类型只改这个 `switch`，不用在 `onMessage` 里堆 `if`。坏消息在 `parse()` 已经变成空对象，这里再挡一次空 `type`，两层保险。

#### `handleJoined()` / `handleState()`：槽位怎么变成“我”

进房成功时（`BattleSession.java:290` 起）：

```java
    private void handleJoined(JsonObject msg) {
        joined = true;
        room = BattleProtocol.str(msg, "room");
        mySlot = BattleProtocol.str(msg, "you");
        opponentName = BattleProtocol.str(msg, "opponent");
        String diff = BattleProtocol.str(msg, "difficulty");
        if (diff != null) {
            try {
                difficulty = Difficulty.valueOf(diff);
            } catch (IllegalArgumentException ignored) {
                // 服务端返回了未知难度，沿用本地值
            }
        }
        target = BattleProtocol.integer(msg, "target", target);
```

- **在干嘛**：把 `joined` 置真，记下服务端分配的 `room`、`you`（A/B）、`opponent`；如果服务端回了难度，就用它覆盖本地难度；目标分也以服务端为准；最后（省略的几行）把 `youName`/`oppName` 初始化好，回调 `listener.onJoined(...)`。
- **为什么难度要以服务端为准**：加入房间的人本地可能随便选了一个难度，但一局必须两人同难度。房主建房时把难度发给服务端，服务端在 `joined` 里原样发回，加入者用这个值覆盖自己本地的选择。
- **为什么 `Difficulty.valueOf` 要包 `try/catch`**：服务端可能升级、发了个客户端不认识的难度名。捕获 `IllegalArgumentException` 后沿用本地值，至少还能进房。
- **`target` 的默认值**：`integer(msg, "target", target)` 的第三个参数是“缺字段时用当前值”，不是 0。

每次服务端广播状态时（`BattleSession.java:309` 起）：

```java
    private void handleState(JsonObject msg) {
        JsonObject a = msg.has("a") && !msg.get("a").isJsonNull()
                ? msg.getAsJsonObject("a") : new JsonObject();
        JsonObject b = msg.has("b") && !msg.get("b").isJsonNull()
                ? msg.getAsJsonObject("b") : new JsonObject();
        JsonObject mine = "B".equals(mySlot) ? b : a;
        JsonObject opp = "B".equals(mySlot) ? a : b;

        youName = BattleProtocol.str(mine, "name");
        youScore = BattleProtocol.integer(mine, "score", 0);
        youHp = BattleProtocol.integer(mine, "hp", 0);
        oppName = BattleProtocol.str(opp, "name");
        oppScore = BattleProtocol.integer(opp, "score", 0);
        oppHp = BattleProtocol.integer(opp, "hp", 0);
```

- **在干嘛**：服务端固定发 `a`、`b` 两个槽位；客户端根据自己是 A 还是 B，决定 `a` 是“我”还是“对手”。然后分别取出名字、分数、血量，存到 `you*`/`opp*` 字段，最后回调 `listener.onState(...)`。
- **为什么这么绕**：服务端不知道“你”是谁，它只认槽位；同一份 `state` 广播给两个人，A 看到 `a` 是自己，B 看到 `b` 是自己。如果客户端不转这一下，B 会把 A 的分数当成自己的，界面直接反了。
- **具体例子**：本机 `mySlot="B"`，收到 `a={"name":"玩家A","score":1200}`、`b={"name":"玩家B","score":950}`；`mine` 取 `b`，所以“我”是 950 分，“对手”是 1200 分。
- **容错**：`a` 或 `b` 缺失/为 `null` 时用空对象，后面的 `integer(..., 0)` 会给出 0，不会空指针。`mySlot` 还没确定时（理论上 `joined` 一定先到），代码按 A 处理。

#### `handleOver()`：服务端说结束了，客户端才敢结束

```java
    private void handleOver(JsonObject msg) {
        over = true;
        String winner = BattleProtocol.str(msg, "winner");
        int scoreA = BattleProtocol.integer(msg, "scoreA", 0);
        int scoreB = BattleProtocol.integer(msg, "scoreB", 0);
        boolean win = mySlot != null && mySlot.equals(winner);
        stopHeartbeat();
        listener.onOver(win, scoreA, scoreB, BattleProtocol.str(msg, "reason"));
    }
```

- **在干嘛**：置 `over=true`，取 `winner` 和两边分数；如果 `winner` 等于自己的槽位就是赢；停心跳；把结果交给界面。
- **为什么胜负由服务端判**：客户端只负责上报，不负责宣布“我赢了”。如果客户端自己算，改个包就能场场赢；服务端收到 `score >= target` 才发 `over`，两边收到的是同一条权威结果。
- **平局怎么处理**：服务端同分时发 `winner:null`，`mySlot.equals(null)` 是 `false`，所以 `win=false`；但 `GameActivity.onBattleOver()` 还会判断 `scoreA == scoreB`，相等就显示“平局”。光看 `win` 会把平局误报成输。
- **界面怎么收尾**：`onOver` → `GameActivity.onBattleOver()`（`GameActivity.java:448`）停上报、按槽位换算“我的/对手的”分数、弹不可取消的结算框；点“返回”后 `finish()` → `onDestroy()` → `session.leave()`。对手离开则走 `handleOpponentLeft()`，游戏页显示“对手掉线或退出，你获胜！”。

#### 心跳与断线重连：15 秒、2 次、3 秒、5 次、60 秒

心跳的核心在 `BattleSession.java:345` 起：

```java
            if (closedByUser || over) {
                return;
            }
            if (client == null || !client.isOpen()) {
                onSocketDown();
                return;
            }
            sendPing();
            missedPongs++;
            if (missedPongs >= MAX_MISSED_PONGS) {
                missedPongs = 0;
                onSocketDown();
            } else {
                handler.postDelayed(this, HEARTBEAT_INTERVAL_MS);
            }
```

- **在干嘛**：每次心跳先检查“用户关了没/局结束了没”，再检查连接；没问题就发 `ping`，把 `missedPongs` 加一；如果已经累计 2 次没收到 `pong`，清零并走掉线；否则 15 秒后再来一次。
- **具体时间线**：`startHeartbeat()` 在 `onOpen` 时排第一次，15 秒后发 `ping #1`，`missedPongs=1`；如果 `pong` 回来，`dispatch()` 把 `missedPongs` 清 0。假设一直没 `pong`，30 秒时发 `ping #2`，`missedPongs=2`，立刻 `onSocketDown()`。所以最坏大约 **30 秒**发现“对面没动静”。
- **为什么是 15 秒 / 2 次**：15 秒一次，一分钟才 4 条 `ping`，开销可以忽略；允许丢 1 次 `pong`，避免网络抖一下就误判。服务端那边也有 30 秒没消息判掉线的逻辑，两边是双保险。

掉线后（`BattleSession.java:376` 起）：

```java
    private void onSocketDown() {
        if (down || closedByUser || over) {
            return;
        }
        down = true;
        if (client != null) {
            client.close();
            client = null;
        }
        stopHeartbeat();
        listener.onDisconnected();
```

- **在干嘛**：如果已经处理过、用户主动关了、或者局已经结束，直接返回；否则标记 `down=true`，关掉旧连接、停心跳、通知界面“连接断开，正在重连…”。
- **为什么需要 `down` 去重**：一次断网可能同时触发 `onFailure` 和 `onClosed`，心跳也可能在下一拍发现连接不可用；没有 `down`，会安排三次重连，服务端会看到三个同名连接。
- **后面的重连策略**（省略的几行）：如果 `reconnectCount >= MAX_RECONNECT`（5 次），回调 `onError("连接失败，已放弃重连")` 并返回；否则 `reconnectCount++`，`handler.postDelayed(reconnectTask, 3000)`。`reconnectTask` 到点后先看 `closedByUser`/`over`，没关就 `open()` 重新拨号。
- **具体数字**：每次失败后等 3 秒再试，最多 5 次；算上每次连接最多 5 秒的超时，从掉线到放弃**至少约 15 秒，实际可能接近 30～40 秒**。服务端保留房间 **60 秒**，所以前几次重连通常能把局救回来；但客户端大约 30～40 秒就放弃了，真断到 60 秒，服务端也早把对手判赢了。
- **重连成功后怎么恢复**：`open()` → `onOpenOnMain()` → `resendCurrentRequest()`，因为 `joined=true` 且有 `room`，会发 `join`；服务端 `resume()` 补发当前 `state`，客户端 `handleState()` 把双方分数/血量追回来。这期间游戏页还在跑，下一拍 `reportScore()` 也会继续上报。

#### `close()` / `leave()`：主动退房和被动掉线不是一回事

`close()`（`BattleSession.java:411`）先设 `closedByUser = true`，停心跳、撤掉待执行的重连任务、关 socket、清空引用，最后 `joined=false`、`over=true`。先设 `closedByUser` 很关键：`client.close()` 会触发 `BattleClient` 的 `onClosed`，那个回调会 `post(onSocketDown)`；如果标志不是先设好，`onSocketDown` 会以为“意外掉线”，又给你安排重连——用户明明已经退出，后台还在拨号。

`leave()` 则先发一条 `{"type":"leave","room":...}` 给服务端，再 `close()`。服务端收到 `leave` 会**立刻**给对手发 `opponent_left`，对手直接获胜，不等 60 秒宽限期；普通掉线要等 60 秒。所以“主动退房”和“网络断了”在服务端是两种处理。

整局串起来就是：创建/加入 → `joined` → 双方进游戏（`setupBattle()` 换监听、启动每秒上报）→ 服务端 `over` → 结算；中途掉线则 3 秒 × 5 次重连，服务端保留 60 秒。

### 7.5 这一章最容易问倒人的点

- **如果被问到“网络回调为什么不能直接 `setText`”**，就答：`onOpen`/`onMessage` 跑在 OkHttp 的后台线程，Android 的 View 只能在主线程碰；`BattleSession` 用绑定主 Looper 的 `Handler` 统一 `post` 回去，所以状态和界面都只在主线程改。
- **如果被问到“为什么胜负要服务端判”**，就答：客户端只上报分数，自己宣布赢就可以改包作弊；服务端收到 `score >= target` 才发 `over`，两个人收到同一条结果，客户端只负责显示。
- **如果被问到“心跳为什么是 15 秒、2 次”**，就答：15 秒一次开销很小，允许丢 1 个 `pong` 防网络抖动，连续 2 次没回大约 30 秒判掉线；服务端也有 30 秒超时，两边互为保险。
- **如果被问到“客户端 5 次重连、服务端却保留 60 秒，是不是对不上”**，就答：客户端 5 次是防止无限拨号，按 3 秒间隔至少约 15 秒、加上连接超时更久；60 秒是服务端给“切后台/短暂断网”留的宽限，两者目的不同，但客户端放弃得确实比服务端早，这是可以改进的地方。
- **如果被问到“为什么不用 `enum` 表示状态”**，就答：现在状态少，用 `joined`/`over`/`down` 几个布尔组合就够，配合 `down` 还能挡住重复的异步回调；缺点是可读性一般，状态一多就该换成显式状态机。

## 八、为什么逻辑 25Hz、渲染 60fps —— 专治"觉得插值太复杂"

> 一句话：**逻辑决定"游戏跑多快"，渲染决定"画面多顺"**。这两件事本来就不该绑在一起，
> 绑在一起就会变成"手机卡的时候游戏跟着变慢"。至于插值，全部代码只有 12 行。

这一章是为一个人写的：他觉得"渲染和逻辑帧不一样"很难理解，想把两者统一成 60 帧，
顺便把插值删掉。我们先把它拆开看，最后再算一笔账。

### 8.1 先认清两个数字

代码里就两行常数（`GameSurfaceView.java`）：

```java
private static final long LOGIC_INTERVAL_NS = 40_000_000L;
private static final long IDLE_SLEEP_MS = 4L;
```

上面这两行分别在第 30、32 行。第一行是 40ms（25Hz），第二行是每转一圈睡 4ms
（不睡的话这个 `while` 会把一个 CPU 核吃满）。

- **逻辑 40ms 一步 = 25Hz**（游戏规则每秒算 25 次）
- **渲染尽量快**，手机上一般是 60 / 90 / 120Hz（画面每秒画 60~120 次）

两个数字不一样，是因为它们回答的是两个不同的问题：

| | 逻辑 | 渲染 |
|---|---|---|
| 回答什么问题 | 敌机这一瞬间在哪、有没有撞上、该不该加分 | 这一帧画面该长什么样 |
| 快一点的好处 | 几乎没有（25Hz 已经够精确） | 明显：越接近屏幕刷新率越顺 |
| 快一点的代价 | 吃 CPU、发热、耗电 | 吃 CPU、掉帧 |
| 能不能变 | **不能随便变**（会改手感与平衡） | 越快越好 |

### 8.2 三个方案摆一起，为什么选第三个

**方案 A：逻辑跟着渲染走（也就是你说的"统一 60 帧"）**

```
理想情况：手机 60fps → 逻辑 60 次/秒 → 正常
糟糕情况：手机只有 45fps → 逻辑 45 次/秒 → 全场慢 25%
```

这就是致命点：**游戏速度变成了"取决于这台手机有多快"**。
低端机同一关卡敌机飞得更慢，旗舰机飞得更快，排行榜上不同手机的人根本没法比。
你在队友的旧手机上测和在自己手机测，难度都不一样。

**方案 B：逻辑 25Hz，渲染也 25Hz（不插值）**

```
每 40ms 画一张，每秒 25 张 → 敌机是一格一格"跳"过去的
```

25 张/秒在手机屏幕上肉眼可见地不流畅，像 PPT。插值就是为了消灭这个"跳"。

**方案 C：本方案 = 逻辑 25Hz（方案 B 的稳定性）+ 渲染 60~120Hz（方案 A 的顺滑）**

```
逻辑时间轴：  |----40ms----|----40ms----|----40ms----|
逻辑位置：    x=100       x=110       x=120
渲染时间轴：  |--16ms--|--16ms--|--16ms--|--16ms--|--16ms--|
画在哪：      100     104     108     112     116     120
              ↑ alpha=0  ↑0.4  ↑0.8  ↑0.2  ↑0.6  ↑1.0
```

**碰撞、计分、判定全部用真实的 `locationX/Y`（100、110、120），
只有"画在哪个像素"用插值算出来的中间值。** 所以画面顺滑，但规则一点没变。

### 8.3 循环到底怎么写的（逐行）

真正的代码（`GameSurfaceView.java:150` 起）：

```java
long lastLogic = System.nanoTime();
while (running) {
    long now = System.nanoTime();
    if (!paused) {
        if (now - lastLogic >= LOGIC_INTERVAL_NS) {
            lastLogic += LOGIC_INTERVAL_NS;
            if (now - lastLogic > 5 * LOGIC_INTERVAL_NS) {
                lastLogic = now;
            }
            applyInput();
            world.update();
```

三行不起眼但都是坑：

**① `if (now - lastLogic >= LOGIC_INTERVAL_NS)` —— 用"比较"而不是"睡 40ms"**

为什么不直接 `Thread.sleep(40)`？因为渲染也要在这个循环里做。
如果睡 40ms，渲染也只能 25fps，就退化成了方案 B。所以是"渲染每轮都做，逻辑只在够 40ms 时才推一步"。

**② `lastLogic += LOGIC_INTERVAL_NS` —— 累加，不是 `lastLogic = now`**

这是全章最关键的一行，注释也写了原因：

```java
// 按固定步长累加，而不是对齐到当前帧；否则实际步长会被渲染节拍撑长
```

假设渲染一帧要 17ms，而逻辑要 40ms：

```
用 lastLogic = now：  实际步长 = 17, 17, 17 → 累计够 40 才推，但起点被拉歪
                      推完之后 lastLogic 落在"帧边界"上，误差一点点累积
用 += 40ms：          逻辑时间轴是 40 / 80 / 120 / 160…，永远精确
                      多出来的 0.5ms 留给下一轮，不会丢也不会攒
```

一句话：**逻辑时间轴必须自己走，不能被渲染的节拍拖着走。**

**③ `if (now - lastLogic > 5 * LOGIC_INTERVAL_NS) lastLogic = now;` —— 欠债太多就赖掉**

切后台回来、或者手机卡了一下，可能已经过了 2 秒。如果老老实实补 50 步，
玩家会看到飞机"瞬移"，而且这 50 步在一帧里算完会造成更严重的卡顿（死亡螺旋）。
所以超过 5 步（200ms）就直接认栽，从当前时间重新开始。

### 8.4 插值到底有多少行代码？12 行

很多人以为插值是一座大山。实际上全项目就这几行：

`AbstractFlyingObject.java:52`（逻辑推进前，把当前位置存成"上一帧位置"）：

```java
public void snapshotPosition() {
    prevLocationX = locationX;
    prevLocationY = locationY;
}
```

`AbstractFlyingObject.java:58`（插值本体，就一个 `Math.round`）：

```java
public int renderX(double alpha) {
    return (int) Math.round(prevLocationX + (locationX - prevLocationX) * alpha);
}
```

`GameSurfaceView.java:175`（算出 0~1 的进度）：

```java
double alpha = paused ? 1.0
        : Math.min(1.0, (System.nanoTime() - lastLogic) / (double) LOGIC_INTERVAL_NS);
```

`GameRenderer.java:158`（画的时候用 `renderX` 代替 `locationX`）：

```java
float x = object.renderX(alpha) - drawW / 2f;
float y = object.renderY(alpha) - drawH / 2f;
```

**加起来 12 行，一句 `线性插值` 公式，没有三角函数、没有缓动曲线、没有状态机。**

所以"插值很复杂"这个感觉，来源不是这 12 行，而是**"固定步长 + 累加器"**那套写法。
但请注意：那套写法跟插值是**两件独立的事**——就算你把插值全删了，
为了保证"手机卡的时候游戏不变慢"，累加器还是得留着。

### 8.5 如果真的统一 60 帧，要改多少东西（诚实账单）

`40ms → 16.67ms`，相当于每一步的时间变成原来的 **1/2.4**。于是：

| 类别 | 现在的值 | 改 60Hz 后 | 方向 | 在哪 |
|---|---|---|---|---|
| 逻辑步长 | `40_000_000L` | `16_666_667L` | ÷2.4 | `GameSurfaceView.java:30` |
| 敌机生成周期 | 25 / 20 / 16 tick | 60 / 48 / 38.4 | **×2.4** | 三个 `GameWorld` 子类 |
| 英雄射击周期 | 8 / 10 / 12 tick | 19.2 / 24 / 28.8 | **×2.4** | 同上 |
| 难度递增间隔 | `500` tick（20 秒） | `1200` tick | **×2.4** | `GameWorld.java:57` |
| 每次递增的幅度 | `-0.6` / `-0.4` tick | `-1.44` / `-0.96` | **×2.4** | 同上 |
| 道具持续时长 | `150` tick（6 秒） | `360` tick | **×2.4** | `GameWorld.java:53,55` |
| 加速道具时长 | `BOOST_DURATION_FRAMES = 150` | `360` | **×2.4** | `HeroAircraft` |
| 射速下限钳制 | `Math.max(3, …)` / `Math.max(5, …)` | `7.2` / `12` | **×2.4** | 三个 `GameWorld` |
| **所有实体速度** | `MobEnemy` 的 `speedY = 10` | 需要 **÷2.4 = 4.17** | **÷2.4** | 6 个敌机类 + 子弹 + 道具 |
| 概率、血量倍率、血量值 | `0.5` / `0.02` / `0.03` / `20` | **不能动** | — | 同上，且和上面混在同一个方法里 |

看到问题了没有——**同一个方法里，一半的数字要乘 2.4，另一半绝对不能乘**。
`HardGameWorld.applyDifficultyProgression()` 就是这么混着写的：

```java
enemySpawnCycle = Math.max(3, enemySpawnCycle - 0.6);
enemySpeedMultiplier += 0.03;
// ...（省略 enemyHpMultiplier）
enemyShootIntervalMultiplier = Math.max(0.5, enemyShootIntervalMultiplier - 0.02);
heroShootCycle = Math.max(5, heroShootCycle - 0.2);
eliteProbability = Math.min(0.40, eliteProbability + 0.015);
// ...（省略 elitePlusProbability、mobProbability 两行）
getHero(playerIndex).increasePower(2);
```

这六行里哪些要改：

| 行 | 单位 | 60Hz 下怎么改 |
|---|---|---|
| `enemySpawnCycle - 0.6` | tick | **×2.4 → −1.44** |
| `Math.max(3, …)` | tick | **×2.4 → 7.2** |
| `enemySpeedMultiplier += 0.03` | 无量纲倍率 | 不动 |
| `… - 0.02` 和 `0.5` | 无量纲倍率 | 不动 |
| `heroShootCycle - 0.2`、`Math.max(5, …)` | tick | **×2.4** |
| `eliteProbability + 0.015`、`0.40` | 概率 | 不动 |
| `increasePower(2)` | 火力值 | 不动 |

靠眼睛分辨"这个 0.6 是 tick 还是倍率"，改错了不会报错，只会让游戏**悄悄变得更难或更简单**。

### 8.6 还有一个隐藏的坑：速度是 `int`

`AbstractFlyingObject.java:21`：

```java
protected int speedX;
protected int speedY;
```

速度是整数，单位是"每 tick 多少像素"。改成 60Hz 要除以 2.4，**除完必须取整**：

| 原速度 | ÷2.4 精确值 | 取整后 | 实际偏差 |
|---|---|---|---|
| 10（普通敌机） | 4.17 | 4 | **−4%** |
| 6 | 2.5 | 2 | **−20%** |
| 4 | 1.67 | 2 | **+20%** |
| 15（子弹） | 6.25 | 6 | −4% |

**子弹只慢 4%，慢速敌机慢 20%** —— 相对速度全乱了。
最直接的后果：敌机变慢 → 玩家更容易打中 → 分数虚高 → 排行榜的历史成绩全不可比。

要根治只能把 `speedX/speedY` 从 `int` 改成 `double`（或者干脆改成"像素/秒"再乘 `dt`），
那就要动 `forward()`、`AbstractEnemy.originalSpeedX/originalSpeedY`、
所有射击策略、`MobEnemy.create()` 这类工厂方法，以及 **317 行单元测试里的 13 处按 tick 断言的用例**。

### 8.7 还有两个容易被忽略的点

**① 你的手机很可能是 120Hz**

删掉插值后，逻辑 25Hz + 屏幕 120Hz，意味着同一张画面要连续画 5 次（5 张一模一样的帧）。
观感上不是"变卡"，而是"变一顿一顿的"。反过来如果按 60Hz 逻辑、120Hz 屏幕，
也是画 2 次同一张。**只有插值能把高刷屏用满。**

**② 这不是我们新加的设计，是 Windows 版原样迁移过来的**

`docs/02-迁移分析.md` 第 58 行写得很清楚：

> 字段与 `getImage()` 返回类型改为 `android.graphics.Bitmap`；**坐标/碰撞/插值数学全部保留**

迁移实验的核心要求是"**行为保持一致**"。如果我们在迁移过程中把帧率模型换掉，
等于顺手改了游戏手感——验收时这会被问"你凭什么改"，
而且很难证明"新版本和 Windows 版是同一个游戏"。

### 8.8 结论与三条路

**我的建议：不动。** 理由排序：

1. 省钱：插值只有 12 行，删掉不减少多少复杂度
2. 省事：真改要动 10 类数值 + 1 个类型 + 13 处测试断言 + 重新调平衡
3. 不能省：累加器（固定步长）无论如何都得留，否则游戏速度会随手机性能漂移
4. 不该省：这是从 Windows 版继承的设计，迁移要保行为不变

如果你还是想动，有三条路：

| 路 | 做什么 | 代价 | 建议 |
|---|---|---|---|
| **A** | 什么都不改，把本章的图和账记住 | 0 | ✅ **推荐**，验收时这是加分项 |
| **B** | 保留 25Hz 逻辑，只把 `alpha` 恒定为 `1.0`（等于关掉插值）看效果 | 改 1 行，立刻能对比 | 想亲眼看看"没插值有多跳"可以试，试完记得改回来 |
| **C** | 真的统一 60Hz | 上表 10 类改动 + 速度改 `double` + 重跑单测 + 重调手感 | 建议开独立分支、留出半天，且**不要**在验收前一晚做 |

### 8.9 这一章最容易问倒人的点

**Q：为什么逻辑不跟渲染一样 60fps？**

> 因为逻辑频率决定**手感与平衡**，不能随便动。25Hz 是 Windows 版调好的节奏，
> 迁移要保持行为一致。而且逻辑跟渲染绑死的话，手机掉到 45fps 游戏就整体慢 25%，
> 难度会变成"取决于这台手机有多快"。所以逻辑固定 40ms 一步，渲染尽量快。

**Q：那画面不会一格一格跳吗？**

> 会，所以加了插值。逻辑记下"上一步位置"和"这一步位置"，
> 渲染时按"离下一次逻辑推进还差百分之多少"（`alpha`）在两点之间取中间值。
> 碰撞和计分还是用真实位置，只有画在哪个像素用了插值。全部代码 12 行。

**Q：`lastLogic += 40ms` 和 `lastLogic = now` 有什么区别？**

> 前者让逻辑时间轴严格按 40/80/120ms 走，误差不累积；后者会把逻辑起点对齐到渲染帧边界，
> 每帧多出来的零头被丢掉，长期累积会让逻辑变慢。注释里写了这一点。

**Q：如果手机卡了 2 秒，回来要补 50 步吗？**

> 不补。代码里 `if (now - lastLogic > 5 * LOGIC_INTERVAL_NS) lastLogic = now;`
> 超过 5 步（200ms）就直接丢弃欠账，否则玩家会看到飞机瞬移，
> 而且 50 步挤在一帧里算完会更卡（死亡螺旋）。

**Q：为什么不干脆把逻辑也提到 60Hz，速度改一下不就行了？**

> 试过算这笔账：速度是 `int`，÷2.4 之后取整误差最大 20%，
> 子弹和慢速敌机的相对速度会乱；周期类数值要 ×2.4、倍率类绝对不能动，
> 而它们混在同一个方法里；还要改 13 处单元测试断言并重新调平衡。
> 换来的只是少 12 行插值，不划算。要做也该把速度改成"像素/秒"再乘 `dt`，
> 那是另一个量级的重构。

### 9.1 一次完整对局的调用链

```
① 手指点「开始游戏」
   MainActivity.onStartGame()
        ↓
   MenuOverlayView 收到触摸 → 命中「开始游戏」卡片 → 播放收起动画 → listener.onStartGame()
        ↓
   MainActivity 打开 GameActivity，把 难度 / 皮肤 / 昵称 塞进 Intent

② GameActivity.onCreate()
        ↓
   创建对应的 GameWorld（EasyGameWorld / NormalGameWorld / HardGameWorld）
        ↓
   new GameSurfaceView(this, world)，setContentView 放进去
        ↓
   setDecorFitsSystemWindows(false)   ← 全屏，游戏画面要铺满

③ GameSurfaceView 的 Surface 准备好
   surfaceCreated() → 起一条线程 loopThread → run()
        ↓
   ┌─────────── 每 4ms 转一圈 ───────────┐
   │  够 40ms 了吗？                      │
   │    够 → applyInput() → world.update() │  ← 逻辑：25Hz
   │  算 alpha（0~1）                      │
   │  lockCanvas()                         │
   │  GameRenderer.draw(canvas, world, alpha) │  ← 渲染：能多快就多快
   │  unlockCanvasAndPost()                │
   └──────────────────────────────────────┘

④ world.update() 内部（core/，完全不认识 Android）
   先给所有实体 snapshotPosition()  ← 记下"上一步位置"，供插值用
        ↓
   处理输入 → 英雄移动 / 射击 → 敌机生成 → 敌机射击 → 子弹飞行
        ↓
   碰撞检测（用真实坐标）→ 掉血 / 加分 / 掉落道具
        ↓
   道具计时递减、难度递增、Boss 检查、清理越界与已销毁对象
        ↓
   if (isGameOver()) → callback.onGameOver(总分)

⑤ 画面怎么出来
   GameRenderer.draw()
        ↓
   背景（滚动星空）→ 道具 → 敌机子弹 → 我方子弹 → 敌机 → 英雄
        ↓
   HUD：状态卡（分数/血量）→ 返回、暂停按钮 → 背包槽位
        ↓
   每个实体的坐标都用 renderX(alpha) 而不是 locationX  ← 只有这里用插值

⑥ 死了
   GameSurfaceView 回调 onGameOver(score)  → GameActivity 弹出成绩框
        ↓
   点「查看排行榜」→ RankActivity → ScoreDao 查库 → ListView 显示
        ↓
   点「返回」→ finish() → 回到 MainActivity，刷新最高分标签

⑦ 中途切后台
   onPause() → GameSurfaceView 暂停循环（不再 update，但保住状态）
        ↓
   onResume() → 恢复；surfaceDestroyed() 时要 stopLoop() 并 join，
                等线程真正退出，否则下次进游戏会有两条线程抢同一个 Surface
```
