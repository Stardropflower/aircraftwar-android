## 一、这个项目长什么样

### 1.1 目录结构

```
app/src/main/java/edu/hitsz/aircraftwar/
├── core/          ← 游戏规则，43 个类，一个 import android 都没有
│   ├── GameWorld.java          主循环：update() 每 40ms 走一步
│   ├── Easy/Normal/HardGameWorld.java   三种难度（继承 + 模板方法）
│   ├── aircraft/               飞机：英雄、五种敌机（工厂模式）
│   ├── strategy/               射击方式：直射/散射/环形（策略模式）
│   ├── item/                   五种道具 + 观察者（炸弹、冰冻）
│   └── basic/AbstractFlyingObject.java  所有东西的老祖宗
├── render/        ← 只管画
│   ├── GameSurfaceView.java    起线程、跑循环、收触摸
│   ├── GameRenderer.java       把 core 里的数字画到 Canvas 上
│   └── Assets.java             贴图盒 + 碰撞框尺寸表
├── ui/            ← 界面
│   ├── MainActivity / GameActivity / SkinActivity / RankActivity
│   ├── visual/     五个全部自绘的 View（星空、菜单面板、开场动画…）
│   └── UiInsets.java           系统栏留白
├── net/           ← 网络对战（超出中期范围）
├── db/            ← SQLite 排行榜
├── data/LocalStore.java   ← SharedPreferences：最高分、皮肤、昵称、静音
└── audio/SoundManager.java
```

### 1.2 三层的边界（验收必问）

| 层 | 行数 | 认识 Android 吗 | 职责 | 换平台要重写吗 |
|---|---|---|---|---|
| `core/` | 2593 | **不认识**（零 `import android`） | 敌机怎么飞、子弹怎么飞、什么时候加分、什么时候死 | 不用，一行不改 |
| `render/` | 1077 | 认识（`Canvas`、`SurfaceView`） | 把 `core` 里的坐标画成像素 | 要 |
| `ui/` | 3372 | 认识（`Activity`、`View`） | 菜单、翻页、弹窗、输入 | 要 |
| `net/` `db/` `data/` `audio/` | 1941 | 认识 | 联机、排行榜、本地设置、音效 | 要 |

**为什么这么分**：`core` 是纯 Java，所以能在电脑上跑单元测试（22 个用例，全绿，不用模拟器）；
也正因为如此，界面层怎么改都不会碰到游戏规则。

### 1.3 界面为什么全部自绘，不用 XML 布局

全项目只有 `activity_main.xml` 一个 XML，其余界面全是 `View` 里 `onDraw` 画出来的。

| 理由 | 具体好处 |
|---|---|
| 不受屏幕尺寸影响 | 所有尺寸按 `宽度 × 百分比` 算，不写死 dp，1280 宽和 1080 宽都成比例 |
| 动画自由 | 面板进场是一个 `progress` 从 0 到 1，随便怎么缓动，XML 动画做不到 |
| 性能 | 没有一层层嵌套布局，一次 `onDraw` 画完 |

**代价**：点击判定要自己写（`onTouchEvent` 里算矩形），不能靠 `OnClickListener`。

## 二、启动链路：从点图标到主菜单

### 2.1 调用链

```
图标 → MainActivity.onCreate()
        → setContentView(activity_main.xml)      ← 唯一的 XML
        → 这个 XML 里其实只放了两个"壳"：
              MenuOverlayView   显示菜单（自绘）
              StarfieldView     星空背景（自绘）
        → refreshLabels()   把最高分、当前皮肤写进标签
        → startEntrance()   让 MenuOverlayView 播进场动画
```

### 2.2 `MainActivity` 干什么（267 行）

它只做四件事，**不含任何绘制逻辑**：

| 方法 | 干什么 |
|---|---|
| `onCreate()` | 建 `LocalStore`（一个对象管所有本地数据）→ 存 5 个控件引用 → 4 个按钮各绑一个 lambda |
| `openPanel(mode)` | `new` 一个 `MenuOverlayView` → `bind(store, listener)` 塞数据和回调 → `addView` 铺满屏幕 |
| `refreshLabels()` | 从 `LocalStore` 读最高分、皮肤名，写进两个 TextView（从游戏页回来要刷新） |
| `onBattle()` / `startGame()` | 拼 `Intent`，跳 `BattleRoomActivity` 或 `GameActivity` |

**关键设计**：`MenuOverlayView` 弹出来时是**加在 Activity 最上层的子 View**，
所以它可以把整个屏幕盖住（包括标题和最高分），退出时 `removeView` 即可。
比 `Dialog` 轻，也比 `Dialog` 好控制动画。

### 2.3 `MenuOverlayView`：一个 View，三种形态（643 行）

**它只有一个 `View` 实例，靠一个 `mode` 字段决定画什么。** 这是本节最该记住的一句话。

```
Mode.START  ──点「开始游戏」──→  Mode.DIFFICULTY  ──点某档──→  回调 Activity 开局
    │                                  │
    └──点「设置」──→  Mode.SETTINGS ←──┘（返回）
```

| 方法 | 干什么 |
|---|---|
| 构造函数 | 把 `density`（1dp = 几像素）存成字段，后面所有尺寸都靠它换算 |
| `computeLayout()` | 按当前屏幕算面板矩形 + 每个卡片的可点区域，存进字段 |
| `onDraw()` | `progress=0` 直接返回（面板还没开，别浪费帧）→ 算布局 → 缓动 → 按 mode 画卡片 |
| `drawModeCard()` | 卡片左边 56dp 圆角方块，贴图取"宽比/高比"里**小的那个**做统一缩放，不变形 |
| `onTouchEvent()` | **只处理按下**，其余动作全吃掉；`progress` 没到 1 时忽略所有点击（防误触） |
| `handleItemTap()` | 命中哪个卡片 → 该翻页翻页、该关面板关面板、该切开关切开关 |
| `goBack()` | 只有难度页有上一层；改完 `mode` 只要 `invalidate()`，下一帧自动重画 |
| `finish()` | 先把自己从父容器摘掉、停帧循环，**再**发回调（顺序不能反，否则回调里又开新页面会打架） |

**音乐/音效两个开关**：`handleItemTap` 里取反 → 写回 `LocalStore` → `invalidate()`。
注意这里**故意不 `dismiss()`**，开关不该把面板关掉。

## 三、游戏页：三个类撑起一局游戏

### 3.1 `GameActivity`：装配工 + 生命周期（560 行）

| 方法 | 干什么 |
|---|---|
| `onCreate()` | ① 先全屏 ② 读难度（对战局用房间里的难度**覆盖** Intent 带来的） ③ 按难度 `new` 对应的 `GameWorld` ④ `Assets.load()` 装贴图 ⑤ 挂 `GameSurfaceView` |
| `configurePlayField()` | 逻辑宽度**永远 512**，高度按屏幕长宽比换算，再夹在 768~1600 之间 |
| `createListener()` | 给 `GameWorld` 挂监听：击杀→播 `hit`、拾取→播 `item`、Boss 出现→换 BGM |
| `onGameOver(int)` | 渲染线程不能碰 UI，所以塞进 `Message` 发给主线程 `Handler` |
| `showGameOverDialog()` | 先存成绩（`LocalStore` + `ScoreDao`）→ 再弹框（点外面关不掉）→ 左返回 / 右看排行榜 |
| `onPause()` / `onResume()` | `paused = true` + 停 BGM，切回来反过来。**不这么做切后台游戏还在跑** |
| `onDestroy()` | 按"消息 → 渲染线程 → 世界 → 音频 → 数据库"的顺序拆，顺序错了会崩在已关闭的对象上 |
| `enterFullscreen()` | 三件事：内容铺到系统栏底下、隐藏状态栏和导航栏、允许边缘上划临时叫出系统栏 |

> 💡 **为什么 `GameActivity` 不用 `UiInsets`，别的页面要用？**
> 游戏页是全屏的，画面本来就要铺满；别的页面有标题和输入框，
> Android 15 起强制 edge-to-edge，不做留白就会被状态栏盖住半个字。

### 3.2 `GameSurfaceView`：整个游戏的心脏（378 行）

它同时是 `View`（一块画布）和 `Runnable`（一个工人）。

| 方法 | 干什么 |
|---|---|
| `surfaceCreated()` | 开一条叫 `aircraftwar-loop` 的线程，优先级 `+1`（别被日志线程抢时间片） |
| `surfaceDestroyed()` | → `stopLoop()`：举旗 `running=false`，`join(1000)` 最多等 1 秒 |
| `run()` | 就是主循环，下面单独讲 |
| `onTouchEvent()` | 屏幕坐标先除以缩放比换成逻辑坐标，再**按 UI 优先顺序**判：返回键→暂停键→背包格→拖飞机 |

**`stopLoop()` 为什么要 `join`**：`surfaceDestroyed` 返回之后系统才敢销毁 Surface 缓冲区。
如果线程还活着还在 `lockCanvas`，拿到的是块死掉的 surface——轻则抛异常，重则 native 崩，
而且 Activity 都关了线程还在跑就是泄漏。
**为什么是 `join(1000)` 不是 `join()`**：这方法跑在主线程，无限等万一线程卡住就轮到主线程 ANR。

主循环（下面这段**为了看清结构删掉了几行**，比如错误处理和回调细节，
原文件是 `GameSurfaceView.java:149-203`）：

```java
long lastLogic = System.nanoTime();
while (running) {
    long now = System.nanoTime();
    if (!paused) {
        if (now - lastLogic >= LOGIC_INTERVAL_NS) {      // 够 40ms 了吗
            lastLogic += LOGIC_INTERVAL_NS;              // 累加，不是对齐到 now
            if (now - lastLogic > 5 * LOGIC_INTERVAL_NS) {
                lastLogic = now;                          // 落后太多就丢弃欠账
            }
            applyInput();
            world.update();
            if (world.isGameOver()) { /* 回调一次 */ }
        }
    } else {
        lastLogic = now;
    }
    double alpha = Math.min(1.0, (System.nanoTime() - lastLogic) / (double) LOGIC_INTERVAL_NS);
    Canvas canvas = getHolder().lockCanvas();   // 借一张后台草稿纸
    renderer.draw(canvas, world, alpha, paused);
    getHolder().unlockCanvasAndPost(canvas);    // 交卷，两张纸互换
    Thread.sleep(4);
}
```

三句话概括：**逻辑够 40ms 才走一步；渲染每转一圈都画；中间那段差值用 `alpha` 补。**

`lockCanvas`/`unlockCanvasAndPost` 就是**双缓冲**：一块正被屏幕显示，一块给你画，
交卷时互换。所以屏幕永远不会看到"背景画了、飞机还没画"的撕裂画面。

### 3.3 `GameRenderer`：画什么、按什么顺序（410 行）

绘制顺序就是图层顺序，**从下往上盖**：

```
① drawColor(0xFF0E1218)        擦黑板（不擦会留上一帧的残影）
② drawBackground               三张背景图，512×768，和逻辑画布同宽
③ drawEntities(道具)            越界/已销毁的跳过
④ drawEntities(敌机子弹)
⑤ drawEntities(我方子弹)
⑥ drawEntities(敌机)
⑦ drawEntities(英雄)
⑧ drawStatusCard               左上状态卡：分数 + 血条
⑨ drawBackpack                 右上 2 格背包，SLOT=52dp
⑩ drawBackButton / drawPause   返回、暂停，40dp 圆角按钮，距顶 12dp
⑪ drawOverlay                  暂停/结束时铺一层 0xAF 的半透明黑
```

| 方法 | 关键点 |
|---|---|
| `draw()` | 先 `save()` → 按 `屏幕宽/512` 缩放整块画布 → 之后所有坐标都按 512 逻辑系写，**不用管手机是 1K 还是 2K 屏** |
| `drawEntities()` | 坐标用 `renderX(alpha)` 而不是 `locationX`——这是**全项目唯一用到插值的地方** |
| `onTouchEvent()` | 和 `GameSurfaceView` 一样先转逻辑坐标，再按 UI 优先顺序判定（返回→暂停→暂停遮罩→背包→拖飞机） |

### 3.4 `Assets`：贴纸盒 + 一张尺寸表（289 行）

| 方法 | 干什么 |
|---|---|
| `load()` | 开局一次性 `decodeResource` 二十来张图，按字符串 key 塞进 `HashMap`；七款皮肤另存一份 `EnumMap` |
| `bitmapFor(Object)` | 13 个 `instanceof` 分支：这个对象是什么类就取哪张图，最后兜底返 `mob` |
| `widthOf / heightOf(Class)` | 飞机查下面的尺寸表；子弹和道具没重绘过，直接返位图像素 |
| `logicalAircraftBox(Class)` | **把每类飞机的逻辑宽高钉死在换高清贴图之前的尺寸** |

**最后这条是全项目最值得讲的一个决定**：贴图换成了 3 倍分辨率，如果碰撞框跟着变大，
判定范围就会变成原来的 9 倍，手感全毁。所以尺寸表是写死的常量：

| 对象 | 逻辑尺寸 |
|---|---|
| 英雄机 | 100 × 83 |
| 普通敌机 | 75 × 50 |
| 精英敌机 | 105 × 68 |
| Boss | 300 × 200 |

画的时候按"贴图尺寸 → 逻辑尺寸"缩放画到屏幕上，**画得更大，但判定一点没变**。

## 四、帧率：为什么逻辑 25Hz、渲染 60fps

这一章专门回答"能不能统一成 60 帧"。

### 4.1 两个数字

- **逻辑 40ms 一步 = 25Hz**（`GameSurfaceView.java:30` 的 `LOGIC_INTERVAL_NS`）
- **渲染尽量快**，手机一般 60 / 90 / 120Hz

它们回答的是两个不同的问题：逻辑决定"敌机这一刻在哪、撞没撞上"，
渲染决定"这一帧画面长什么样"。

### 4.2 三个方案

| 方案 | 做法 | 结果 |
|---|---|---|
| A | 逻辑跟着渲染跑（统一 60 帧） | 手机掉到 45fps 时**游戏整体慢 25%**，难度取决于手机性能 |
| B | 逻辑 25Hz，渲染也 25Hz | 每秒 25 张，肉眼可见地跳，像 PPT |
| **C** | 逻辑 25Hz + 渲染 60~120Hz + 插值 | 规则稳定 + 画面顺滑 ← **本项目** |

```
逻辑时间轴：  |----40ms----|----40ms----|----40ms----|
逻辑位置：    x=100       x=110       x=120
渲染画在哪：  100  104  108  112  116  120
              alpha=0  .4  .8  .2  .6  1.0
```

**碰撞、计分、判定全部用真实坐标（100/110/120），只有"画在哪个像素"用插值。**

### 4.3 循环里最关键的一行

```java
lastLogic += LOGIC_INTERVAL_NS;
```

**为什么不是 `lastLogic = now`**：假设渲染一帧要 17ms、逻辑要 40ms，
`= now` 会把逻辑起点对齐到渲染帧边界，每帧多出来的零头被丢掉，长期累积逻辑就变慢；
`+= 40ms` 让逻辑时间轴严格按 40/80/120 走，误差不累积。

**为什么后面要 `if (now - lastLogic > 5 * LOGIC_INTERVAL_NS) lastLogic = now`**：
切后台两秒回来，如果老实补 50 步，玩家会看到飞机瞬移，而且 50 步挤在一帧里算完会更卡。

### 4.4 插值其实只有 12 行

```
snapshotPosition()  逻辑推进前存一下旧位置        （2 行）
renderX(alpha)      Math.round(旧 + (新-旧)×alpha) （2 行）
alpha 的计算         循环里一行                   （1 行）
绘制时改用 renderX   代替 locationX               （2 行）
```

**没有三角函数、没有缓动曲线、没有状态机。** 觉得复杂不是这两行的问题，
而是"固定步长 + 累加器"那套写法——但**那套写法删不掉**，否则手机卡时游戏就变慢。

### 4.5 如果真统一成 60 帧，要改多少东西

`40ms → 16.67ms`，每一步的时间变成原来的 1/2.4，于是：

| 类别 | 现在 | 改后 | 方向 |
|---|---|---|---|
| 敌机生成周期 | 25 / 20 / 16 tick | 60 / 48 / 38.4 | **×2.4** |
| 英雄射击周期 | 8 / 10 / 12 tick | 19.2 / 24 / 28.8 | **×2.4** |
| 难度递增间隔 | 500 tick（20 秒） | 1200 tick | **×2.4** |
| 道具持续 | 150 tick（6 秒） | 360 tick | **×2.4** |
| **所有实体速度** | `MobEnemy` 的 `speedY = 10` | 需 **÷2.4 = 4.17** | **÷2.4** |
| 概率、倍率、血量 | `0.03` / `0.02` / `0.40` | **绝对不能动** | — |

两个坑：

**① 最后一类跟前面混在同一个方法里。** `HardGameWorld.applyDifficultyProgression()` 六行代码，
`enemySpawnCycle - 0.6` 要改成 `-1.44`，紧挨着的 `enemySpeedMultiplier += 0.03` 一个字都不能动。
改错了不报错，只会让游戏悄悄变难。

**② 速度是 `int`，÷2.4 之后要取整：**

| 原速度 | 精确值 | 取整 | 偏差 |
|---|---|---|---|
| 10（普通敌机） | 4.17 | 4 | −4% |
| 6 | 2.5 | 2 | **−20%** |
| 4 | 1.67 | 2 | **+20%** |
| 15（子弹） | 6.25 | 6 | −4% |

子弹只慢 4%，慢速敌机慢 20%，相对速度全乱 → 玩家更容易打中 → 分数虚高 → 历史成绩不可比。
要根治得把 `speedX/speedY` 改成 `double`，那要动 `forward()`、射击策略、**317 行单测里的 13 处断言**。

**③ 还有一条不能忽略**：这是从 Windows 版**原样迁移**过来的（`docs/02-迁移分析.md` 写了"坐标/碰撞/插值数学全部保留"）。
迁移实验的核心要求就是"行为保持一致"，中途换帧率模型等于顺手改手感。

### 4.6 五条问答（直接背）

**Q：为什么逻辑不跟渲染一样 60fps？**
> 逻辑频率决定手感和平衡，25Hz 是原版调好的节奏，迁移要保持一致。
> 而且绑死的话手机掉到 45fps 游戏就整体慢 25%，难度会变成取决于手机性能。

**Q：画面不会一格一格跳吗？**
> 会，所以加了插值。逻辑记下"上一步位置"和"这一步位置"，
> 渲染按 `alpha` 在两点之间取中间值。碰撞和计分还是用真实位置，只有画在哪个像素用插值。

**Q：`lastLogic += 40ms` 和 `lastLogic = now` 什么区别？**
> 前者让逻辑时间轴严格按 40/80/120ms 走，误差不累积；
> 后者会把起点对齐到渲染帧边界，零头被丢掉，长期累积逻辑变慢。

**Q：手机卡了 2 秒，回来要补 50 步吗？**
> 不补。超过 5 步（200ms）就丢弃欠账，否则飞机瞬移，而且 50 步挤在一帧里算完会更卡。

**Q：为什么不干脆把逻辑提到 60Hz，速度改一下不就行了？**
> 速度是 int，÷2.4 取整误差最大 20%，子弹和慢速敌机的相对速度会乱；
> 周期类数值要 ×2.4、倍率类绝对不能动，而它们混在同一个方法里；
> 还要改 13 处单测断言并重新调平衡。换来的只是少 12 行插值，不划算。

## 五、界面层其余部分

### 5.1 三个自绘组件

| 组件 | 干什么 | 最值得记的一点 |
|---|---|---|
| `StarfieldView` | 主菜单背景的星空 | `onSizeChanged` 里一次性建 4 个 `Shader`、分配好星星数组；出屏的星星**传送回顶部**，运行期一个对象都不 new |
| `GradientTextView` | 带渐变的标题文字 | `onSizeChanged` 时建一个纵向 `LinearGradient` 挂到 `Paint` 上，然后照常 `super.onDraw` |
| `SkinPreviewView` | 皮肤页的飞机预览 | 光晕在背后呼吸、飞机轻微浮动微倾；**影子先画、飞机后画**，画完变换必须 `restore` 回去 |

**自定义 View 三件套**（会被问）：`onMeasure` 决定多大、`onSizeChanged` 尺寸确定时来一次（建 `Shader`、算坐标的最佳时机）、`onDraw` 每帧画。

### 5.2 开场动画 `IntroOverlayView`（912 行，全项目最大）

**不用 `Animation`/`Animator`，全靠自己算时间轴。** 两幕：

| 时间段 | 演什么 |
|---|---|
| 0 ~ 3020ms | 加载幕：飞机扫描式显现 → 英文标题逐字扫出 |
| 3020 ~ 3820ms | 衔接幕：英雄机飞向最终位置 → 中文标题从一条线展开 → 淡出交出菜单 |

关键方法：

| 方法 | 干什么 |
|---|---|
| `doFrame(long nanos)` | 节拍器，每 16.7ms 被叫一次；第一次进来把时间定成零点 |
| `timeMs()` / `mainMs()` | 纳秒换成毫秒；`mainMs()` 把第一幕 3020ms 整段跳过去，让第二幕的 0 点落在该在的地方 |
| `clamp01` + 三个缓动 | 进度条别越界；缓入缓出让动作不是匀速（线性像机器，缓动像人） |
| `drawLoadPlane()` | 没有"逐行绘制"，就是**画整张图再用 `clipRect` 把没扫到的部分裁掉** |
| `drawPlaneSweep()` | `scale(open, 1)` 让标题从一条线展开到满宽，130ms |
| `syncMenuText()` | 每帧把 `alpha` 写给菜单上的标题，交接时不闪 |

**为什么不用系统动画框架**：要精确控制时间轴、要能中途跳过、要不依赖布局层级。

### 5.3 系统栏适配 `UiInsets`（31 行）

Android 15 起所有应用强制 edge-to-edge，内容会铺到状态栏底下。
`UiInsets.applySystemBars(root)` 给根 View 挂监听，每次系统栏尺寸变化就把 `padding` 设成四条边的内边距。

**规则**：全屏的游戏页不调（画面本来就该铺满），有标题和输入框的页面都要调。

## 六、数据层

### 6.1 SQLite 三件套（实验四重点）

| 类 | 职责 | 关键点 |
|---|---|---|
| `ScoreDbHelper` | 建库建表，`SQLiteOpenHelper` 的子类 | `onCreate` 拼 `CREATE TABLE range`；`onUpgrade` 先删表再重建（版本号变了才触发） |
| `ScoreDao` | 增删查改 | 用 `?` 占位符防注入；`Cursor` **必须在 `finally` 里 close**；排序写在 `orderBy score DESC` |
| `ScoreRecord` | 纯数据对象 | 六个字段 + 两个构造，一个方法都没有 |

表结构 `score_list`：`_id` 自增主键、`name`、`score`、`difficulty`、`time`、`synced`。

**为什么用 SQLite 而不是文件**：要按难度过滤、按分数排序、按主键删除，
这些用 SQL 一行搞定，用文件得自己写一堆解析。

### 6.2 排行榜界面

| 类 | 干什么 |
|---|---|
| `RankActivity` | 查库 → 交给 Adapter → 没数据就显示"还没有记录"空状态 → 底部写条数和最高分 |
| `RankAdapter` | `ListView` 的适配器，用 **ViewHolder 模式**：`convertView` 为空才 `inflate`，否则复用旧视图 |

**ViewHolder 解决什么**：列表滑动时每一行都要重新绑定，每次都 `findViewById` 会卡。
把控件引用缓存进 `ViewHolder` 挂在 `convertView` 的 tag 上，复用时就省掉查找。

### 6.3 皮肤与本地设置

| 方法 | 干什么 |
|---|---|
| `SkinActivity.rebuildGrid()` | 清空网格，遍历 7 款皮肤逐格生成，顺手算"解锁没""是不是当前选中" |
| `isSkinUnlocked()` | 默认皮肤恒解锁；其余查**本机该难度历史最高分**，够门槛（1500~6000）就解锁 |
| `LocalStore.submitScore()` | 只有**严格大于**本机最高分才写入，返回"是否破纪录" |
| `LocalStore` 其余 | `SharedPreferences` 存：最高分、选中皮肤、昵称、音乐静音、音效静音、服务器地址 |
| `migrateLegacyMute()` | 旧版本只有一个总静音开关，新版本拆成音乐/音效两个；这里把旧值抄给两个新键再删旧键 |

**为什么设置用 `SharedPreferences` 不用 SQLite**：就是几个键值对，
读一次几微秒，用数据库反而要建表、开游标，杀鸡用牛刀。

## 七、联机对战（选读，中期不考）

### 7.1 四个文件

| 文件 | 干什么 |
|---|---|
| `BattleRoomActivity` | 房间页：服务器地址输入、创建房间（选难度+目标分）、加入房间（6 位房间码）、右上角「使用教程」 |
| `BattleClient` | 把 `ws://` 地址包成 OkHttp `WebSocket`，转成自己的回调接口 |
| `BattleProtocol` | 所有消息的 JSON 定义（create / join / score / state / over / ping） |
| `BattleSession` | 一条连接的状态机：未连接 → 进房 → 对局中 → 结束 |

### 7.2 一条消息走完一圈

```
① 房主点「创建房间」→ BattleProtocol.create → 服务端建房，回 joined（你是 A + 房间码）
② 对手输房间码 → join → 服务端回 joined（你是 B）+ 房主也收到"对手进来了"
③ 双方各自在本机打同一关卡，每秒上报一次 score + hp
④ 服务端把两人的分数拼成 state 广播 → HUD 上显示对手得分和血量
⑤ 有人到目标分 → 服务端回 over（winner）→ 客户端只负责**显示**结果
```

**关键设计**：胜负由**服务端判定**，客户端不自己算。否则两边各算各的必然不一致。
网络回调不能直接碰 UI，要 `Handler` 切回主线程。

## 八、验收冲刺

### 8.1 一次对局的完整调用链（这张图能答一半问题）

```
点「开始游戏」→ 选难度 → MainActivity 拼 Intent 开 GameActivity
  → new GameWorld → Assets.load() → 挂 GameSurfaceView
  → surfaceCreated 起线程 → run() 每 40ms: world.update()
       update 内部：snapshotPosition（记旧位置）→ 处理输入 → 生成/移动敌机
                    → 子弹飞行 → 碰撞检测 → 加分/掉血/掉道具 → 难度递增
  → 每帧: renderer.draw(canvas, world, alpha)  用 renderX(alpha) 画在中间位置
  → 死了 → onGameOver → Handler → 弹框 → 存成绩 → 可跳排行榜
```

### 8.2 必背 15 问

**1. 项目分几层？为什么？**
> 三层：`core` 纯规则（零 Android 依赖）、`render` 绘制、`ui` 界面。
> 好处是 `core` 能在电脑上跑单元测试（22 个用例），而且换界面不会碰游戏规则。

**2. 界面为什么不用 XML？**
> 尺寸按屏幕宽度百分比算，不写死 dp，什么分辨率都不变形；动画和绘制完全可控；
> 没有嵌套布局，一次 `onDraw` 画完。代价是点击判定要自己算矩形。

**3. 为什么用 `SurfaceView` 而不是普通 View + `invalidate()`？**
> 普通 View 的绘制节奏由主线程决定，触摸、布局、弹窗都会挤掉帧；
> `SurfaceView` 有独立绘制表面，可以在自己的线程里画，节奏自己控。

**4. 主循环为什么用 `nanoTime` 不用 `currentTimeMillis`？**
> 后者受系统时间调整影响，可能突然跳变；前者是单调递增的，适合算间隔。

**5. 为什么 `lastLogic += 40ms` 而不是 `= now`？**
> 累加让逻辑时间轴严格按 40/80/120 走，误差不累积；对齐到 `now` 会把零头丢掉，长期累积变慢。

**6. `join(1000)` 为什么？**
> `surfaceDestroyed` 返回后系统才销毁 Surface 缓冲区，线程还活着就会拿到死 surface；
> 但主线程不能无限等，所以给 1 秒上限。

**7. 双缓冲是什么？**
> `lockCanvas` 借一块后台缓冲区画，`unlockCanvasAndPost` 交卷后和前台互换。
> 屏幕永远显示完整的帧，不会看到画到一半的画面。

**8. 为什么贴图是 3 倍分辨率却不改碰撞框？**
> 碰撞框钉死在换高清贴图之前的尺寸（英雄 100×83 等）。跟着放大的话判定范围变 9 倍，手感全毁。
> 画得更大，判定没变。

**9. 为什么贴图放 `drawable-nodpi`？**
> 普通 `drawable` 目录会按屏幕密度自动缩放，3 倍图在小屏上被缩掉就白做了。
> `nodpi` 表示别缩放，我们用 `inScaled = false` 自己控制尺寸。

**10. `minSdk 33` 是什么意思？**
> 能装的最低系统版本，Android 13。低于这个版本的手机装不上（报"解析软件包时出现问题"）。
> 需要旧机演示可以用 `-PminSdkOverride=24` 打兼容包。

**11. SQLite 三件套各干什么？**
> `ScoreDbHelper` 建库建表；`ScoreDao` 增删查改；`ScoreRecord` 纯数据对象。

**12. `Cursor` 为什么要 `close()`？**
> 它持有数据库的游标资源，不关会泄漏，积累多了会崩。所以写在 `finally` 里，异常也能关。

**13. 排行榜怎么排序的？**
> 在 SQL 里 `orderBy score DESC`，不是在 Java 里排。数据库排得更快，而且数据量大时差别明显。

**14. `ListView` 的 ViewHolder 是什么？**
> 列表滑动时行视图会复用。把每行里的控件引用缓存进 ViewHolder 挂在 tag 上，
> 复用时就不用再 `findViewById`，省掉大量查找。

**15. 如果让你加一种新敌机，怎么加？**
> 新建一个类继承 `AbstractEnemy`（实现 `doShoot` 和 `getPower`）→
> 新建一个对应的 `EnemyFactory` 实现类 → 在 `GameWorld.spawnEnemies` 里按概率选到这个工厂。
> 不用改碰撞、移动、渲染——那些都在父类和 `Assets` 里。
