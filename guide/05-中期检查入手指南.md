## 0.6 看懂 Java 文件开头的两行

## 1.3 布局声明：XML 静态 vs Java 动态（课件第 7–9 页）

**课件说的**：两种方式
- **XML 静态布局**：写在 `res/layout/xxx.xml`，用 `setContentView(R.layout.xxx)` 加载，界面和逻辑分离
- **Java 动态布局**：在代码里 `new LinearLayout(this)` 一个个加，运行时实例化

**我们代码里 —— 两条路线都用了**：

| 页面 | 用的方式 | 位置 |
|---|---|---|
| 主菜单 | **XML 静态布局** | `res/layout/activity_main.xml`；`MainActivity.java:41` 用 `setContentView(R.layout.activity_main)` 加载 |
| 皮肤选择页 | **Java 动态布局** | `SkinActivity.java:68` 里 `new GridLayout(this)` 逐个 `addView` |
| 游戏页 | 都不用 | `setContentView(gameView)`，画面全部由 Canvas 逐帧绘制 |

XML 那条（主菜单）长这样：
```xml
<ScrollView ...>
    <LinearLayout android:orientation="vertical" ...>
        <TextView android:text="飞机大战" android:textSize="42sp" ... />
        <Button android:id="@+id/btn_easy" ... />
        <Button android:id="@+id/btn_music" ... />
        ...
    </LinearLayout>
</ScrollView>
```
```java
// MainActivity.java 第 41 行
setContentView(R.layout.activity_main);
// 第 43-45 行：找到控件
bestScoreLabel = findViewById(R.id.tv_best);
musicButton = findViewById(R.id.btn_music);
```

**怎么答**：
> "课件讲了两种方式，我两种都用了，是按场景选的。
> 主菜单结构固定，放在 XML 里，界面和逻辑分开，改布局不用动 Java 代码。
> 皮肤页的格子数量跟着 Skin 枚举走，用代码遍历生成更合适——以后加一款皮肤不用同步改 XML。
> 游戏页两者都不用，因为画面全是 Canvas 逐帧画的，本来就没有布局可言。"

> 💡 这个回答比只用一种更有说服力：能说清**为什么在这个页面选这种方式**。

## 1.4 事件处理：监听 vs 回调（课件第 10–16 页）

**课件说的**：Android 有两种事件处理模型
- **①基于监听**：给控件 `setOnClickListener`，事件来了通知监听器
- **②基于回调**：没有监听器，重写控件自己的方法（如 `onTouchEvent`）

课件还列了监听的三种写法：Activity 实现接口、匿名内部类、内部类。

**我们代码里 —— 两种都用到了**：

### 基于监听（`setOnClickListener`）

| 文件 | 行号 | 内容 |
|---|---|---|
| [MainActivity.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\ui\MainActivity.java) | 49–53 | 五个控件各绑一个监听器，如 `findViewById(R.id.btn_easy).setOnClickListener(v -> startGame(Difficulty.EASY))` |
| 同上 | 53 | `musicButton.setOnClickListener(v -> toggleMusic())` —— 音乐开关 |
| [SkinActivity.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\ui\SkinActivity.java) | 140 | `cell.setOnClickListener(v -> { ... })` |

> 我们用的是 **lambda 写法**，等价于课件的「匿名内部类」那种：
> `v -> { ... }` 就是 `new View.OnClickListener() { public void onClick(View v) { ... } }` 的简写。

### 基于回调（`onTouchEvent`）

| 文件 | 行号 | 内容 |
|---|---|---|
| [GameSurfaceView.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\render\GameSurfaceView.java) | 203 | `public boolean onTouchEvent(MotionEvent event)` |

里面处理了 `ACTION_DOWN`（按下）、`ACTION_MOVE`（移动）、`ACTION_POINTER_DOWN`（第二根手指按下）、
`ACTION_UP`（抬起）、`ACTION_CANCEL`（取消）——**正好对应课件第 10 页那张流程图**。

**怎么答**：
> "两种都用了。按钮这种一次性点击用监听器，代码简单。
> 游戏画面不行——它要连续跟踪手指的按下、移动、抬起，还要处理两根手指和手势被系统打断的情况，
> 所以用的是重写 onTouchEvent 这种回调方式。"

**可能追问：「为什么 onTouchEvent 返回 true？」**
> "返回 true 表示这个事件我已经消费了，后续的 MOVE、UP 还会继续派发给我。
> 如果返回 false，系统就认为我不处理，接下来就收不到移动和抬起事件了。"

## 1.5 Intent 页面跳转与传参（课件第 17 页）

**课件说的**：A 页面建 Intent 指定 B 页面 → `putExtra` 传数据 → `startActivity` → 系统调 B 的 `onCreate`

```java
    Intent intent = new Intent(this, GameActivity.class);              // ① 指定目标

    if (debugGrant) {
        intent.putExtra(GameActivity.EXTRA_DEBUG_GRANT, true);
    }
    startActivity(intent);                                             // ③ 启动
}
```

```java
// GameActivity.java 第 171 行 —— 取出数据
private Difficulty readDifficulty() {
    String extra = getIntent() == null ? null : getIntent().getStringExtra(EXTRA_DIFFICULTY);
    ...
}
```

**怎么答**：
> "主菜单点难度按钮时，new 一个 Intent 指定 GameActivity，用 putExtra 把难度名字传过去，
> 然后 startActivity。GameActivity 在 onCreate 里 getStringExtra 读出来，

## 1.6 音频：MediaPlayer 和 SoundPool（课件第 18–23 页）

**课件说的**：
- 音频文件放 **`res/raw`** 目录
- **MediaPlayer**：适合长的、对时间要求不高的（BGM）
- **SoundPool**：适合短的、反应要求高的（游戏音效），支持并发
- 封装一个音频管理类，把音频逻辑和 Activity 解耦
- BGM 有 `bgm.wav` 和 `bgm_boss.wav`，**boss 出现时要暂停游戏 BGM**
- 音效有 4 个：`bullet_hit`、`bomb_explosion`（可选）、`get_supply`、`game_over`

**我们代码里**：[SoundManager.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\audio\SoundManager.java)

| 行号 | 内容 | 对应课件 |
|---|---|---|
| 32 | `public class SoundManager` | 课件第 21 页「封装音频管理类」 |
| 44–50 | `EFFECT_RES.put("hit", R.raw.bullet_hit);` 等四行 | 课件第 20 页「从 res/raw 加载音频」 |
| 109 | `playEffect(String name)` | 课件第 20 页 SoundPool 播放音效 |
| 130 | `playBgm(String name)` | 课件第 19 页 MediaPlayer 播放 BGM |
| 210 | `setMuted(boolean muted)` | 音乐开关（对应实验内容第 3 条） |

**音效在哪触发**：[GameActivity.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\ui\GameActivity.java) 第 123 行 `createListener()`

```java
onEnemyKilled  -> sound.playEffect("hit");     // 英雄机子弹打死敌机
onItemPicked   -> sound.playEffect("item");    // 拾取道具
onBombDetonated-> sound.playEffect("bomb");    // 炸弹爆炸
onBossSpawned  -> sound.playBgm(BGM_BOSS);     // 切 boss 曲
onBossDefeated -> sound.playBgm(BGM_NORMAL);   // 切回普通曲
onGameOver     -> 停止 BGM + playEffect("game_over")
```

**怎么答（核心讲法）**：
> "音频封装在 SoundManager 一个类里。BGM 和音效用的 API 不一样：
> BGM 长、对延迟不敏感，用 MediaPlayer 循环播放；音效短、可能同时触发好几个，
> 用 SoundPool——它预加载解码、延迟低、支持并发播放。
>
> 触发方式是核心层发事件，Activity 把事件翻译成音效。
> 这样核心层完全不知道有声音这回事，它只负责说'我打死了一个敌人'，
> 要不要响、响什么，由上层决定。"

**Boss 换曲怎么做**：
> "核心层检测到分数够了会生成 Boss，同时发出 onBossSpawned 事件，
> Activity 收到就切到 boss 曲。MediaPlayer 切换时先把旧的 stop + release，再加载新的。
> Boss 被打死时再切回来。"

### ✅ 与课件的一致性（这里原本有两处不一致，现在已经改好）

| 课件要求 | 现在的实现 |
|---|---|
| 音频放 `res/raw`（第 18 页） | ✅ 7 个 wav 全在 `app/src/main/res/raw/`，用 `R.raw.xxx` 引用，`assets/` 已移除 |
| `SoundPool.load(context, R.raw.click, 1)`（第 20 页） | ✅ `soundPool.load(appContext, resId, 1)`，资源 id 在第 44–50 行注册 |
| 四个音效文件名（第 23 页） | ✅ `bullet_hit` / `bomb_explosion` / `get_supply` / `game_over`，**文件名与课件完全一致** |
| Boss 出现要暂停游戏 BGM（第 22 页） | ✅ `onBossSpawned` → `playBgm(BGM_BOSS)`；切换时先 stop + release 旧曲再加载新曲 |
| 添加音乐开关（实验内容第 3 条） | ✅ 主菜单「音乐音效：开启/关闭」按钮，状态存在 SharedPreferences，进游戏时读取 |

> 💡 如果老师问「音频为什么不用 `MediaPlayer.create(context, R.raw.bgm)` 的简写」，
> 我们用的是四参重载 `create(context, resId, audioAttributes, 0)`，

## 1.7 Context（课件第 24–25 页）

**课件说的**：Context 是「应用程序环境」，组件不能像普通 Java 对象那样 new 出来。
三种获取方式：`Activity.this`、`View.getContext()`、`Activity.getApplicationContext()`。

**我们代码里**：用的是 **`getApplicationContext()`**

| 文件 | 用法 |
|---|---|
| `Assets.java` | `context.getApplicationContext().getResources()` |
| `SoundManager.java` | `context.getApplicationContext()`（构造时存成 `appContext` 字段） |

**怎么答**：
> "我给 Assets 和 SoundManager 传的是 ApplicationContext 而不是 Activity。
> 因为它们持有的资源生命周期比 Activity 长——如果传 Activity，
> 页面销毁了但管理器还活着，就会把整个 Activity 泄漏掉。"

> 💡 这是个**能体现工程意识**的点，老师问「Context 有什么区别」时正好答。

## 1.8 进程与线程（课件第 26–27 页）

**课件说的**：主线程（UI 线程）负责 UI；子线程做耗时任务；主线程阻塞 5 秒会 ANR。

**我们代码里**：[GameSurfaceView.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\render\GameSurfaceView.java)

```java
public class GameSurfaceView extends SurfaceView
        implements SurfaceHolder.Callback, Runnable {   // 第 27 行：注意 implements Runnable
    private static final long LOGIC_INTERVAL_NS = 40_000_000L;  // 第 30 行：40ms = 25Hz

    public void surfaceCreated(SurfaceHolder holder) { ... }    // 第 75 行：启动线程
    public void run() { ... }                                   // 第 129 行：线程主体
    public void surfaceDestroyed(SurfaceHolder holder) { ... }  // 第 88 行：停止线程
}
```

**这是整个项目最值得讲的技术点**，怎么答：
> "游戏循环跑在自己的线程里，不在主线程。因为主线程还要处理触摸、页面切换，
> 时间不可控，而且阻塞超过 5 秒就 ANR 崩了。
> SurfaceView 提供了独立的绘制表面，可以在子线程里 lockCanvas 画完再 unlockCanvasAndPost。
>
> 逻辑更新固定 40 毫秒一次，也就是 25Hz；渲染尽量贴近屏幕刷新率。
> 两者分离，中间的帧用插值补顺。"

**可能追问：「线程什么时候停？」**
> "SurfaceView 被销毁时系统回调 surfaceDestroyed，我在里面把运行标志置 false，
> 然后 join 等线程真正结束。如果不 join 就返回，线程可能还在画一个已经销毁的表面，会崩。"

## 1.9 Handler（课件第 28–32 页）

**课件说的**：
- 子线程不能直接改 UI，会抛 `CalledFromWrongThreadException`
- Handler 把子线程的消息传到主线程
- 写法：主线程 `new Handler(Looper.getMainLooper())`，重写 `handleMessage`
- 子线程 `sendMessage` / `sendEmptyMessage`
- **课件第 30 页的思考题**：「游戏结束时如何跳转到排行榜页面？」
  答案：BaseGame 在子线程，发消息给 GameActivity，由 GameActivity 加载排行榜

**我们代码里**：[GameActivity.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\ui\GameActivity.java)
第 224 行 `onGameOver()`、第 232 行 `showGameOverDialog()`、第 255 行 `GameHandler`

```java
// 第 224 行：这一步还在渲染线程（子线程）里执行
private void onGameOver(int score) {
    Message message = Message.obtain();
    message.what = MSG_GAME_OVER;   // 第 60 行定义：private static final int MSG_GAME_OVER = 1;
    message.arg1 = score;           // 用 arg1 携带分数
    handler.sendMessage(message);   // 第 228 行：发到主线程的消息队列
}

// 第 255 行：主线程 Handler
private static class GameHandler extends Handler {
    private final WeakReference<GameActivity> activityRef;

    GameHandler(GameActivity activity) {
        super(Looper.getMainLooper());      // 绑定主线程的 Looper
        this.activityRef = new WeakReference<>(activity);
    }

    @Override
    public void handleMessage(@NonNull Message msg) {   // 第 264 行
        GameActivity activity = activityRef.get();
        if (activity == null || activity.isFinishing()) { return; }
        switch (msg.what) {                  // 第 270 行：按 what 区分消息类型
            case MSG_GAME_OVER:
                activity.showGameOverDialog(msg.arg1);
                break;
        }
    }
}
```

**怎么答**：
> "游戏结束的回调是从渲染线程发出的，弹窗必须回主线程做，
> 子线程直接改 UI 会抛 CalledFromWrongThreadException。
>
> 所以我按课件讲的 Handler 机制写：渲染线程里 Message.obtain() 拿到消息，
> 填上 what 标识和分数，用 sendMessage 发到主线程的消息队列；
> 主线程的 Handler 在 handleMessage 里根据 what 分发，再去弹结算框。"

**可能追问：「为什么 Handler 写成静态内部类？课件里是普通内部类」**
> "普通内部类会隐式持有外部 Activity 的引用。如果消息队列里还有没处理完的消息，
> 这个引用就会拖住 Activity 让它无法回收，属于内存泄漏。
> 所以我写成静态类，再用 WeakReference 拿 Activity——拿不到就直接返回，
> 不会再操作已经销毁的界面。"
> （补一句：`onDestroy` 里还调了 `handler.removeCallbacksAndMessages(null)` 清队列。）

**如果老师问「handlerMessage 里能做什么」**：
> "只能做轻量的 UI 更新。耗时的活还得在子线程干完再把结果传过来，否则主线程还是会卡。"

## 1.10 Service（课件第 33–34 页）

**课件说的**：Service 是没有界面的后台组件，适合长期运行、不需要和用户交互的任务。
飞机大战的适用场景：**背景音乐播放**。

**我们代码里**：⚠️ **没有使用 Service，BGM 直接由 SoundManager 管。**

**这条要能讲出理由**（不用的理由充分就没问题）：
> "我们没用 Service。Service 适合'退出界面后还要继续跑'的任务，
> 但游戏 BGM 的合理生命周期和游戏页面完全一致——离开游戏页本来就应该停。
> 用 MediaPlayer 跟着 Activity 的 onPause/onResume/onDestroy 管理反而更准确。
>
> 另外 Android 8 以后对后台 Service 限制很严，要做成前台服务得挂常驻通知，
> 对游戏场景是多此一举。"

> 💡 这个回答既说清了 Service 是什么，又说明了不用的合理性，比硬凑一个 Service 强。

## 1.11 MVC 架构（课件第 35–36 页）

**课件说的**：
- **View**：显示数据
- **Model**：业务逻辑、数据处理
- **Controller**：Activity/Fragment，接 View 的操作，向 Model 请求
- 缺点：Activity 既是 View 又是 Controller，容易臃肿

**我们代码里** —— 比 MVC 分得更细：

| MVC 角色 | 我们的对应 | 目录 |
|---|---|---|
| **Model**（业务逻辑） | `GameWorld`、`AbstractFlyingObject`、各敌机、道具、策略 | `core/`（43 个类） |
| **View**（显示） | `GameRenderer`（画）、`Assets`（图片） | `render/` |
| **Controller**（协调） | `GameActivity`（生命周期、音频、存档）、`GameSurfaceView`（主循环、输入） | `ui/` + `render/` |

**怎么答**：
> "课件的 MVC 里 Activity 既当 View 又当 Controller，容易变臃肿。
> 我们分得更细：核心逻辑放在 core 包里，它是纯 Java、不依赖安卓，
> 所以能在普通电脑上跑单元测试，43 个类配了 22 个测试用例。
> 渲染和输入放在 render 包，Activity 只管生命周期和页面级的协调。
>
> 这么分是因为游戏和普通 App 不一样：普通 App 是一次操作一次刷新，
> 游戏有一个持续的主循环，View 需要每一帧去读 Model 的最新状态。
> 如果照搬 MVC 让 Activity 兼管渲染，Activity 会大到没法维护。"

> 💡 **加分点**：`core/` 里搜不到一个 `import android`。
> 现场可以按 Ctrl+Shift+F 演示。

```java

    @Override public Object getItem(int position)          { }  // 第几行的数据
```

**`getView` 里必须做的一件事：复用 `convertView` + ViewHolder**
（课件第 9 页点名的性能优化）。骨架长这样：

```java
if (convertView == null) {
    convertView = inflater.inflate(R.layout.item_rank, parent, false);
    holder = new ViewHolder();
    holder.tvRank  = convertView.findViewById(R.id.tv_rank);
    holder.tvName  = convertView.findViewById(R.id.tv_name);
    holder.tvScore = convertView.findViewById(R.id.tv_score);
    holder.btnDel  = convertView.findViewById(R.id.btn_delete);
    convertView.setTag(holder);          // 把控件缓存在行视图上
} else {
    holder = (ViewHolder) convertView.getTag();   // 复用，不用再 findViewById
}
```

> **为什么要复用**：列表滚动时每一行都会反复创建/销毁。
> 如果每次都 `findViewById`，滑动会明显卡顿。复用了就只创建一次，后面反复贴数据。

## 2.4 存储方案怎么选（课件第 11–15 页）

**课件对比**：SharedPreferences（键值）、文件存储、SQLite（结构化）

**我们项目里已经有的**：`data/LocalStore.java` 用 **SharedPreferences** 存最高分和皮肤。

## 2.5 SQLiteOpenHelper（课件第 13–15 页）

课件要求的写法：
```java
public class DBHelper extends SQLiteOpenHelper {
    public DBHelper(Context c) { super(c, "aircraftwar.db", null, 1); }

    @Override
    public void onCreate(SQLiteDatabase db) {
        db.execSQL("CREATE TABLE score_list (" +
                "id INTEGER PRIMARY KEY AUTOINCREMENT," +
                "name TEXT NOT NULL, score INTEGER NOT NULL," +
                "difficulty TEXT, created_at INTEGER)");
    }

    @Override
    public void onUpgrade(SQLiteDatabase db, int oldV, int newV) { }
}
```
> `onCreate` 只在你**第一次**装 App 时调一次，建表。之后 App 打开都是直接连已有库。
> 改表结构要改版本号，然后在 `onUpgrade` 里写迁移逻辑。

# 第 4 部分：可能被追问的 20 个问题

## 关于实验三

**Q1：你的难度选择用 Intent 传，如果传的难度不存在怎么办？**
> → `readDifficulty()` 里 try-catch 了 `IllegalArgumentException`，不合法或没传都回退到简单难度。

**Q2：你的 Handler 怎么用的？**
> → 渲染线程里 `Message.obtain()` 拿到消息，填 `what` 标识和 `arg1` 分数，
> `sendMessage()` 发到主线程队列；主线程的 `GameHandler.handleMessage()` 按 `what` 分发。
> 写成静态类 + WeakReference 是为了避免内部类持有 Activity 造成泄漏。

**Q3：为什么音效用 SoundPool 不用 MediaPlayer？**
> → 音效短、触发密、要能同时响多个。SoundPool 预加载解码、延迟低、支持并发（我们设了最多 8 路）。
> MediaPlayer 每次都要 prepare，延迟大，而且一个实例只能放一个音频。

**Q4：BGM 切换时怎么处理？**
> → `playBgm()` 里先判断是不是同一首，是就直接返回不重启；不是就 stop + release 旧的，再加载新的。

**Q5：切到后台音乐要停吗？**
> → 停。`onPause` 里调 `pauseBgm()`，`onResume` 里 `resumeBgm()`。
> 另外还会暂停游戏本身，不然切出去打电话回来就发现自己死了。

**Q6：你们的音频放在哪？**
> → ⚠️ **如实说**：目前在 `assets/videos`，用 AssetManager 打开。
> 如果已经按课件改成 res/raw，就说 "放在 res/raw，用 `SoundPool.load(context, R.raw.xxx, 1)`"。

**Q7：Service 用了吗？**
> → 没用，理由见 1.10（BGM 生命周期跟页面一致，且 Android 8+ 后台服务限制严）。

**Q8：MVC 里你们的 Activity 算哪一层？**
> → Controller。View 是 GameRenderer，Model 是 core 包。

## 关于实验四

**Q9：为什么排行榜用 SQLite 不用 SharedPreferences？**
> → SharedPreferences 是键值，存单值合适；排行榜是一组要排序、可删除、分难度的结构化记录。
> 用 `orderBy "score DESC"` 一条查询就是榜单，删除按 id 删。SharedPreferences 做不到。

**Q10：`onCreate` 什么时候被调用？**
> → 第一次创建数据库时调用一次，建表。之后不会重复调用。

**Q11：改了表结构怎么办？**
> → 改 `DB_VERSION` 版本号，在 `onUpgrade` 里写迁移（比如 ALTER TABLE 加列）。

**Q12：为什么要复用 `convertView`？**
> → 列表滚动时行视图会反复创建。复用就是把滚出屏幕的行拿来改数据再用，
> 省掉 inflate 和 findViewById 的开销，滑动才不卡。

**Q13：`Cursor` 不关会怎样？**
> → 资源泄漏，累积多了会 OOM 或者报 "CursorWindow allocation failed"。

**Q14：删除一行之后列表怎么刷新？**
> → 从数据源 List 里移除，然后 `adapter.notifyDataSetChanged()`。

## 通用/架构

**Q15：你的代码里哪部分是自己写的？**
> → 如实说。建议：Windows 版是自己写的；安卓迁移用了 AI 辅助，
> 但每一处设计取舍能讲清（指南里每条的「怎么答」就是证据）。

**Q16：为什么把游戏逻辑和安卓分开？**
> → 能在普通电脑上跑单元测试（22 个用例），改一行几秒验证；
> 换平台时只重写渲染层；逻辑层是纯 Java，可读性好。

**Q17：25Hz 逻辑、60fps 渲染怎么协调的？**
> → 逻辑每 40ms 推进一次，渲染每帧算出"离上次推进过了百分之几"（alpha），
> 用插值把实体画在中间位置。所以画面是平滑的，但游戏规则还是 40ms 一步。

**Q18：为什么死了不能马上从列表里删？**
> → 碰撞检测正在遍历列表，边遍历边删会抛 `ConcurrentModificationException`。
> 所以先 `vanish()` 打标记，等这一帧所有判定做完，再统一清理。

**Q19：怎么保证线程安全？**
> → 游戏状态只在渲染线程改。主线程的触摸只写 volatile 变量，
> 由渲染线程在每个逻辑步开头统一读取应用。

**Q20：如果网络对战要做，你怎么同步？**
> → 用比分竞赛，不同步游戏状态。只每秒上报分数和血量，
> 服务端判定胜负。因为只同步一个数字，延迟容忍度高得多。
