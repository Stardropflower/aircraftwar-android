# 第 0 部分：Android Studio 零基础操作（约 30 分钟）

## 0.1 打开项目

1. 双击启动 Android Studio（本机在 `L:\android-toolchain\android-studio\bin\studio64.exe`）
2. 欢迎界面点 **Open**（不是 New Project！）
3. 在弹出的目录选择框里选：
   ```
   L:\android-projects\AircraftWar-Android
   ```
   > ⚠️ **选这个目录本身**，不要双击进去选 `app`。选错会变成一个没有构建配置的文件夹。
4. 点 OK，等右下角的进度条跑完（第一次要几分钟，显示 `Gradle Sync`）

**如果它问要不要导入设置** → 选 **Do not import settings**

## 0.2 认识界面（只有 4 个区域要认）

```
┌───────────────┬──────────────────────────────────────┐
│ ① Project    │  ③ 代码编辑区                          │
│   文件树      │     （双击文件在这里打开）              │
│               │                                      │
├───────────────┴──────────────────────────────────────┤
│ ④ 底部标签栏：Build / Run / Logcat / Terminal         │
└──────────────────────────────────────────────────────┘
              ② 顶部工具栏：设备下拉框 + ▶ 运行按钮
```

**① Project 面板（左边）**
默认是 **Android 视图**（按类型分组，看到的是 app/manifests、java、res 等）。
建议点左上角的下拉框切成 **Project 视图**，这样看到的是真实目录结构，和文档里写的路径对得上。

**② 顶部工具栏**
- 设备下拉框：显示你连的手机或模拟器
- **绿色三角 ▶**：编译 + 安装 + 运行
- 甲虫图标 🐞：调试模式

**③ 代码编辑区**
双击左边文件树里的 `.java` 文件就在这里打开。

**④ 底部标签栏**
| 标签 | 什么时候用 |
|---|---|
| **Build** | 编译失败时看红色错误 |
| **Run** | 程序运行时崩溃会在这里显示堆栈 |
| **Logcat** | 打印的日志，**排查问题最有用** |

## 0.3 把游戏跑起来

1. 手机插上 USB、开 USB 调试，**或者**启动模拟器
2. 顶部设备下拉框选中你的设备
3. 点绿色三角 ▶
4. 等底部出现 `BUILD SUCCESSFUL`，手机会自动装上并打开游戏

**如果设备下拉框是空的**：
- 手机没连上 → 检查 USB 调试、换数据线
- 想用模拟器 → `Tools` → `Device Manager` → 启动一个

## 0.4 看日志（出问题时唯一有用的工具）

1. 点底部 **Logcat**
2. 顶部选设备、选应用 `edu.hitsz.aircraftwar`
3. 级别下拉框选 **Error**（只看错误）
4. 关键命令行的等价写法（在 Terminal 里）：
   ```powershell
   adb logcat -d -s AndroidRuntime:E
   ```

**崩溃时会看到什么**：一大段 `FATAL EXCEPTION` + `at edu.hitsz.aircraftwar.xxx(Xxx.java:123)`，
最后那行 `Xxx.java:123` 就是出错的行号。

## 0.5 三个必会快捷键

| 快捷键 | 作用 | 用在哪 |
|---|---|---|
| **Ctrl + N** | 按类名找文件 | 老师说「打开 GameWorld」，直接按 Ctrl+N 输入 GameWorld |
| **Ctrl + Shift + F** | 全局搜文字 | 想知道某个方法在哪被调用 |
| **Ctrl + B**（或 Ctrl+点击） | 跳到定义 | 看到一个方法想看看它怎么实现的 |

再加一个：**Ctrl + F** 在当前文件里搜文字。

## 0.6 看懂 Java 文件开头的两行

每个 `.java` 文件开头都有：

```java
package edu.hitsz.aircraftwar.ui;      // ① 我在哪个"文件夹"里

import android.os.Bundle;              // ② 我要用的外部东西
```

- **package**：相当于文件夹路径。`edu.hitsz.aircraftwar.ui` 就是目录 `java/edu/hitsz/aircraftwar/ui/`
- **import**：声明要用到别人写好的类

> 💡 **一个重要的自检点**：`core/` 目录下的文件**一个 `import android` 都没有**。
> 这是我们有意的设计（后面第 1.11 节会讲为什么）。老师如果问「你的核心层真的不依赖安卓吗」，
> 你就按 `Ctrl+Shift+F` 搜 `import android`，限定在 core 目录，搜不到就是最好的证明。

## 1.1 Android 平台架构分六层（课件第 7–14 页）

**课件画的六层**，从下往上：

| 层 | 大白话解释 | 写 App 的人碰不碰 |
|---|---|---|
| **Linux 内核** | 管驱动、进程内存、电源、WiFi | 碰不到 |
| **HAL（硬件抽象层）** | 把不同厂家的摄像头、蓝牙包成统一接口 | 碰不到 |
| **原生 C/C++ 库** | Webkit、OpenGL（画图）、Media Framework（音视频解码） | 间接用到 |
| **Android Runtime (ART)** | 把 Java 字节码（dex）翻译成 CPU 能懂的机器码 | 间接用到 |
| **Java API Framework** | Activity、View、资源管理、通知……**我们天天调的 API 就在这层** | **主要用这层** |
| **系统应用** | 桌面、电话、相机 | 同层，但不是我们写的 |

**课件第 14 页的结论最有用**：
> 做 **Android 应用开发**，应该研究「Application Framework 层 + 应用程序层」；
> 做系统开发才研究系统库和运行时；做驱动才研究 Linux 内核。

**我们代码在哪**：
`core/` `render/` `ui/` `audio/` `db/` 全部属于最上面的「应用层」，
它们调用的 `SurfaceView`、`SoundPool`、`SQLiteOpenHelper`、`View` 都属于「Java API Framework」。

**怎么答**：
> "课件把 Android 分成六层，做应用开发只关心最上面两层。
> 我们的代码全在应用层，调用的是 Framework 提供的 API——
> 画画面用 SurfaceView、播音效用 SoundPool、存排行榜用 SQLiteOpenHelper。"

## 1.2 API 级别（课件第 6 页）

**课件说了三点**：
1. 唯一标识 Android 平台版本及其框架 API 状态
2. 控制应用安装的**兼容性范围**（最低 API / 目标 API）
3. 运行时根据 API 决定功能实现方式，**避免调用不存在的 API 而崩溃**

**我们代码在哪**：`app/build.gradle`

```gradle
minSdk 33        // 最低能装在 Android 13 及以上
targetSdk 35     // 声明按 Android 15 的行为规范适配
compileSdk 35    // 编译时用哪一版 SDK
```

- `minSdk` 是**兼容下限**：低于 33 的手机装不上
- `targetSdk` 是**行为契约**：系统按这个版本的行为规范对待你的应用（比如 35 会强制 edge-to-edge）
- `compileSdk` 只影响编译期能调到哪些 API

**怎么答（这里有个真实案例，说出来很加分）**：
> "课件第 6 页说『避免调用不存在的 API』，这个我们迁移盘点时真的碰到了：
> Windows 版用 `java.net.http.HttpClient` 发网络请求，但 **Android 上根本没有这个包**，
> 哪怕 minSdk 调到最高也不存在——因为它不在 Android 的 Java API Framework 里。
> 所以迁移时网络层必须换成 OkHttp。
> 这就是课件说的『按 API 决定实现方式』。"

> 💡 顺带能说清「为什么 targetSdk 35 会出现内容被状态栏压住」——那是 Android 15 的新行为，
> 我们靠给页面加系统栏内边距解决的。

**我们代码在哪**：

## 1.7 进程与线程（课件第 21 页）

**这页课件主要是架构图，核心概念两条**：
- 一个应用启动时，系统会启动一个 **Linux 进程**和一个**主线程**
- 主线程也叫 **UI 线程**，负责处理 UI 事件；耗时操作要放到子线程

**我们代码在哪**：
- **主线程**：所有 Activity 的界面、按钮点击、`onTouchEvent` 的分发
- **子线程**：`GameSurfaceView` 里的 `loopThread`，跑游戏循环（每 40ms 一步）

**为什么必须有子线程（课件后续实验会展开）**：
> "主线程被阻塞超过 5 秒会 ANR 崩溃。游戏循环是持续运行的，
> 放主线程一定会卡界面，所以必须开子线程。"

**怎么答**：
> "我们有两个线程：主线程管界面和输入，渲染线程跑游戏循环。
> 两者之间不直接共享可变状态——主线程只写几个 volatile 变量，由渲染线程在每个逻辑步取值。"

## 1.9 架构模式（课件第 23 页）

**课件说的**：
- Android 常见架构模式：**MVC / MVP / MVVM**
- 手段：软件分层、接口隔离
- 目的：**降低耦合，减少迭代改动，增强稳定性，降低维护成本**

**我们实际用的**（比 MVC 更细，接近 MVP 的思路）：

| 角色 | 我们的目录 | 职责 |
|---|---|---|
| Model | `core/`（43 个类） | 纯游戏规则，**零 Android 依赖**，可在 JVM 上单测 |
| View | `render/` | 只负责把 Model 的状态画出来，不改数据 |
| Controller | `ui/` + `render/GameSurfaceView` | 生命周期、输入分发、把 Model 事件翻译成音效/界面反应 |

**「接口隔离」体现在哪**：`GameWorld.Listener`
- 核心层通过这个接口往外发事件（击杀、拾取、炸弹、Boss、结束）
- Activity 实现接口去播声音、弹窗
- 核心层完全不知道 `SoundPool` 和 `AlertDialog` 的存在

**怎么答**：
> "课件说架构模式的目的就是降低耦合。我们做到的形式是三处分层：
> core 是纯逻辑、不依赖安卓，所以能跑单元测试；
> render 只画不改；ui 负责协调。
> 层与层之间靠 GameWorld.Listener 这个接口通信——
> 核心层只管喊『我打死了一个敌人』，要不要播声音是上面决定的。"

## 1.10 调试分析：Logcat（课件第 24–27 页）

**课件讲了两样东西**：
1. **Android Studio 调试器**：断点、变量窗格、求值监视、堆栈
2. **系统日志**：五种级别，优先级 `Verbose < Debug < Info < Warn < Error`

| 级别 | 课件说什么时候用 | 方法 |
|---|---|---|
| Verbose | 最详细的辅助信息 | `Log.v` |
| Debug | 开发阶段详细调试信息 | `Log.d` |
| Info | 关键执行节点（如登录成功） | `Log.i` |
| **Warn** | **潜在问题，不会直接崩，但可能影响功能** | `Log.w` |
| **Error** | **严重错误，会导致功能异常或崩溃** | `Log.e` |

**我们代码里的实际用法**（级别是按课件语义选的，这点能讲）：

| 位置 | 用的级别 | 为什么 |
|---|---|---|
| `ScoreDbHelper.java:61` 建表 SQL | `Log.d` | 正常流程节点，开发期看 |
| `ScoreDao.java:138` 删除行数 | `Log.d` | 同上 |
| `SoundManager.java:87` 音效加载失败 | `Log.w` | 潜在问题：少一个音效游戏还能玩 |
| `SoundManager.java:146` BGM 创建失败 | `Log.e` | 严重错误：没背景音乐了 |
| `GameActivity.java:309` 排行榜写入失败 | `Log.e` | 严重错误：成绩丢了 |

**怎么答**：

**我们各个资源目录在干什么**：

| 目录 | 课件说放什么 | 我们放什么 |
|---|---|---|
| `res/drawable` | 图片 | 启动图标（矢量） |
| `res/drawable-nodpi` | — | **22 张游戏图片**（见下方解释） |
| `res/layout` | 布局 XML | `activity_main` / `activity_rank` / `item_rank` |

> "普通 `drawable` 不带密度限定符，系统会按屏幕密度自动缩放——

> 所以放 `drawable-nodpi`（禁止密度缩放），解码时再设 `inScaled = false` 双保险。"

## 2.4 AndroidManifest.xml（课件第 10 页）

**课件给了各节点说明表**，要点：
- `manifest` 是根节点
- `uses-sdk` 声明 SDK 版本（现代写法改在 `build.gradle` 里了）
- `application` 是组件根节点，带图标、名称

## 2.6 为什么游戏画面不用普通 View（课件第 14–16 页）★

**课件第 14 页一句话点破了**：
> View 是所有界面控件的基类，**绘制与事件都在主线程完成**；
> 游戏画面不用普通 View，而用 SurfaceView——它拥有独立画布，可在子线程高频绘制。

**课件第 15–16 页展开**：

| 项 | View | SurfaceView |
|---|---|---|
| 绘制线程 | 主线程 | **新的子线程** |
| 画布 | 共享主线程画布 | **拥有独立的 Surface 和缓冲队列** |
| 问题 | 如果绘制时间过长，主线程被阻塞，无法响应按键触屏 | 不阻塞主线程 |
| 适用 | 普通界面 | **2D 游戏** |

**双缓冲机制**（课件第 16 页的原图）：
```
CPU 子线程绘图 → 画到 Back Buffer
                     ↓ 每隔 16.6ms 交换
                  Front Buffer
                     ↓ 屏幕以固定频率读取
                    屏幕
```
- **优点**：① 流畅，绘制过程中不会闪烁花屏；② 高效，一次性画完再提交
- **缺点**：图片过大时严重消耗内存

**我们代码在哪**：`render/GameSurfaceView.java`，类声明第一行就写着
```java
public class GameSurfaceView extends SurfaceView
        implements SurfaceHolder.Callback, Runnable {
```

**怎么答**：
> "课件第 14 页专门讲了这件事：普通 View 的绘制在主线程，画得一慢界面就卡死。
> SurfaceView 有独立的 Surface 和双缓冲——CPU 在子线程画到后台缓冲，
> 每 16.6 毫秒和前台缓冲交换一次，屏幕从前台读。
> 好处是不闪烁、不阻塞主线程，缺点是图片太大费内存。
> 我们游戏画面全部走 SurfaceView。"

## 2.7 Activity 生命周期（课件第 17–18 页）

**课件讲的五个状态**：启动 → 活动（获得焦点可交互）→ 暂停（失焦点但仍可见）→ 停止（不可见）→ 销毁

**我们每个回调都有实际用途**（这是能讲出"为什么"的地方）：

| 回调 | 我们在里面做了什么 | 不加会怎样 |
|---|---|---|
| `onCreate` | 装图片资源、算战场尺寸、建游戏世界、挂 SurfaceView、启动 BGM | 什么都没有 |
| `onResume` | 取消暂停、恢复 BGM | 切回来游戏还是暂停状态、没声音 |
| **`onPause`** | **暂停游戏、暂停 BGM** | **切出去打电话回来发现自己已经死了** |
| `onDestroy` | 停渲染线程、停游戏世界、释放音频、关数据库、清 Handler 队列 | 线程泄漏、音频焦点泄漏、数据库连接泄漏 |

**怎么答**：
> "生命周期的关键在 onPause——切到后台时把游戏暂停、BGM 暂停。
> 不然玩家切出去接个电话，回来发现飞机已经撞死了。
> onDestroy 里要把渲染线程 join 掉、音频 release、数据库 close，
> 否则反复进出会泄漏。"

## 2.9 把 BaseGame 重构成 SurfaceView（课件第 20 页）★

**课件给了六条具体要求**，我们逐条对应：

| 课件要求 | 我们的代码 |
|---|---|
| 自定义 SurfaceView 类，实现 `SurfaceHolder.Callback` 和 `Runnable`，初始化 SurfaceHolder、绘制线程、标志位 | `GameSurfaceView` 类声明 + `loopThread` + `running`/`paused` 标志 |
| 重写 `surfaceCreated`：**加载图片**、标志位 true、**启动绘制线程** | 第 75 行：置 `running=true`，新建并启动 `loopThread` |
| 重写 `surfaceChanged`：**获取屏幕宽高** | 第 83 行：不需要重建（渲染器每帧按 Canvas 尺寸算缩放系数） |
| 重写 `surfaceDestroyed`：标志位 false、**终止绘制** | 第 88 行：`stopLoop()`，置 false 并 `join(1000)` 等线程结束 |
| 实现 `run()`：判断标志位 → `lockCanvas` → 用 Canvas API 绘制 → `unlockCanvasAndPost` | 第 129 行 |
| `MainActivity` 里 `setContentView(new EasyGame(this))` | `GameActivity` 里 `setContentView(gameView)`，gameView 按难度创建 |

**我们和课件不一样的两处（能讲出来是加分）**：

**① 图片不在 `surfaceCreated` 里加载**
> "课件把加载图片放在 surfaceCreated。我们放到 Activity 启动时由 `Assets` 统一解码并缓存，
> 因为二十多张图在 surfaceCreated 里解码会拖慢首帧、第一屏会黑一下。
> 而且 surfaceCreated 可能因切后台重建而再次触发，重复解码纯属浪费。"

**② `run()` 里多了两级节奏**
> "课件是画一帧就 sleep 一下。我们把逻辑和渲染分开：
> 逻辑固定 40ms 一步（25Hz），渲染尽量贴近屏幕刷新率，
> 中间用插值把实体画在两步之间的位置。
> 这样游戏数值不变，画面是平滑的。"

**为什么逻辑不能跟着 60fps 走**（这题必问）：
> "所有速度都是按帧算的，敌机 speedY=10 意思是每帧下降 10 像素。
> 如果逻辑从 40ms 改成 16ms，敌机速度就变成 2.5 倍，游戏直接没法玩。
> 所以逻辑步长必须固定。"

## 2.10 五个必踩的坑（课件第 24 页）★

课件的原话是「移动前想一想：五个必踩的坑」，我们逐条对照：

| # | 坑 | 课件的现象 | 我们 |
|---|---|---|---|
| 1 | **资源命名不合法** | R 不生成，`Cannot resolve symbol R` | **踩到了**：三个文件名含大写，迁 res 时全部改小写 |
| 2 | **图片反复加载** | 内存暴涨、卡顿、甚至 OOM | **避开**：`Assets.load()` 一次性解码缓存到 Map，循环里只 `drawBitmap` |
| 3 | **坐标写死像素** | 换机器就跑出屏幕 | **避开**：逻辑坐标固定宽 512，绘制时 `canvas.scale(viewWidth/512)`；战场高度按屏幕比例算 |
| 4 | **绘制线程没停** | 退出后日志刷屏、再进黑屏 | **避开**：`surfaceDestroyed` 置 `running=false` 并 `join(1000)` 等线程真正退出 |
| 5 | **持有 Activity 引用** | 内存泄漏、Activity 无法回收 | **避开**：`Assets` / `SoundManager` 全用 `getApplicationContext()`；Handler 用静态类 + 弱引用 |

**怎么答（建议主动说踩到的那一个）**：
> "课件列的五个坑，第一个资源命名我们真踩了——
> Windows 版有 elitePlus、elitePro 这种驼峰命名，搬到 res/drawable 直接不生成 R 文件。
> 改成全小写就好了。
> 另外四个我们提前规避了：图片一次缓存、坐标不写死像素、销毁时 join 绘制线程、
> Context 一律用 ApplicationContext。"

> 💡 **主动承认踩过一个坑**比声称"全避开了"可信，也说明你真做过。

## 3.8 进程与线程（课件第 26–27 页）

**课件说的**：主线程（UI 线程）负责 UI；子线程做耗时任务；主线程阻塞 5 秒会 ANR。

**我们代码里**：[GameSurfaceView.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\render\GameSurfaceView.java)

```java
public class GameSurfaceView extends SurfaceView
        implements SurfaceHolder.Callback, Runnable {   // 第 27 行：注意 implements Runnable
    private static final long LOGIC_INTERVAL_NS = 40_000_000L;  // 第 30 行：40ms = 25Hz

    public void surfaceCreated(SurfaceHolder holder) { ... }    // 第 75 行：启动线程
    public void run() { ... }                                   // 第 129 行：线程主体
    public void surfaceDestroyed(SurfaceHolder holder) { ... }  // 第 88 行：停止线程
}
```

**这是整个项目最值得讲的技术点**，怎么答：
> "游戏循环跑在自己的线程里，不在主线程。因为主线程还要处理触摸、页面切换，
> 时间不可控，而且阻塞超过 5 秒就 ANR 崩了。
> SurfaceView 提供了独立的绘制表面，可以在子线程里 lockCanvas 画完再 unlockCanvasAndPost。
>
> 逻辑更新固定 40 毫秒一次，也就是 25Hz；渲染尽量贴近屏幕刷新率。
> 两者分离，中间的帧用插值补顺。"

**可能追问：「线程什么时候停？」**
> "SurfaceView 被销毁时系统回调 surfaceDestroyed，我在里面把运行标志置 false，
> 然后 join 等线程真正结束。如果不 join 就返回，线程可能还在画一个已经销毁的表面，会崩。"

## 3.9 Handler（课件第 28–32 页）

**课件说的**：
- 子线程不能直接改 UI，会抛 `CalledFromWrongThreadException`
- Handler 把子线程的消息传到主线程
- 写法：主线程 `new Handler(Looper.getMainLooper())`，重写 `handleMessage`
- 子线程 `sendMessage` / `sendEmptyMessage`
- **课件第 30 页的思考题**：「游戏结束时如何跳转到排行榜页面？」
  答案：BaseGame 在子线程，发消息给 GameActivity，由 GameActivity 加载排行榜

**我们代码里**：[GameActivity.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\ui\GameActivity.java)
第 224 行 `onGameOver()`、第 232 行 `showGameOverDialog()`、第 255 行 `GameHandler`

```java
// 第 224 行：这一步还在渲染线程（子线程）里执行
private void onGameOver(int score) {
    Message message = Message.obtain();
    message.what = MSG_GAME_OVER;   // 第 60 行定义：private static final int MSG_GAME_OVER = 1;
    message.arg1 = score;           // 用 arg1 携带分数
    handler.sendMessage(message);   // 第 228 行：发到主线程的消息队列
}

// 第 255 行：主线程 Handler
private static class GameHandler extends Handler {
    private final WeakReference<GameActivity> activityRef;

    GameHandler(GameActivity activity) {
        super(Looper.getMainLooper());      // 绑定主线程的 Looper
        this.activityRef = new WeakReference<>(activity);
    }

    @Override
    public void handleMessage(@NonNull Message msg) {   // 第 264 行
        GameActivity activity = activityRef.get();
        if (activity == null || activity.isFinishing()) { return; }
        switch (msg.what) {                  // 第 270 行：按 what 区分消息类型
            case MSG_GAME_OVER:
                activity.showGameOverDialog(msg.arg1);
                break;
        }
    }
}
```

**怎么答**：
> "游戏结束的回调是从渲染线程发出的，弹窗必须回主线程做，
> 子线程直接改 UI 会抛 CalledFromWrongThreadException。
>
> 所以我按课件讲的 Handler 机制写：渲染线程里 Message.obtain() 拿到消息，
> 填上 what 标识和分数，用 sendMessage 发到主线程的消息队列；
> 主线程的 Handler 在 handleMessage 里根据 what 分发，再去弹结算框。"

**可能追问：「为什么 Handler 写成静态内部类？课件里是普通内部类」**
> "普通内部类会隐式持有外部 Activity 的引用。如果消息队列里还有没处理完的消息，
> 这个引用就会拖住 Activity 让它无法回收，属于内存泄漏。
> 所以我写成静态类，再用 WeakReference 拿 Activity——拿不到就直接返回，
> 不会再操作已经销毁的界面。"
> （补一句：`onDestroy` 里还调了 `handler.removeCallbacksAndMessages(null)` 清队列。）

**如果老师问「handlerMessage 里能做什么」**：
> "只能做轻量的 UI 更新。耗时的活还得在子线程干完再把结果传过来，否则主线程还是会卡。"

**课件说的**：Service 是没有界面的后台组件，适合长期运行、不需要和用户交互的任务。
飞机大战的适用场景：**背景音乐播放**。

## 3.11 MVC 架构（课件第 35–36 页）

**课件说的**：
- **View**：显示数据
- **Model**：业务逻辑、数据处理
- **Controller**：Activity/Fragment，接 View 的操作，向 Model 请求

**我们代码里** —— 比 MVC 分得更细：

|---|---|---|

## 4.4 存储方案怎么选（课件第 11–15 页）

**课件对比**：SharedPreferences（键值）、文件存储、SQLite（结构化）

**我们项目里两种都用了，各管各的**：

| 数据 | 用什么 | 为什么 |
|---|---|---|
| 本机最高分、当前皮肤、昵称、静音开关 | `SharedPreferences`（[LocalStore.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\data\LocalStore.java)） | 都是**单个键值**，一次读一个值，最轻量 |
| **排行榜记录** | **SQLite**（[ScoreDao.java](L:\android-projects\AircraftWar-Android\app\src\main\java\edu\hitsz\aircraftwar\db\ScoreDao.java)） | 是一组**带顺序、要排序、要删除**的记录，键值存储撑不住 |

**怎么答**：
> "最高分是单个数值，用 SharedPreferences 最合适。
> 但排行榜是一组记录，要按难度筛选、按分数排序、还能删除单条，
> 这是结构化数据，必须用 SQLite——一条 query 带上 `orderBy score DESC` 就是榜单顺序。"

**可能追问：「为什么不用文件存储？」**
> "课件第 11–15 页对比过。文件存储适合大块非结构化数据（比如图片、日志），
> 要自己管格式和解析。排行榜需要按条件查询和局部删除，
> 用文件要么全读进内存再过滤，要么自己实现一套索引，完全是重复造轮子。"

| **增** | `insert(table, nullColumnHack, values)` | 第 65 行 | 用 `ContentValues` 封装一行；返回新行 id，失败返回 -1 |

> `targetSdk 35` 是行为契约，声明按 Android 15 的规范适配；
> `compileSdk 35` 只影响编译期能调到哪些 API。

**Q3：课件说「避免调用不存在的 API」，你们有实际例子吗？**
> → 有。Windows 版网络层用 `java.net.http.HttpClient`（Java 11 引入），
> 但 **Android 的 Java API Framework 里没有这个包**，minSdk 调到最高也不存在。
> 所以迁移盘点时就定了必须换成 OkHttp。

**Q4：Logcat 那五种级别你们怎么用的？**
> → 优先级 Verbose < Debug < Info < Warn < Error。
> 能继续运行的问题用 Warn（某个音效没加载上），功能已经坏了的用 Error
> （BGM 创建失败、排行榜写库失败）；正常流程节点用 Debug（建表、删除行数）。

**Q5：为什么用 Java 不用 Kotlin？**
> → Windows 版就是 Java，逻辑可以直接搬；Kotlin 和 Java 互操作要加适配层，
> 对这个项目是纯负担。而且课程允许 Java。

**Q6：debug 包和 release 包有什么差别？**
> → release 会走 R8 压缩和混淆，包更小、运行更快；debug 保留调试信息和日志。
> 提醒一点：混淆会改类名，所以我们代码里「实体 → 图片」的映射特意用 `instanceof`
> 而不是类名字符串，否则 release 包里会静默失效。

## 关于实验二（代码迁移）

**Q7：迁移不是重写，你们怎么判断哪些能复用？**
> → 扫 `import`，不靠印象。一共 60 个源文件：37 个纯 Java 可原样复用（62%）、
> 9 个只换类型（`BufferedImage`→`Bitmap`）、1 个 `Game` 类保留内核重写外壳、
> 13 个必须完全重写（界面、音效、网络）。

**Q8：为什么游戏画面用 SurfaceView 不用普通 View？**
> → 普通 View 的绘制在主线程，画慢了界面就卡死、点不动。
> SurfaceView 有独立的 Surface 和双缓冲：子线程画到 Back Buffer，
> 每 16.6ms 和 Front Buffer 交换一次，屏幕从前台缓冲读。
> 代价是图片大了吃内存。

**Q9：你们迁移过程中踩过什么坑？**
> → 课件第 24 页列的五个坑，第一个「资源命名不合法」我们**真踩了**：
> `elitePlus.png`、`elitePro.png` 这种驼峰命名放进 res 目录不生成 R 文件，编译报错。
> 全部改成小写解决。另外四个（图片反复加载、坐标写死像素、绘制线程没停、
> 持有 Activity 引用）我们提前规避了。

**Q10：屏幕是 20:9 的，坐标写死 512×768 会怎样？**
> → 会留大片黑边或者错位。我们保留 Windows 版的逻辑宽度 512，
> 高度按屏幕长宽比算（1080×2400 → 512×1138），绘制时用 `canvas.scale` 缩放到实际像素。
> 代价是纵向更"深"、难度略降，可以用刷怪节奏调回来。

## 关于实验三

**Q11：你的难度选择用 Intent 传，如果传的难度不存在怎么办？**
> → `readDifficulty()` 里 try-catch 了 `IllegalArgumentException`，不合法或没传都回退到简单难度。

**Q12：你的 Handler 怎么用的？**
> → 渲染线程里 `Message.obtain()` 拿到消息，填 `what` 标识和 `arg1` 分数，
> `sendMessage()` 发到主线程队列；主线程的 `GameHandler.handleMessage()` 按 `what` 分发。
> 写成静态类 + WeakReference 是为了避免内部类持有 Activity 造成泄漏。

**Q13：为什么音效用 SoundPool 不用 MediaPlayer？**
> → 音效短、触发密、要能同时响多个。SoundPool 预加载解码、延迟低、支持并发（我们设了最多 8 路）。
> MediaPlayer 每次都要 prepare，延迟大，而且一个实例只能放一个音频。

**Q14：BGM 切换时怎么处理？**
> → `playBgm()` 里先判断是不是同一首，是就直接返回不重启；不是就 stop + release 旧的，再加载新的。

**Q15：切到后台音乐要停吗？**
> → 停。`onPause` 里调 `pauseBgm()`，`onResume` 里 `resumeBgm()`。
> 另外还会暂停游戏本身，不然切出去打电话回来就发现自己死了。

**Q16：你们的音频放在哪？**
> → ⚠️ **如实说**：目前在 `assets/videos`，用 AssetManager 打开。
> 如果已经按课件改成 res/raw，就说 "放在 res/raw，用 `SoundPool.load(context, R.raw.xxx, 1)`"。

**Q17：Service 用了吗？**
> → 没用，理由见 1.10（BGM 生命周期跟页面一致，且 Android 8+ 后台服务限制严）。

**Q18：MVC 里你们的 Activity 算哪一层？**
> → Controller。View 是 GameRenderer，Model 是 core 包。

## 关于实验四

**Q19：为什么排行榜用 SQLite 不用 SharedPreferences？**
> → SharedPreferences 是键值，存单值合适；排行榜是一组要排序、可删除、分难度的结构化记录。
> 用 `orderBy "score DESC"` 一条查询就是榜单，删除按 id 删。SharedPreferences 做不到。

**Q20：`onCreate` 什么时候被调用？**
> → 第一次创建数据库时调用一次，建表。之后不会重复调用。

**Q21：改了表结构怎么办？**
> → 改 `DB_VERSION` 版本号，在 `onUpgrade` 里写迁移（比如 ALTER TABLE 加列）。

**Q22：为什么要复用 `convertView`？**
> → 列表滚动时行视图会反复创建。复用就是把滚出屏幕的行拿来改数据再用，
> 省掉 inflate 和 findViewById 的开销，滑动才不卡。

**Q23：`Cursor` 不关会怎样？**
> → 资源泄漏，累积多了会 OOM 或者报 "CursorWindow allocation failed"。

**Q24：删除一行之后列表怎么刷新？**
> → 从数据源 List 里移除，然后 `adapter.notifyDataSetChanged()`。

## 通用/架构

**Q25：你的代码里哪部分是自己写的？**
> → 如实说。建议：Windows 版是自己写的；安卓迁移用了 AI 辅助，
> 但每一处设计取舍能讲清（指南里每条的「怎么答」就是证据）。

**Q26：为什么把游戏逻辑和安卓分开？**
> → 能在普通电脑上跑单元测试（22 个用例），改一行几秒验证；
> 换平台时只重写渲染层；逻辑层是纯 Java，可读性好。

**Q27：25Hz 逻辑、60fps 渲染怎么协调的？**
> → 逻辑每 40ms 推进一次，渲染每帧算出"离上次推进过了百分之几"（alpha），
> 用插值把实体画在中间位置。所以画面是平滑的，但游戏规则还是 40ms 一步。

**Q28：为什么死了不能马上从列表里删？**
> → 碰撞检测正在遍历列表，边遍历边删会抛 `ConcurrentModificationException`。
> 所以先 `vanish()` 打标记，等这一帧所有判定做完，再统一清理。

**Q29：怎么保证线程安全？**
> → 游戏状态只在渲染线程改。主线程的触摸只写 volatile 变量，
> 由渲染线程在每个逻辑步开头统一读取应用。

**Q30：如果网络对战要做，你怎么同步？**
> → 用比分竞赛，不同步游戏状态。只每秒上报分数和血量，
> 服务端判定胜负。因为只同步一个数字，延迟容忍度高得多。
